# Adversarial Review — Hexalith Agents PRD (2026-09-09 revision)

Reviewed: `prd.md` (status `final`, frontmatter `updated: 2026-09-08`, body revised 2026-09-09, 834 lines) and `addendum.md`. The 2026-09-08 adversarial pass (`review-adversarial-general-2026-09-08-validate.md`) was read so that closed findings are not repeated; this pass concentrates on the material that revision introduced and on whether the fixes hold under a literal reading.

## Verdict

I would not sign off. The 2026-09-09 revision closes most of the 09-08 findings by name, and the additions (FR-33, §8.1, the gate/launch-health split) are real improvements. But the three central fixes were written as *guarantees* rather than as *mechanisms*, and each guarantee is false under the PRD's own rules one step later. FR-7 now asserts "no proposal can exist that nobody may approve" while also re-resolving the Approver set at every action from the Conversation's *current* Participants — so the invariant dies the moment the one eligible Approver leaves, and the caller-only exclusion is defeated by a single edit from the other Approver. FR-2 now says a Conversations-side removal "fails closed at the next membership check", while defining that check as an idempotent *join*, which re-admits `hexa` and silently reverses the removal. §8 now names four Conversations seams and claims the Assumptions Index is complete, yet the seams that FR-9, FR-27, and FR-2 actually need — reading Conversation content, message content versions or edit/delete visibility, and participant-state reads — are not among them, so the FR-21 `ready-for-dev` gate will pass stories whose runtime dependency was never registered. Add an authorization contradiction between FR-13 and FR-24/FR-33 (any Participant can read unposted proposal content through Audit Evidence that discovery refuses to show them), a cost reservation that is taken before the context it must price is measured and is never released when a later pre-Provider check fails, and a primary launch-health metric a tenant can opt out of by setting expiry to 23 hours. The document should go back for one more pass that replaces the new invariant sentences with the state-transition rules that would make them true.

## Critical

### C-1. FR-7's segregation of duties is a roster check, not an act check: the caller can approve their own call, and one edit makes the caller the sole Approver

- **Location:** FR-7 (call-time and edit-time bullets, closing bullet), §3 "Approver Policy" (lists "the caller" as a source), UJ-3.
- **Literal reading that breaks:** The call-time rule rejects only when the resolved set *excluding the caller* is empty, "so the caller is never the sole Approver". Nothing forbids the caller from *acting* as Approver when another Approver exists. Policy `{caller, predefined Party P}`: Milan calls, the set is `{Milan, P}`, the check passes, Milan approves his own Agent Call immediately. Then take the edit rule: it rejects an edit "that would leave no Approver other than the editor". P edits; the Approver other than P is Milan, the caller; the edit is accepted; Milan — the caller — is now the only Party who may approve. The call-time invariant "the caller is never the sole Approver of their own Agent Call" is violated after one permitted action, and the caller approves a version another human wrote for him. SM-7's rubber-stamp band will not see this: an edit occurred, so the proposal counts as "substantive".
- **Fix:** Define one eligibility predicate and apply it at every moment: `eligible(X, proposal) = X ∈ resolved(now) ∧ X ≠ caller ∧ X ≠ lastEditor`. Call-time: reject unless some `eligible` Party exists. Edit-time: reject unless some `eligible` Party would exist after the edit (this now excludes the caller). Approval: reject unless `eligible(approver)`. Then either delete "the caller" as an Approver Policy source or state explicitly that a caller-source Party may approve only proposals they did not call, and say so in UJ-3.

### C-2. The "no proposal nobody may approve" invariant is false one membership change later, and proposals with no eligible actor have no exit

- **Location:** FR-7 ("Approver resolution is Conversation-scoped ... current Participants ... at the moment of the action", "no proposal can exist that nobody may approve"), FR-18 (`PostingFailed` remains until "an authorized Approver abandons it"), FR-2, SM-3, SM-C5, §9 retention.
- **Literal reading that breaks:** The call-time set is a snapshot; every later action re-resolves from *current* Participants and *current* read access. The single non-caller Approver leaves the Conversation (or is removed in Conversations, which Agents does not observe): the proposal is `Pending` with an empty eligible set, nobody may approve, reject, or abandon it (all require an Approver with current read access), and it sits until `Expired`. The PRD's own sentence "no proposal can exist that nobody may approve" is therefore false as written, and every such proposal lands in SM-3's denominator and SM-C5's numerator as an approval failure. Worse: `PostingFailed` never expires ("Approval freezes expiry"), its exit is "an authorized Approver abandons it" — but an Approver must "hold current read access to the Source Conversation at the moment of each proposal action" (FR-7). When the post failed *because the Conversation no longer exists*, no Party has read access, the Tenant Agent Administrator's retry can never succeed, and the proposal is immortal: never terminal, so never enters §9's 365-day retention clock, retained forever.
- **Fix:** Add a system disposition: when any action or scheduled re-check finds the eligible set empty, or the Source Conversation gone or inaccessible to the Agents Service Principal, the proposal moves to `Abandoned` with a typed system reason (`NoEligibleApprover`, `SourceConversationUnavailable`), versions preserved; permit the Tenant Agent Administrator to abandon `PostingFailed` proposals without Conversation read access (audited); state that system-abandoned proposals are excluded from SM-3's denominator and reported separately. Rewrite the closing FR-7 bullet as "at creation" rather than "ever".

### C-3. A removal performed in Hexalith.Conversations is reversed by the next call: the "membership check" is an idempotent join

- **Location:** FR-2 (membership and removal bullets), OQ-16, §8 ("Removal of `hexa` needs no Conversations notification").
- **Literal reading that breaks:** Membership is defined as "The Agent joins a Conversation as a participant during acceptance" via `AddParticipantAsync`, idempotent, under the Agents Service Principal. Removal by a Facilitator inside the Conversations UI (the obvious path; §8 says no notification is needed) leaves the Agents-side block unset. The next call reaches the membership step, which is a *join*; `hexa` is absent, so the join is not a "repeated join" no-op — it is a fresh add that succeeds. The PRD's claim that such a removal "fails closed under the same rules" is not what the specified step does; the specified step re-admits the Agent, defeats the Facilitator's removal, and does so under a platform principal. Conversely, the Agents-owned block never removes `hexa` from the Conversations participant list at all — "removal" leaves `hexa` visible to Participants "on the same terms as any other participant" while the PRD says it was removed.
- **Fix:** Split the step into (1) read participant state for `hexa` in that Conversation; (2) if `hexa` was previously joined by Agents and is now absent, treat it as an external removal: set the block, abandon non-terminal proposals, reject the call with `RemovedInConversations`; (3) only if Agents has never joined this Conversation, add. Make the Agents block also call the Conversations removal seam, and add both the participant-state read and participant removal to `EXT-CONV-AI-1` (see C-4).

### C-4. §8 registers four Conversations seams; the guarantees in FR-9, FR-27, FR-2, and FR-18 depend on at least four others that are not registered, so the FR-21 gate cannot see them

- **Location:** §8 Hexalith.Conversations bullet and §8.1 Assumptions Index ("Every `[ASSUMPTION]` tag in this PRD is listed here"), FR-9, FR-27 cache contract, FR-2, FR-18 pre-post re-validation, FR-21.
- **Literal reading that breaks:** The bullet opens by naming "Source Conversation access, complete Conversation Context loading" as dependencies and then defines `EXT-CONV-AI-1` as exactly four seams: membership add, posting, `ParticipantRole.Facilitator`, and an active-Conversation count. Not registered: (a) reading the complete Conversation content and Participant roster under the Agents Service Principal — the single most basic dependency, needed for every call; (b) a per-message content version and visibility of message edit/deletion, which the FR-27 cache key ("keyed by Conversation, message content version, and Content Safety Policy version") and its invalidation rule ("editing or deleting a Conversation Message invalidates that message's verdict") require — nothing in §8 says Conversations exposes either; (c) a participant-state read and a participant removal (C-3); (d) an existence/access check "accessible to the Agents Service Principal" for FR-18 pre-post re-validation and a cross-system deletion signal (see H-2). FR-21 blocks a story from `ready-for-dev` only when a *registered* entry is `Uncommitted`; an unregistered seam blocks nothing, so the gate the PRD relies on is blind exactly where the new contracts are.
- **Fix:** Enumerate the full seam list under `EXT-CONV-AI-1` (content read with tenant scoping, participant roster read with roles, participant remove, message content-version or content hash, existence/access check, deletion notification) each with an `[ASSUMPTION]` tag and an A-index row. For the cache, replace the Conversations-owned "message content version" with an Agents-computed content hash per message taken on each load, so invalidation on edit/delete needs no notification seam at all.

## High

### H-1. Conversation-scoped Approver resolution plus tenant-wide Confirmation mode makes `hexa` unusable in every Conversation that lacks an Approver, and that unavailability is not counted anywhere

- **Location:** FR-7 ("contributes only those holders or Parties who are current Participants"), FR-6 (tenant-wide mode), FR-25 blocked-call counts, SM-C4, §3 "Conversation Facilitator", A-3.
- **Literal reading that breaks:** In a tenant running Confirmation mode, a Conversation whose Participants include no tenant-role holder and no predefined Party yields an empty set and every call is rejected `NoEligibleApprover` — for the life of that Conversation. Predefined-Party and tenant-role sources therefore work only in Conversations those people happen to be in. The only source that resolves in every Conversation is the Facilitator, and a Facilitator-only policy is rejected at configuration time if a Conversation has exactly one Facilitator ("sources can never resolve two distinct Parties") — whether it does depends on unconfirmed A-3, so the flagship configuration in the addendum and UJ-3 may be unconfigurable. Meanwhile SM-C4 and the FR-25 counts track blocks by "Conversation Context Policy, Content Safety Policy, and cost caps" only; `NoEligibleApprover` blocks are invisible, so the tenant sees SM-2 collapse without a signal that says why.
- **Fix:** Add `NoEligibleApprover` (and `RemovedInConversations`) to the FR-25 per-tenant blocked-call counts and to SM-C4. State the trade-off the way OQ-10 does ("hexa is unavailable in Conversations with no resolvable Approver; SM-C4 makes that visible"). Resolve A-3's cardinality now: either "a Conversation may have several Facilitators" or "Facilitator-only is valid when paired with the caller-exclusion rule because the Facilitator is not always the caller" — and rewrite the configuration-time test to say what "can never resolve two distinct Parties" is evaluated against.

### H-2. Audit inspection lets any Participant read unposted proposal content that FR-13 refuses to disclose; the Compliance Inspector is a self-justified tenant-wide reader; Conversations erasure does not propagate

- **Location:** FR-24 access bullets, FR-33 rows "Inspect Audit Evidence ..." and "Apply or release legal hold; request authorized export", §9, FR-13, OQ-21, §3 "Audit Evidence" (includes "generated versions, edits").
- **Literal reading that breaks:** FR-33 grants "A current Participant with read access to the Source Conversation" the right to inspect Audit Evidence containing Conversation-derived content; Audit Evidence includes every generated, edited, and rejected proposal version. FR-13 says proposals on which a requester "was never resolved as an Approver are not listed, counted, or otherwise disclosed". The same Participant is refused in the queue and served in the audit query. Second, the Compliance Inspector needs only "a recorded justification" — self-written, unreviewed — to read and *export* every Agent-derived record in the tenant; there is no second-party approval, no scope limit, no rate limit, and the same role applies legal hold and approves deletion. Third, "Retained evidence is never made uninspectable by the loss of its Conversation" is stated as a requirement: when Conversations deletes a Conversation under a data-subject erasure, Agents' copy of the derived content (prompts, context metadata, generated text quoting the Conversation) survives for up to 365 days by design. There is no cross-system deletion seam in §8.
- **Fix:** Scope participant-based audit inspection to *posted* messages' provenance; unposted proposal versions require Approver resolution or compliance inspection. Give compliance inspection a scope (Conversation or case id), a second-party approval or post-hoc review requirement, and an audit surface the Tenant Agent Administrator can see. Add a Conversations→Agents deletion signal to `EXT-CONV-AI-1` and state that approved deletion in Conversations triggers FR-30 approved deletion of derived content; keep only the non-content tombstone.

### H-3. Cost reservation is taken before the context it must price is measured, and a reservation is never released when a later pre-Provider check fails

- **Location:** §3 "Accepted Agent Call" order ("rate limits, cost reservation, Conversation Context Policy, pre-Provider Content Safety Policy, Approver resolution ..., Agent membership"), FR-28 ("reserves the maximum estimated attempt cost before Provider invocation ... A reservation is released when the Provider outcome confirms no usage occurred"), FR-2.
- **Literal reading that breaks:** The reservation is "the maximum estimated attempt cost", which depends on input tokens, which are only known after the Context Policy step that follows it. Either the estimate is the model's full input limit plus output allowance on every call (grossly over-reserving, so concurrent callers hit the 100% fail-closed boundary on a cap that has not been spent), or the implementer reorders the checks in violation of the normative order. Then four checks run after the reservation — context, safety, Approver resolution, membership — and each can fail. The only release rule is "when the Provider outcome confirms no usage"; a call that never reached the Provider has no Provider outcome. Read literally, a `NoEligibleApprover` rejection holds its reservation for the `Indeterminate` hold period (24 h default) and is then "conservatively settled at the estimated maximum" — the tenant is charged, against its cap, for calls that were rejected before any Provider work.
- **Fix:** Reorder: context measurement before reservation. Add: "A reservation held by a call that fails any subsequent pre-Provider check is released immediately with reason `NotInvoked` and is never settled." State the estimate formula (measured input tokens + reserved output allowance, at the current pricing version).

### H-4. SM-3 is opt-out by configuration, collapses into SM-C5 at the default expiry, and the launch-health consequence is delegated to an unwritten record

- **Location:** §12 SM-3, SM-C5, OQ-11, FR-28 kill-switch bullets, OQ-22.
- **Literal reading that breaks:** SM-3 is "measured on proposals whose configured expiry is at least 24 hours". Expiry is configured per tenant Agent. A tenant that sets 23 hours contributes nothing; a cohort of such tenants evaluates to `InsufficientEvidence`, which "is reported as such" and triggers nothing. At the 24-hour default, a proposal not decided within 24 h is by definition `Expired`, so SM-3 ≥ 80% is arithmetically identical to SM-C5 ≤ 20%: the primary metric and its counter-metric are the same number. Then the consequence: "a miss triggers the launch-health review and, where the recorded trigger conditions are met, the kill switch" — the trigger conditions are "recorded before enablement" somewhere outside the PRD, so the document that calls SM-7 "the metric the §1 thesis would falsify" does not say what happens when it is falsified. The metrics are cohort-wide (proposals "created during a rolling 30-day window") while the kill switch is "tenant-wide"; which tenant is killed on a cohort miss is unstated. Automatic-mode tenants produce no proposals, so neither primary launch-health metric can ever fire for them.
- **Fix:** Measure SM-3 as "decided within min(configured expiry, 24 h)" over all proposals, so no expiry setting excludes a tenant; define SM-C5 independently (share of proposals that reach `Expired` with expiry ≥ 48 h, or drop it). Put the kill-switch trigger conditions in the PRD (per-tenant thresholds, evaluation cadence, who pulls it — see M-1). Add a launch-health metric that applies to Automatic mode (e.g., post-hoc flag or deletion rate of automatic posts).

### H-5. `[ASSUMPTION]` rows in the role matrix and the A-index are "confirmed before the first tenant is enabled" but nothing in `RQ-1` checks that, and A-4's fallback quietly breaks SM-2

- **Location:** FR-33 preamble, §8.1 A-9..A-13 "Retired when", FR-28 `RQ-1` inputs, OQ-22, A-4.
- **Literal reading that breaks:** Five authorization rows (who may call, who may remove, who enables Providers, who approves deletion) and both launch-health thresholds are assumptions retired "when Product confirms". `RQ-1` evaluates "only" the enumerated evidence; an unretired assumption is not on the list, so READY can be recorded with the authorization model still hypothetical. A-4 offers "or Product substitutes an Agents-owned denominator": Agents can only count Conversations it has seen (those with at least one call), so the substitute denominator turns SM-2 into "share of called Conversations that were called" ≈ 100%.
- **Fix:** Add to FR-28: "Any A-index row whose owner is Product or Architecture and that is not retired is an `RQ-1` blocker (`UnretiredAssumption`)." Delete the A-4 fallback or constrain it ("an Agents-owned denominator must count Conversations from a Conversations-side event feed, never from Agent Calls").

## Medium

### M-1. The kill switch has no owner, no state, and no defined effect on pending or approved proposals
- **Location:** FR-28 kill-switch bullet, FR-33 (no row), FR-18 pre-post re-validation, FR-3.
- **Literal reading:** "Disables Agent Calls tenant-wide without deleting proposals." If it is implemented as FR-3 disable, the FR-18 pre-post check ("the Agent is active") sends every `Approved` proposal to `PostingFailed`, exhausts the retry budget in 15 minutes, and strands them (C-2). If it is a distinct state, Approved proposals keep posting as `hexa` while the switch is on. No FR-33 row says who may pull or release it.
- **Fix:** Define a `Suspended` lifecycle state distinct from `Disabled`: blocks calls and posting, freezes retry budgets and holds `Approved`/`PostingFailed` without consuming attempts; pulled by Release Operator or Platform Operator, released by Platform Operator; add the row.

### M-2. The Release Operator is tenant-scoped, sets the "hard enforcement boundary", records readiness, and enables — with no segregation and no owner for real production enablement
- **Location:** FR-33 rows "Configure cost caps", "Record cost-control posture and launch readiness; enable production-like generation", consequence "Every role except Platform Operator is tenant-scoped"; FR-28.
- **Literal reading:** The matrix row enables *production-like* generation; nothing enables *production*. The same role records READY and flips the switch. If the Release Operator can be tenant staff (tenant-scoped role), the cap boundary that FR-33 says "is not self-set" is set by the tenant.
- **Fix:** State whether Release Operator is a platform-staff role assigned per tenant; add a "Enable production for a tenant" row requiring Platform Operator plus a READY `RQ-1` record by a different principal.

### M-3. "Previously resolved as an Approver" makes discovery a write, leaves late joiners undiscoverable, and leaks Conversation activity to removed Approvers
- **Location:** FR-13 discovery bullet, FR-7 Conversation-scoped resolution.
- **Literal reading:** Resolution happens "at the moment of the action"; a tenant-role holder who joins the Conversation after the call is an Approver by FR-7 but was never "resolved" until she acts, and discovery is the action — so either every list query must durably record who it resolved (a read that writes to the aggregate), or late joiners never see the queue. A removed Approver keeps receiving state transitions (`Edited`, `Regenerated`, `Posted`, `Abandoned`) for a Conversation she was removed from — that is activity disclosure about a Conversation she may no longer read.
- **Fix:** Define the durable resolution record as "the set resolved at call time plus any Party who performed a proposal action"; late joiners are discoverable by re-resolution at list time without a write. For access-lost Approvers, return existence and a coarse `Open`/`Closed` status only, and drop them from the pending count.

### M-4. The safety cache key ignores the tenant's mode-specific policy, and per-message caching changes what "the history fails the policy" means
- **Location:** FR-27 cache contract, FR-26 ("stricter mode-specific policy"), OQ-9, OQ-18, FR-33 (policy is Platform-scoped).
- **Literal reading:** The key holds one "Content Safety Policy version", but two policies apply (platform + tenant mode-specific). Publication "invalidates every cached verdict tenant-wide" — the policy is platform-wide, so every tenant's cache goes at once. Per-message verdicts are context-free, yet OQ-9's categories (impersonation, asserting a decision "on a Party's behalf") are only decidable in context; the same history will pass per-message and fail as a whole. And the sole unblock path for a Conversation with one failing historical message is a *platform* policy publication that changes the verdict — a tenant cannot act, and the Platform Operator will not republish for one Conversation.
- **Fix:** Key = (Conversation, message hash, platform policy version, tenant policy version). Say which scan is cached (per-message classification) and which is always live (whole-context checks). Decide OQ-18 with a tenant-actionable path or state plainly that such Conversations are permanently unavailable in V1.

### M-5. No latency bound covers the path from call to acceptance for calls that succeed
- **Location:** §3 "Accepted Agent Call" ("The acceptance timestamp ... starts the NFR-9 latency clocks"), NFR-9, FR-27 ("scan latency is budgeted and measured separately" — no number).
- **Literal reading:** Every gate starts at acceptance; the 2 s gate measures rejections only. A call that loads a 150k-token Conversation, scans it for four minutes, and then is accepted meets every gate.
- **Fix:** Add a call-to-acceptance gate (e.g., p95 ≤ 15 s excluding classifier time, classifier time p95 ≤ N s) and put the scan budget number in NFR-9.

### M-6. OQ-22's "evaluates only" list drops NFR-11 and NFR-12 from `RQ-1`, contradicting FR-28's first sentence
- **Location:** OQ-22, §3 `RQ-1`, FR-28 ("requires ... NFR-11 through NFR-14"), NFR-11 (15-minute recovery exercise), NFR-12 (numeric limits recorded before enablement).
- **Fix:** Add "the NFR-11 recovery exercise and the NFR-12 limit records" to the `RQ-1` enumerations in §3, FR-28, and OQ-22.

### M-7. An `AiAgent` Party can be resolved as an Approver or as a caller
- **Location:** FR-7 (predefined Parties, tenant roles), FR-33 "Call `hexa`: Every Conversation Participant", FR-2 (hexa is a Participant after join).
- **Literal reading:** Nothing excludes `hexa`'s own Party from a predefined-Party source or from tenant roles. A policy naming it passes the configuration check (two distinct Parties), passes call time (an Approver other than the caller exists), and produces a proposal only an AI Party may approve — nobody. The matrix also literally lets `hexa` call `hexa`.
- **Fix:** "Parties of type `AiAgent` are never resolved as Approvers or callers; a policy source that resolves only such Parties is rejected."

### M-8. Human-edited provenance names the editing Party wherever provenance is shown, which can reveal restricted-role membership FR-7 forbids disclosing
- **Location:** FR-17, FR-24, §8 `EXT-CONV-UI-1` markers; FR-7 disclosure bullet.
- **Fix:** Apply the source's disclosure category to the editor identity in Conversation-facing surfaces (show "human-edited" always; show *by whom* only where the policy source is user-visible), keeping the Party in Audit Evidence.

### M-9. Regeneration is an "Agent Call" but the PRD does not say whether Approver resolution and the call-permission restriction apply to it
- **Location:** FR-16, §3 "Accepted Agent Call" (includes Approver resolution), FR-33 call row, UJ-3.
- **Literal reading:** If regeneration re-runs the Accepted-Agent-Call checks with the Approver as caller, a sole non-caller Approver who regenerates is excluded from her own regeneration's set and gets `NoEligibleApprover`; and an Approver outside the tenant role that calling is restricted to cannot regenerate at all. UJ-3 assumes she regenerates and then approves.
- **Fix:** "Regeneration re-runs FR-9 and FR-27 only; it does not re-run Approver resolution or the call-permission check, and the regenerating Approver remains eligible to approve the regenerated version."

### M-10. Conversation Context Policy has no owner in FR-33 and §10 puts it under tenant Agent administration
- **Location:** §10 ("Agent administration: ... Conversation Context Policy"), FR-9, FR-28, FR-33 (no row).
- **Literal reading:** A Tenant Agent Administrator could declare an Approved Bounded Context Behavior through the public surface; "V1 declares none" is then a product statement, not an enforced one.
- **Fix:** Add a row (Platform Operator, Platform scope) and put "declare an Approved Bounded Context Behavior" on the FR-23 deprecate-and-reject register for V1.

### M-11. `AgentSetupWriteStatus.Submitted = 0` cannot be "corrected additively" under FR-23's own rules
- **Location:** FR-23 (`Unknown = 0` bullet vs "No public member or enum value is removed, renamed, or semantically reused").
- **Literal reading:** Moving `Submitted` off zero and putting `Unknown` at zero changes what value 0 means — semantic reuse — and is forbidden within V1.
- **Fix:** Exempt this enum in V1 with a documented client rule, or accept that its correction is a major-version change.

### M-12. `Approved` and `PostingFailed` have no staleness bound, so an administrative retry can post weeks-old content into a Conversation that has moved on
- **Location:** FR-18 (approval freezes expiry; administrative retry after budget exhaustion), FR-33 retry row.
- **Fix:** Give `PostingFailed` a system deadline (e.g., 72 h) after which it is system-abandoned, or require the administrative retry to re-obtain an Approver decision when older than the configured expiry.

### M-13. FR-13's "Conversation status entry" is a Conversations-owned surface not covered by `EXT-CONV-UI-1`
- **Location:** FR-13, §8 `EXT-CONV-UI-1` (action contribution and provenance markers only).
- **Fix:** Either add a status-entry contribution to `EXT-CONV-UI-1` or move the entry to the Agents admin surface.
