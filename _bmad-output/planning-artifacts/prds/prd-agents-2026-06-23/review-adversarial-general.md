## Verdict

I would not sign off. The third update closed the prior Critical and eight of nine Highs the way it said it would, and the FR-18 table, the FR-8 order, edit-time scanning, person-only Approvers, and the FR-34 secrets-custodied comparison value are real improvements. But two of those fixes opened holes of the same class they closed. The AH-2 fix added a `Joined`-and-absent branch that re-adds `hexa` whenever "a clear is newer than the last mirror" — a condition that stays true forever after any cleared block, so a Facilitator who removes `hexa` in Conversations after a clear is silently overruled on the next call, which is the exact negative test the same requirement names (C-1). The AC-1 fix inverted the late-`ARCH-A` default but gave the Release PM an unaccepted, calendar-unbounded deferral that item 6 of the same list denies for dependency exclusions (H-1). Around those sit an external-removal detector that abandons proposals on a single, possibly lagging roster read (H-2), a `PostingPending` state with no durable timeout after process loss (H-3), an automatic-mode post that can be abandoned but has no terminal call status — so its retention clock and its per-Party concurrency slot never release (H-4), a data-handling loosen/tighten rule whose direction is whatever the Platform Operator types (H-5), an attestation whose own wrapper test cannot be passed by the mechanism described (H-6), an FR-8 order that omits the kill switch (H-7), and a trigger review that a single Participant can force and a Release Operator can ignore without consequence (H-8). Each fix is one or two sentences; none needs a new mechanism. One more scoped pass on C-1 and H-1..H-8 would make this signable.

## Findings by severity

### Critical

- **[Critical] C-1. The post-clear "late mirror effect" branch re-admits `hexa` after every later external removal, forever** (FR-2 line 156; negative tests line 160; clear rule line 168; OQ-16 line 1001; Spine AD-7 line 161) — Line 156: "`Joined`, the participant read confirms `hexa` is absent, and a clear is newer than the last mirror: the absence is the cleared mirror's late effect, not a removal; the step re-adds `hexa` idempotently ... stays `Joined`, and accepts." Nothing ever makes the clear *not* newer than the last mirror except a new block. Sequence: Facilitator blocks (mirror confirmed), Administrator clears (`ReadmitPending`), next call re-joins (`Joined`, present). Weeks later a Facilitator removes `hexa` directly in Conversations. Next call: `Joined`, absent, clear newer than the last mirror → re-add, accept, generate. The removal authority is overruled by the Agent it removed, and line 160's own negative test ("a step that re-admits `hexa` from `Joined` when the last mirror is confirmed and no clear is newer does not satisfy this requirement") is not tripped because a clear *is* newer. The Spine's AD-7 has no such branch — `Joined` and absent records the removal unconditionally — and the divergence is not in the §8.1 dated list. *Fix:* Replace line 156's condition with: "`Joined`, the participant read confirms `hexa` is absent, a clear is newer than the last mirror, and no participant read since that clear has confirmed `hexa` present: the absence is the cleared mirror's late effect ... re-add idempotently ... Once a post-clear read has confirmed `hexa` present, a later absence is an external removal on the terms of the previous branch." Add the negative test: "a step that re-adds `hexa` after a post-clear read confirmed it present does not satisfy this requirement." Record the AD-7 divergence in §8.1.

### High

- **[High] H-1. The `DeferredAssumption` deferral is unaccepted, calendar-unbounded, and contradicts four other sentences that say every unretired row blocks** (FR-28 item 9 line 699; §8.1 lines 850, 852; FR-33 line 481; §3 line 115; §0 line 16; OQ-22 line 1007; OQ-24 line 1009) — Item 6 says a dependency exclusion "is itself an `RQ-1` blocker until Product accepts it"; item 9 lets the Release PM defer a late `ARCH-A` row with no acceptance by anyone, and the only bound on the revisit date is the phrase "never unbounded by the calendar", which names no bound. "After the `RQ-1` evaluation is scheduled" is an instant nobody records, so Architecture and the PM can schedule early and make every subsequent row deferrable, including a Security-owned row (§8.1 says a row naming Security is retired only by Security, but says nothing about deferring it). Meanwhile line 16, line 850, OQ-22, and OQ-24 still say every unretired `ARCH-A-n` row in the current index version blocks "whatever its owner" — a row added after scheduling is in the current index version. Nothing says what happens when a deferral's revisit date passes after enablement. *Fix:* In FR-28 item 9: "The deferral is an `RQ-1` blocker until Product accepts it, on the same terms as an item 6 exclusion; the scheduled evaluation instant is a dated launch readiness register entry; a row whose retirement condition names Security cannot be deferred; the revisit date is no later than the first launch-health review; a deferral whose revisit date passes without a recorded retirement or a new Product-accepted deferral is a launch-health finding and, for a row whose FR consequences include a fail-closed path, a kill-switch trigger review." Amend line 850, OQ-22, and OQ-24 to read "blocks `RQ-1` unless deferred under FR-28 item 9".

- **[High] H-2. External removal is detected from one roster read with no read-after-write requirement on the seam, so projection lag after the join abandons the join's own proposal** (FR-2 line 155; line 170; §8 seam 1 line 831, seam 5 line 835; FR-7 line 259 for contrast) — "`Joined`, the participant read confirms `hexa` is absent, the last mirror is confirmed, and no clear is newer ... record `ExternallyRemoved` ... abandon the non-terminal proposals ... A Conversation with no mirror history satisfies 'the last mirror is confirmed'." First call joins `hexa` (seam 1 add, state `Joined`, proposal created). The Conversations participant read model lags by seconds. Second call, or the FR-18 pre-post re-validation ten seconds later: `Joined`, roster without `hexa` → `ExternallyRemoved`, first proposal abandoned `RemovedInConversations`, call rejected. FR-7 required two passes one cadence apart before abandoning on an empty roster precisely "so a momentary absence never abandons"; FR-2 abandons on one absent read. The seam text commits idempotency and typed answers, not read-your-writes. *Fix:* Add to line 155: "An absence is an external removal only when a second participant read, no sooner than the seam's read-consistency bound after the first, confirms it; the first absent read records the marker `RemovalPending`, visible under FR-25, rejects the call with `MembershipUnavailable`, and abandons nothing." Add to seam 1 (line 831): "the participant-state read reflects a completed add or removal by the same principal (read-your-writes) or states its consistency bound."

- **[High] H-3. `PostingPending` has no durable timeout: a process loss mid-post strands the proposal in an uninterruptible state with no exit** (FR-18 line 424; row line 436; NFR-11 line 805; FR-3 line 179) — "`PostingPending` is uninterruptible: nothing leaves it except the posting attempt's own conclusion — an acknowledgement, a typed failure, or an attempt timeout no shorter than the seam's posting timeout." `ExpiresAt` is "enforced on every read and every command, regardless of timer delivery"; the attempt timeout carries no such clause. The process dies after the append is sent; on restart there is no attempt to conclude. No human may abandon it, no clock applies (`PostingWindowElapsed` covers `Approved` and `PostingFailed` only), the FR-7 re-check skips it, and the block/removal rules "apply on exit" — which never comes. *Fix:* Add to line 424: "The attempt timeout is a stored deadline evaluated on every read and command and on recovery, regardless of timer delivery; a `PostingPending` proposal whose deadline has passed is concluded as timed out and moves to `PostingFailed`, after which the `MessageId` lookup applies."

- **[High] H-4. An abandoned automatic post has no terminal `AgentInteractionStatus`, so its retention clock never starts and its per-Party concurrency slot never releases; "Eligible Approver" is undefined for it; and the Spine says automatic mode retries nothing** (FR-8 line 293; FR-11 line 334; FR-18 rows 438–441; FR-32 line 727; §9 line 896; Spine AD-5 line 149) — FR-11 routes an automatic post through `Approved`, `PostingPending`, `PostingFailed`, and the abandon rows, but FR-8 fixes the call's terminal members as "exactly `Denied`, `Blocked`, `ContextBlocked`, `GenerationFailed`, `SafetyFailed`, `Posted`, and `ProposalCreated`" — no `Abandoned`. An automatic post abandoned `PostingWindowElapsed` never reaches a terminal state, so §9's "365 days after the interaction reaches a terminal state" never begins and FR-32's "concurrent non-terminal Agent Calls" bound counts it against the caller until someone notices. The `Approved`/`PostingFailed` → `Abandoned` row names the "Eligible Approver" as an actor, but FR-8 step 6 resolves Approvers only in Confirmation Response Mode, so in Automatic mode the row's human actor is empty and the Administrator's abandon is restricted to gone-or-inaccessible Conversations. Spine AD-5 on disk says "automatic mode itself attempts no further automatic retry; the sole automatic-mode recovery is a new Agent Call" — the opposite of FR-11's "same retry bound" and administrative retry — and §8.1 does not list it. *Fix:* In FR-8: "`Abandoned` is an additive terminal member of `AgentInteractionStatus`, recorded for an automatic post that ends `Abandoned` under FR-18." In FR-11: "For an automatic post the human actor of the FR-18 abandon rows is the Tenant Agent Administrator, without the gone-or-inaccessible restriction; the attempt's per-Party concurrency slot releases when the post reaches `PostingFailed`." Record the AD-5 automatic-retry divergence in §8.1 as a Spine defect.

- **[High] H-5. Loosen-versus-tighten is decided by whoever edits the record, and two of the four fields have no computable direction** (FR-4 line 202; FR-5 line 212; FR-33 lines 468–469; A-10 line 869; FR-24 line 607) — "A change that loosens any field — a longer retention term, training use no longer opted out, a new or broader processing region, or a weaker contractual reference — blocks the model for the tenant immediately ... A change that only tightens continues ... for 30 days." "Broader region" and "weaker contractual reference" are judgements; nothing says who makes them or how. A Platform Operator who wants no outage records a region change as tightening, and every tenant's content leaves under the new terms for 30 days without acceptance — the AH-6 hole, reopened by classification. *Fix:* "The direction of a change is computed, never declared: retention is an integer number of days (longer is looser), training use is a boolean (opted-in is looser), the processing region is a set of region codes (a set that is not a subset of the accepted set is looser), and any change to the contractual reference is looser. A change whose direction cannot be computed is looser."

- **[High] H-6. The FR-34 wrapper test cannot be passed by the mechanism FR-34 describes: the engine identity is self-reported and the canary cannot distinguish encryption from obfuscation** (FR-34 lines 738, 741; A-24 line 883) — The attestation "passes only when every step succeeds and the engine reports an identity and version equal to the register's committed ... target". The canary checks that "the persisted bytes contain no plaintext", the field unseals, and after DEK destruction it "replays as `Erased`". A wrapper around the no-op that base64-encodes on seal, decodes on unseal, returns `Erased` after a flag flip, and reports the committed identity string passes every step. The test at line 741 — "a wrapper around the no-op default that reports itself as production ... must ... report `PayloadProtectionUnavailable`" — is therefore not derivable from the requirement; the AH-7 fix moved the *comparison value* out of the host but left the *compared value* under the host's control. *Fix:* "The engine identity is the signed package identity of the bound engine assembly, verified by Agents against the `EXT-SECRETS-1` value, never a string the engine returns; the canary additionally verifies that a sealed payload cannot be unsealed by an engine instance holding a different tenant KEK, and that the seal output for two identical payloads differs."

- **[High] H-7. The FR-8 "exactly this order" list has no kill-switch step, so a literal implementation accepts calls in a `Suspended` tenant** (FR-8 lines 280–290; FR-3 line 174; FR-12 line 342; FR-28 line 709) — FR-28: "Pulling it disables Agent Calls tenant-wide." - **[High] H-8. The trigger review is forgeable by one Participant and toothless when ignored** (FR-28 line 711; SM-C4 lines 972–975; FR-30 line 632; A-17 line 876) — Numerator: "distinct (Party, Conversation, reason) tuples"; denominator: "distinct (Party, Conversation) tuples" — one pair with three reasons is 3/1, so the share exceeds 100%. A `TriggerReviewOverdue` older than 3 business days escalates to the Platform Operator, who records a disposition or pulls the switch as an audited decision."
