## Verdict

I would still not sign off, but every finding the last gate rated Critical or High is closed in the current text, and the second batch closed them the way it said it would: `PostingPending` is uninterruptible, the Party identity is immutable and AI-typed, `Approved` waits under suspension, the trigger review has four rates, a denominator, a sample, a reviewer, and a deadline, `PostingFailed` exits are classified, FR-34 attests instead of trusting a signal, and the ARCH-A citation is right. What remains is one fail-open in the launch gate that the H-6 fix introduced (a late `ARCH-A` row blocks only if the Release PM chooses to acknowledge it), and nine Highs of a lower class: a state-machine branch that names no outcome and cannot self-heal, an identity guarantee whose enforcement register omits the commands it names, an `Approved` state with no human exit and no clock, an automatic-mode posting path with no lifecycle at all, a 30-day window in which tenant content leaves under terms the tenant has not accepted, an attestation that compares the engine against a value the same operator supplies, a compliance-inspection rule that scope-splitting defeats, an auto-re-admission that trusts whoever can add a participant in Conversations, and a set of statements about the Spine and the register that are false on disk today — including §0's dependency count. None of these needs a new mechanism; each needs one sentence that the current text leaves to the implementer, the Release PM, or the Platform Operator to decide alone. One more scoped pass on AC-1 and AH-1..AH-9 would make this signable.

## Findings

### Critical

- **[Critical] AC-1. `RQ-1` fails open on a late `ARCH-A` row: the party that wants to launch decides whether a known unretired assumption blocks** (FR-28 item 9 line 688; §8.1 line 838) — The headline rule is "No unretired assumption: every §8.1 `A-n` row and every `ARCH-A-n` row in the Architecture Spine table is retired, whatever its owner". The same item then says "An `ARCH-A` row added after the `RQ-1` evaluation is scheduled blocks only once the Release PM records an acknowledgement of it". Architecture discovers a real assumption (say, a Conversations idempotency behaviour the compatibility command did not exercise) two days before the scheduled evaluation and adds the row. The Release PM — whose deliverable is the launch — does nothing; the row does not block; `RQ-1` records READY over a table that contains an unretired row, contradicting the first sentence of the same item and §0's "Every unretired assumption ... blocks `RQ-1`". The prior H-6 fix asked for a guard against Architecture blocking indefinitely; what landed is a guard against Architecture blocking at all once a date is on the calendar, and the "target retirement date" every Architecture-owned row must carry has no consequence when it passes (the Spine's rows read "TBD — target milestone", which is not a date). The gate this whole document hinges on is gameable by inaction. *Fix:* Invert the default: "An `ARCH-A` row added after the evaluation is scheduled blocks `RQ-1` unless the Release PM records a deferral naming the row, its owner, the FR consequences not exercised, and a revisit date; the deferral is itself visible on the FR-30 surface as `DeferredAssumption`." State that a passed target retirement date on an Architecture-owned row escalates the row to Product for a keep-or-retire decision and is reported at the launch-health review. Keep the anti-indefinite-blocking intent by bounding Architecture, not by unbounding the Release PM.

### High

- **[High] AH-1. FR-2 says the Party link and replace commands are on the FR-23 deprecate-and-reject register; FR-23's enumerated register does not contain them** (FR-2 line 148; FR-23 line 557; §3 line 90; OQ-25 line 995) — FR-2: "the shipped Party link and replace commands (Spine AD-7) are on the FR-23 deprecate-and-reject register, and a link or replace naming any Party is a typed rejection". FR-23: "The V1 deprecate-and-reject register is: `CostControlPosture.ReportingOnlyMonitoring` and `CostControlPosture.AcceptedLaunchRisk` ..., `ContentSafetyFailureHandling.BlockWithAuditableOverride` ..., and `ApproverPolicySourceKind.Caller` ... and is listed here so that no consumer treats it as accepted behavior." The register is the enforcement authority and it is closed-form ("is:"). A lazy implementer works from the FR-23 list — that is what the list is for — and leaves the link/replace commands live; the prior C-2 attack (a tenant role re-points `hexa` at a human Party) is back through the door the fix said it locked. The same omission exists for the retired `ApproverPolicySourceKind.Caller` in reverse: it *is* on the list, so the list is clearly meant to be exhaustive. *Fix:* Add to the FR-23 register sentence: "and the Agent Party link and replace commands (FR-2, Spine AD-7; no principal may re-point `hexa`'s Party identity)". Add an FR-23 consequence: "A public command or value that any FR names as deprecate-and-reject is on this register; the register and those FRs are reconciled in the same change."

- **[High] AH-2. The `Joined` + absent + "clear is newer" branch names no call outcome and never self-heals, and the predicate is undefined for a Conversation that was never blocked** (FR-2 line 154; FR-2 line 165; OQ-16 line 986) — "`Joined`, the participant read confirms `hexa` is absent, the last mirror is confirmed, and no clear is newer than that mirror: record `ExternallyRemoved` ... An absence observed while a mirror is unconfirmed or a clear is newer is the mirror's late effect, not an external removal; the state is left as it is." The PRD anticipates the late effect (a duplicate at-least-once removal delivered after `ReadmitPending → Joined`) and then stops. Is the call accepted with `hexa` absent from the roster — in which case Provider budget is spent and the pre-post re-validation, running "the same" membership step, finds the same "late effect" and either posts as a non-member or abandons `RemovedInConversations`, contradicting the branch it just took — or rejected, with which typed reason? Nothing moves the state: the last mirror stays confirmed, the clear stays newer, so every subsequent call to that Conversation lands in the same branch forever. `hexa` is silently, permanently unavailable there, with no state, no marker, and no blocked-call reason, until a Tenant Agent Administrator happens to block and clear it. Worse, in the ordinary case — a Conversation that was never blocked — there is no mirror at all, so "the last mirror is confirmed" is undefined; an implementer who evaluates `lastMirror is null` as *not confirmed* never detects an external removal in any never-blocked Conversation, which is the case the state exists for. *Fix:* Add a branch: "`Joined`, absent, and a clear is newer than the last mirror, or no mirror exists: the absence is not a removal; re-add `hexa` idempotently (the clear or the original join is the standing admission), stay `Joined`, and accept; if the add is refused, reject with `MembershipRejected`." State explicitly: "A Conversation with no mirror history satisfies 'the last mirror is confirmed'." Add both as negative tests, replacing the two history sentences at line 158.

- **[High] AH-3. `ExternallyRemoved` re-admits `hexa` on the say-so of whoever can add a participant in Conversations, and the PRD records no assumption about who that is** (FR-2 line 156; FR-2 line 165; §8 seam 1 line 817; §8.1 A-1, A-21) — "`ExternallyRemoved` and the read confirms `hexa` is present again: record `Joined` and accept, because re-adding `hexa` in Conversations is the removal authority's re-admission." The clause assumes the re-adder is the remover. Seam 1 limits what Agents may add; it says nothing about which Conversations principals may add an `AiAgent` participant, and no `A-n` row records the assumption. A Facilitator removes `hexa` from a Conversation; an ordinary Participant who dislikes the decision adds it back through the Conversations participant UI; the next call re-admits without any Agents-side authority. Compare the block: set by a Facilitator, clearable only by that Facilitator or the Tenant Agent Administrator, "evaluated at clear time". A removal performed in Conversations therefore has *weaker* protection than a block set in Agents, although both are "a rejecting state on the same terms". A hostile tenant gets a re-admission path that bypasses FR-33's clear row. *Fix:* Either (a) record `A-22`: "Conversations restricts adding an `AiAgent` participant to `ParticipantRole.Facilitator` (or the Conversation's administrative role)", owned by the Conversations Maintainer, retired when `EXT-CONV-AI-1` reaches `Committed` with that rule, and state that until it is retired `ExternallyRemoved` + present-again moves to `ReadmitPending`, not `Joined`; or (b) drop the auto re-admission and require the FR-33 clear (already granted to "any current Conversation Facilitator") in every case. State which.

- **[High] AH-4. `Approved` has no human exit and no clock, `PostingFailed` never expires, and the administrative retry has no age bound: approved content can sit outside every retention clock forever or be posted months late into a Conversation that has moved on** (FR-18 table lines 425–433; FR-18 line 438; FR-3 line 176; FR-33 line 478; §9 line 881; deferred M-12) — "Approval freezes expiry: `Approved`, `PostingPending`, and `PostingFailed` proposals never expire." The only rows leaving `Approved` are system rows: re-validation passed, re-validation failed, or removal/block. No Approver, Administrator, or Platform Operator can abandon an `Approved` proposal. Now disable the Agent: "An `Approved` proposal does not start posting while either condition holds: it waits in `Approved`". A Tenant Agent Administrator who disables `hexa` and never re-enables it (or a tenant that stops using it) leaves every `Approved` proposal — approved tenant content under an interaction key — waiting indefinitely, non-terminal, outside §9's "365 days after the interaction reaches a terminal state", with no operator able to end it except by blocking `hexa` in each Conversation, which has the side effect of removing it there. `PostingFailed` has exits but none is time-bound: "always has an exit" is not "always exits". And the audited administrative retry may run a year after approval — "full pre-post re-validation re-run" checks safety, membership, and lifecycle, not whether the Conversation has moved on, and the Approver who approved a reply to a question answered eleven months ago is never consulted. *Fix:* Add a row "`Approved`, `PostingFailed` → `Abandoned` — Eligible Approver; Tenant Agent Administrator (audited) — the `MessageId` lookup finds no posted message (skipped when no post was attempted); permitted while `Disabled` or `Suspended`" (the Spine's "never a human abandon from `Approved`" is then a Spine defect to log). Add a post-decision staleness bound: "A proposal that has been `Approved` or `PostingFailed` for longer than the proposal's original expiry duration, excluding paused time, is system-abandoned with reason `PostingWindowElapsed`, counted as decided for SM-3." Make the administrative retry re-validate against that bound.

- **[High] AH-5. Automatic-mode posting has no lifecycle: no failure state, no retry bound, no `MessageId` lookup, no exit — yet the trigger review counts automatic posts "as one approved and one failed on the same terms"** (FR-11 lines 322–330; FR-12 line 334; FR-28 line 700; NFR-11 line 793; FR-25 line 609; Spine AD-7 "automatic-mode `PostingFailed`") — FR-18's machine is "A Proposed Agent Reply occupies exactly one of the states"; FR-11 says only "the system posts successful generated content". What happens when the append's acknowledgement is lost in Automatic Response Mode? The PRD gives three retries, a 15-minute window, a `MessageId` existence read, `LateConfirmed`, and typed exits to a *proposal*; an automatic post is not a proposal. A lazy implementer either retries until the Conversation answers (bounded only by A-2's uncommitted idempotency) or drops the generated, paid-for content with no status, no evidence of the failure reason, and no exit. The Spine has already invented "automatic-mode `PostingFailed`" to fill the gap — a proposal outcome absent from FR-18 that §8.1's own rule says is "a PRD amendment pending". FR-28's posting-failure rate presumes the state exists. *Fix:* State in FR-11: "An automatic post follows the FR-18 posting rows from `Approved` onward — the generated version is the approved version, the generation success instant is the approval instant — including pre-post re-validation, `PostingPending`, `PostingFailed` with the same retry bound, the `MessageId` lookup, `LateConfirmed`, and the same exits; a `PostingFailed` automatic post is abandonable by the Tenant Agent Administrator on the FR-33 row." Expose the state on FR-25 as the Agent Call's posting outcome.

- **[High] AH-6. A data-handling change runs a 30-day grace during which tenant content leaves under terms the tenant has not accepted, and "the version in force" is ambiguous in the evidence** (FR-4 line 199; FR-5 line 209; FR-24 line 596; FR-33 line 459; A-10 line 859) — "until re-acceptance, calls continue under the previously accepted version for 30 days, after which the model cannot be called for that tenant". A data-handling record documents what the Provider does; changing it to "training-use: not opted out" or a new processing region describes a change that has already happened at the Provider. "Calls continue under the previously accepted version" is a fiction: the content goes to the Provider under the new terms while FR-24 "records the Provider data-handling record version in force" — the accepted one (misleading) or the current one (unaccepted)? The PRD does not say. A compliance auditor asks the tenant to show acceptance for the terms under which its March content was processed, and the answer is a version the tenant accepted for different terms. The grace is a fail-open written to avoid an outage on a Platform Operator's catalogue edit. *Fix:* "A `DataHandlingVersion` change that loosens any field (longer retention, training use enabled, new or broader region, weaker contractual reference) blocks the model for the tenant immediately until the Tenant Agent Administrator accepts the new version; a change that only tightens continues without re-acceptance and notifies. Audit Evidence records both the current `DataHandlingVersion` and the version the tenant accepted; they differ only in the tightening case." Retire the 30-day grace or limit it to tightening changes.

- **[High] AH-7. The FR-34 attestation compares the engine against "the register's committed target", but the runtime "never parses this document" — so the committed identity reaches the runtime through the same host the Platform Operator controls** (FR-34 line 727; FR-28 line 697; FR-33 line 474; §8 line 825) — "it passes only when every step succeeds and the engine reports an identity and version equal to the register's committed `EXT-PROTECTION-1` target". FR-28: "the runtime never parses this document" — the same is true of the register. Where does the runtime get the target? Host configuration, which "the Platform Operator binds ... in the host (`EXT-HOST-1`)". The principal that binds the engine also supplies the value it is compared to; a wrapper that seals with a reversible transform, reports the committed identity string, and passes the canary round-trip clears the blocker. The self-test proves the engine can seal, unseal, and erase *something*; it does not prove the engine is the committed one, which is what the identity clause exists for. *Fix:* "The committed engine identity and version are recorded in the launch readiness register by the Release Operator and provisioned to the runtime as a Release-Operator-owned configuration value through `EXT-SECRETS-1`, separate from host composition; a missing value, or a value that differs from the register, leaves the blocker standing. The attestation records which principal supplied each of the two values." Add to the FR-34 test: a host that binds an engine reporting the committed identity while the Release-Operator value is absent must still block.

- **[High] AH-8. Compliance inspection can be scope-split: N single-Conversation post-hoc inspections cover a tenant with no prior approval, one colleague rubber-stamps them all, and an unreviewed inspection has no consequence** (FR-24 line 590; FR-33 line 476; OQ-30 line 1000; deferred gate L-6) — "any inspection wider than one Conversation requires Platform Operator approval. Post-hoc review by such a second party is permitted only for an inspection scoped to a single proposal or a single Conversation". Inspector B opens 200 inspections, each scoped to one Conversation, each post-hoc; content is read on the spot. Inspector A reviews them within 7 days — the 30-day rule is directional ("cannot approve each other's"), so A approving all of B's is allowed as long as B approves none of A's. The Platform Operator sees "the inspection rate", a number with no threshold and no obligation. If A declines to review, "an inspection not reviewed within that window is recorded as unreviewed" — and B opens the next one; the Spine confirms "already-granted read access is not retroactively revoked". Unilateral tenant-wide content access, one Conversation at a time, remains available to any single Inspector. *Fix:* "Post-hoc inspections by one Inspector touching more than 5 distinct Conversations in a rolling 30-day window are one wide inspection: the sixth requires prior Platform Operator approval. An Inspector with an unreviewed inspection cannot open another post-hoc inspection until it is reviewed or the Platform Operator records a disposition. The inspection rate carries a threshold (A-n) above which the Platform Operator's review is mandatory at the next launch-health review."

### Medium

- **[Medium] AM-1. The `ExpiredWhileSuspended` overlap rule lets a brief pull launder SM-3 and SM-C5** (FR-18 row line 424; FR-28 line 698; §12 lines 947, 961; OQ-27) — "recorded with reason `ExpiredWhileSuspended` when the awaiting window overlapped a `Suspended` period" and such proposals "leave the SM-3 and SM-C5 denominators". A one-minute pull each day (the Platform Operator confirms its own SM-4 event; release needs a justification string) overlaps every awaiting proposal's window; every one of them that later expires — hours or days after release — is excluded. The rule written "so the switch cannot manufacture its own launch-health miss" now lets it manufacture a pass. *Fix:* "`ExpiredWhileSuspended` applies only when `ExpiresAt` fell inside a `Suspended` period, or when the remaining awaiting time at pull was shorter than the suspension's duration." Report the count of `ExpiredWhileSuspended` at each launch-health review next to the switch's pull history.

- **[Medium] AM-2. Release is weaker than pull: either role releases an SM-4 pull with a justification string, no concurrence, no review, no bound** (FR-33 lines 470–473; FR-28 line 698; §3 line 114) — A pull on a security event needs the Platform Operator's recorded confirmation; a pull on operational rates needs a convened review. Release: "Platform Operator or Release Operator, with audited justification". A Release Operator under pressure releases the Platform Operator's SM-4 pull ten minutes later; nothing requires the confirming party's concurrence or a recorded finding that the event is contained. Conversely, a self-confirmed SM-4 pull has no duration bound and no escalation, so one Platform Operator can suspend a tenant indefinitely. *Fix:* "Release of a pull recorded on an SM-4 event requires the Platform Operator's recorded containment finding; release of a review pull requires a recorded review decision. A pull older than 7 days without a recorded review is `SuspensionReviewOverdue` on the FR-30 surface."

- **[Medium] AM-3. Trigger-review episode semantics are undefined, and the Provider-or-generation failure share has no denominator** (FR-28 line 700; A-17) — "A trigger review is mandatory when, over a rolling seven-day window, any of these rates exceeds its threshold". A rolling window exceeds continuously. Is a review owed per evaluation (daily reviews, then `TriggerReviewOverdue` noise) or per episode (one "continue" decision silences a condition that persists for months)? The Release Operator decides, alone, in the direction of fewer reviews. "The Provider-or-generation failure share above 20%" — share of Agent Calls, of Accepted Agent Calls, of distinct tuples? The other three rates say; this one does not. *Fix:* "A review decision is valid for 7 days or until a rate rises by a further 10 points, whichever first; a persisting condition then requires a new review." State the failure-share denominator as Accepted Agent Calls that reached Provider invocation in the window.

- **[Medium] AM-4. A tenant can force the Release Operator into mandatory reviews on demand** (FR-28 line 700; FR-33 line 466; FR-32 line 707) — "a rejection at a limit the Tenant Agent Administrator lowered counts", "cost caps" is a blocked-call reason, and "for a tenant with fewer than 5 calling Parties it is every Party that called and 20 Agent Calls". A Tenant Agent Administrator lowers the rate limit to one call per day (or the cap to near zero), four Parties make 20 calls, blocked share reaches 100%, and the Release Operator must convene and record a review within one business day or be recorded `TriggerReviewOverdue` — repeatable weekly across every tenant that wants attention. The previous fix made tenant-lowered limits count to catch an invisible outage; it also handed the trigger to the tenant. *Fix:* Count tenant-caused rejections in the FR-25 surface and the tenant's own launch-health view, but let the review for a condition composed only of rejections at tenant-lowered limits or caps be a recorded acknowledgement rather than a convened review; a condition with any platform-caused reason keeps the convening bound.

- **[Medium] AM-5. FR-8 still runs the paid classifier and the cost reservation before two free, local rejections, so a blocked Conversation burns classifier budget and the NFR-9 fast gate cannot see the checks behind the scan** (FR-8 lines 276–286; FR-27 line 670; NFR-9 line 791; deferred M-6) — The order is context (5), reservation (6), safety scan (7), Eligible Approver resolution (8), membership (9). The Conversation Agent State "is authoritative the moment it is written, independent of whether Conversations is reachable" — a local read, free, and decisive (`Blocked` "rejects every call ... on it alone"). It is checked ninth, after the context load, the reservation, and the classifier call. A Participant in a blocked Conversation spends a classifier call per attempt up to the rate limit, and the `RemovedInConversations` and `NoEligibleApprover` rejections that NFR-9 counts as "require no content safety classifier call" occur after the classifier call, so their p95 ≤ 2 s gate is unmeasurable. *Fix:* Split step 9: "2a. Conversation Agent State (`Blocked`, `ExternallyRemoved`) — local read" immediately after lifecycle; move Eligible Approver resolution (8) before the reservation (6); leave the roster-dependent join last.

- **[Medium] AM-6. SM-4's completeness rule demands a recorded denial for FR-33 rows that are not callable operations, so the gate is permanently `InsufficientEvidence` or the telemetry is staged** (§12 line 939; FR-33 rows 470, 471, 474) — "SM-4 is `InsufficientEvidence` unless every FR-33 row has at least one recorded denial in qualification telemetry". "Bind the production payload-protection engine in the host composition" is a deployment act; "Confirm an SM-4 event" and "Convene and record the kill-switch trigger review" are human process rows. No runtime can record a denial of them. A tester who needs READY records a synthetic denial, and the security gate's evidence is now partly staged. *Fix:* "The SM-4 completeness rule applies to every FR-33 row that is a callable operation on the §10 public surface; the PRD lists the exempt rows (bind engine, confirm SM-4 event, convene review, Security approval), whose evidence is the recorded artefact each row names."

- **[Medium] AM-7. A permanently refused mirror makes a block unclearable and `MirrorPending` eternal; whether the Agents Service Principal may remove a participant is not in seam 1** (FR-2 lines 164–165; §8 seam 1 line 817; A-1) — "the mirror is retried until it succeeds" and "A clear is refused with a typed reason while a mirror entry is sent and unacknowledged". Seam 1 commits a removal "answering typed 'already absent' as a confirmed no-op"; it does not commit that Conversations authorizes the Agents Service Principal to remove a participant. If Conversations refuses (`MembershipRejected` is a named outcome for exactly this principal), the entry is re-sent forever, every clear finds an entry "sent and unacknowledged", and the Facilitator who set the block can never clear it. The block still works — that is the fail-closed half — but the clear row in FR-33 is dead and `MirrorPending` is not a transient state. *Fix:* "A typed permanent refusal confirms the mirror as `MirrorRefused`, visible under FR-25 and counted as an unavailable-call signal; only a transient failure is retried, each attempt with a timeout, and a clear is refused only while an attempt is in flight." Add the removal authorization to A-1's text.

- **[Medium] AM-8. The computed subject set makes the Tenant Agent Administrator branch dead in single-Administrator tenants, and the PRD and Spine now differ on Administrator turnover** (FR-24 line 590; FR-33 line 476; Spine AD-22) — "plus the Tenant Agent Administrator whose configuration version was in force for any call in scope. The second party is the Tenant Agent Administrator when outside that set". In the common tenant with one Administrator, every call ran under that Administrator's configuration, so the Administrator is always a subject and the "common case" second party is always the Platform Operator or a second Inspector — which, with the 30-day anti-reciprocity rule and two Inspectors, means the Platform Operator alone after the first pair. Fail-closed, but the design intent (tenant-level oversight) is defeated silently. The Spine resolves it with "the current Administrator when not one of the historical principals recorded in the subject set"; the PRD's text does not say "principal" or "historical". *Fix:* Adopt the Spine's wording: "the subject set holds the specific Administrator principal(s) whose configuration version was in force; the second party is the current Tenant Agent Administrator when that principal is not in the set". State the consequence for single-Administrator tenants explicitly.

- **[Medium] AM-9. Agent Instructions are declared not protected content, retained for the life of the tenant plus 365 days, exempt from erasure and approved deletion, and FR-21 still calls "the content fields of Audit Evidence" content-bearing** (FR-34 line 731; §9 lines 881–882; FR-1 line 139; FR-21 line 526; FR-31 line 648) — "Agent Instructions and configuration audit are not protected content ... so `hexa` can be configured before the engine is `Available`". Tenants will write instructions like "never mention the pending acquisition of X" or paste customer lists. FR-1 records "prior value ... and new value" of every instruction change; §9 keeps them "for the life of the tenant plus 365 days"; approved deletion "erases or redacts protected sensitive payloads" — instructions survive it. A tenant that offboards cannot have its instructions erased for a year. The reason given (configure before the engine is available) trades a launch convenience for an unbounded retention of tenant-authored text with no owner recorded for the decision. Separately, FR-21 line 526 lists "the content fields of Audit Evidence" as content-bearing while FR-34 says configuration audit — which carries instruction values — is not; an implementer picks one. *Fix:* Either protect instructions under an Agent-level key with erasure on tenant offboarding, or keep them unprotected and add to §9: "Agent Instructions and their audit history are erased on tenant offboarding or on approved deletion naming the Agent; this exemption from interaction-key protection is a Governance decision (OQ-n) with owner and revisit date." Reconcile FR-21's phrase to "the content fields of interaction Audit Evidence".

- **[Medium] AM-10. Any Participant with write access can switch `hexa` off in a Conversation by posting one policy-failing message, the block is attributed to the caller, and the offending message and its author are not recorded** (FR-27 line 669; FR-26 line 642; OQ-18; SM-C4 line 957) — "A Conversation whose scanned history fails the active policy stays blocked for generation until that history has been re-evaluated under a policy it passes ... a Participant may edit or delete the message there".
