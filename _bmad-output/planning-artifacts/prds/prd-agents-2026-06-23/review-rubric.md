### Findings

- **medium** `Approved` proposals cannot "complete on their own terms" while `Suspended`, because pre-post re-validation checks `Suspended` (§ FR-28 line 673 "lets `Approved` and `PostingPending` proposals complete or fail on their own terms"; OQ-27 "`Approved` and `PostingPending` complete on their own terms"; FR-18 line 426 re-validates "the Agent is `Active`, its tenant not `Suspended`"; table rows 412–413; row 417 "tenant not `Suspended`") — the table's `Approved → PostingPending` guard is "Pre-post re-validation passed", and that re-validation fails on `Suspended`, so every `Approved` proposal at pull time goes to `PostingFailed` with its retry clock paused; "complete" is not a reachable outcome. Both readings are safe, but they differ in what a Tenant Agent Administrator sees on release (a burst of `PostingFailed` retries versus already-posted content), in the SM-3 posting-failure rate (≤ 2%), and in the FR-28 trigger review's posting-failure numerator, which a kill-switch pull would then inflate. *Fix:* Decide: either "a pull fails any `Approved` proposal whose posting has not started to `PostingFailed(TenantSuspended)`, excluded from the posting-failure numerators", and reword FR-28/OQ-27 accordingly; or exempt an already-`Approved` proposal from the `Suspended` term of re-validation and say so in FR-18 line 426.
- **medium** The FR-18 table has no system row for the `PostingFailed` exit the prose promises, and the re-check that would drive it is scoped to awaiting proposals only (§ FR-18 line 423 "or the system abandons it under FR-7 on an authoritative answer that the Source Conversation is gone"; table row 415 `PostingFailed → Abandoned` actor "Eligible Approver; Tenant Agent Administrator"; row 410 system abandonment only from `Pending`/`Edited`/`Regenerated`; line 402 "any other (from, to) pair is rejected"; FR-7 line 246 "A scheduled re-check runs over every awaiting proposal") — the table lists actors per row, so a system `PostingFailed → Abandoned(SourceConversationUnavailable)` is a rejected transition, and FR-7's re-check never visits `PostingFailed` anyway. The prose's fourth exit does not exist. An implementer will either add the row (and extend the re-check) or drop the sentence, and SM-3's "system-abandoned proposals leave the denominator" moves with the choice. *Fix:* Add a row `PostingFailed → Abandoned (SourceConversationUnavailable) | System | Authoritative answer that the Conversation is deleted or the Agents Service Principal is denied (FR-7); the MessageId lookup finds no posted message`, and widen FR-7's re-check to "every awaiting or `PostingFailed` proposal".
- **medium** The `MessageId` lookup has no authoritative-absent outcome, so the FR-33 "gone or inaccessible" abandonment can be refused indefinitely (§ FR-18 line 424 "If the lookup itself is unavailable, the exit is refused"; FR-33 row 458 "Abandon a `PostingFailed` proposal whose Source Conversation is gone or inaccessible ... no Conversation read access required"; FR-7 line 246 treats "deleted" and "Agents Service Principal is denied" as authoritative) — FR-7 distinguishes an authoritative answer from an unavailable one; the lookup rule distinguishes only present / absent / unavailable. When the Conversation is deleted or the principal is denied, the seam-2 existence read returns neither a message nor a plain "absent"; whether that is "unavailable" (exit refused) or "absent" (exit allowed) is the entire question FR-33's row exists for, and the page does not answer it. *Fix:* In FR-18 line 424: "A lookup that returns an authoritative deletion or denial (FR-7) counts as *no posted message*; only a transient failure is *unavailable*." Cite it from the FR-33 row.
- **medium** `ExternallyRemoved` and `Blocked` are written both as alternatives and as a pair, and nobody is named to clear `ExternallyRemoved` (§ §3 line 97 "exactly five states"; FR-2 line 153 "record `ExternallyRemoved`, set the Agents-owned block"; line 160 "Setting the block records `Blocked`"; line 161 "records `ExternallyRemoved` and sets the block itself"; line 160 "A block is cleared only by the authority that set it or by the Tenant Agent Administrator"; OQ-16 "`Joined → (ExternallyRemoved | Blocked) → ReadmitPending`") — if setting the block records `Blocked`, the detecting step writes two states into a record that holds one; if it does not, `ExternallyRemoved` is a block that no "setting authority" set, so only the Tenant Agent Administrator can clear it and the Facilitator who removed `hexa` in Conversations cannot re-admit it — which may be intended but is not said. The mirror outbox is also undefined for this state: `MirrorPending` would be raised to remove a participant that is already absent. *Fix:* State that detection records `ExternallyRemoved` (not `Blocked`), that `ExternallyRemoved` carries no `MirrorPending`, and that it is cleared to `ReadmitPending` by the Conversation Facilitator or the Tenant Agent Administrator (add the actor to the FR-33 clear-block row). Delete "set the Agents-owned block" from line 153 or define it as "the rejection effect of `Blocked`, without a mirror".
