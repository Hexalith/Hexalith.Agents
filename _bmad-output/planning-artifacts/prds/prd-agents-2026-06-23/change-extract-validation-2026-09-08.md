### C1 — SM-3 known-unattainable under permitted expiry range
- Reviewer: rubric
- PRD locations: §12 SM-3; §13 OQ-3, OQ-19; FR-28
- Defect: OQ-3 permits expiry "from 1 hour through 30 days"; SM-3 requires "95% of Proposed Agent Replies ... reach a terminal state within 26 hours" and counts `Expired` as terminal, so the metric measures expiry configuration, not approval behavior, and cannot be met by a 30-day-expiry Agent unless 95% are decided by humans within 26 hours regardless. OQ-19 records both defects ("SM-3's 26-hour terminal threshold is unattainable for any Agent configured with an expiry beyond 24 hours under OQ-3" and "SM-3 measures the expiry setting rather than approval behavior") and defers them. FR-28 makes `RQ-1` depend on live SM attainment and its last consequence says an `InsufficientEvidence` primary metric forces NOT READY. A `final` PRD whose launch gate depends on a metric it declares broken cannot support a READY/NOT READY decision.
- Recommended fix: Either (a) re-express SM-3 in terms of human-decision latency (e.g. "95% of proposals receive an Approver decision — `Approved`, `Rejected`, or `Abandoned` — within N hours of creation, measured on proposals whose expiry is ≥ N hours") with expiry rate as a separate counter-metric, or (b) constrain OQ-3's range to ≤ 24 hours for launch tenants and re-open the range post-launch. Whichever is chosen, mark SM-3 as provisional in §12 until the OQ-19 escalation lands, so `RQ-1` is not evaluated against a metric the PRD disowns.

### C2 — FR-7 segregation/access rules make Confirmation Mode unconfigurable
- Reviewer: adversarial
- PRD locations: §4.3 FR-7 (consequences on segregation of duties, access guarantee, configuration-time rejection, "bare tenant role", edit rule); UJ-3; §13 OQ-14
- Defect: FR-7 says "The caller may not be the sole Approver of their own Agent Call, and the approving Party must differ from the Party that last edited the version being approved. A policy configuration that cannot satisfy this segregation of duties is rejected at configuration time." Whether the caller is the sole Approver is only knowable at *call* time. Two literal readings, both wrong: (a) reject Facilitator-only at configuration time because a Facilitator *could* call — then UJ-3's default configuration is illegal and, because the same FR also rejects "a bare tenant role whose holders are not guaranteed Conversation access" (predefined Parties are equally not guaranteed access), no single-source policy survives validation; (b) accept it and at call time either reject the Facilitator's call with no stated reason code, or create a `Pending` proposal that no Party may approve, which sits until `Expired` and pollutes SM-3's expiry rate. The edit rule has the same hole: with a single Approver, the moment she edits, the proposal becomes unapprovable ("a second authorized Approver would have to approve") and nothing says edit must be refused when no second Approver exists. The adversarial verdict names this as "the single biggest way this PRD gets misbuilt": a fully compliant implementation of §4.3 leaves Confirmation Response Mode (UJ-3) without a valid configuration.
- Recommended fix: Split the rule into a configuration-time check (policy must be able to yield ≥2 distinct Parties *or* must include a fallback source) and explicit call-time and edit-time behaviors: if the resolved Approver set for this proposal is {caller} → typed rejection of the call before Provider work; if an edit would leave zero eligible approvers → typed rejection of the edit. Define "bare tenant role" or delete the phrase; decide whether predefined Parties are permitted at all under the access-guarantee rule.
- Code facts cited: n/a (adversarial); note from drift claim ledger: "Caller not sole approver; approver ≠ last editor; rejected at configuration time" is NOT-YET-IMPLEMENTED — no check in `AgentAggregate.ValidateAndNormalizeApproverPolicy` or `AgentInteractionProposalApprovalOrchestrator`; `AgentGeneratedVersion.EditorPartyId` is recorded.
- Depends on / interacts with: M-R1 (rubric medium proposes the exact call-time fail-closed consequence text), H5 (FR-7 vs FR-13 visibility), H7 (role matrix / who holds Approver roles), H12 (`ConversationOwner` wire name for the Facilitator source), M-D4 (disclosure category per policy vs per source), M-D3 (approval path does not compare approver to `EditorPartyId`), L-A3 and L-A5 (FR-7 wording).

### C4 — FR-24 audit access rule defeats Compliance Operator

### H9 — Safety-verdict cache unversioned; conflicts with FR-26
- Reviewer: adversarial
