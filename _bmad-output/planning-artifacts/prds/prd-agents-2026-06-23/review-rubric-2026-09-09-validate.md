## Overall verdict

**Good.** The PRD holds up as a governing requirements authority: the §1 thesis is specific and the metric set can falsify it (SM-7), §13 states 23 decisions with owners and what was given up, the FR-2 removal contradiction that was the only high finding at the gate is closed by a three-part membership step that detects an external removal before it would re-join, the configuration-time segregation predicate is now stated, and the 17 unconfirmed inferences are tagged, indexed, owned, and wired into `RQ-1`. What is at risk is a small cluster of rules an implementer will otherwise decide alone — four decidability gaps carried forward from the gate and one new state-machine ambiguity introduced by the FR-2 repair — plus a headline status line in §0 that no longer matches the register it cites. None of these blocks UX, architecture, or story extraction; the §0 count is the one a reader will notice first.

## Decision-readiness — strong

Decisions are stated as decisions. §13 carries 23 rows with owners and amendment dates; the three *Deferred* rows (OQ-15, OQ-18, OQ-23) each have a revisit condition, and OQ-18 has a date (A-14). Trade-offs name what was given up: OQ-10 ("`hexa` is unavailable in Conversations that outgrow the budget, in exchange for never sending a silently reduced context"), FR-7's last consequence ("That trade-off is accepted deliberately, on the same terms as OQ-10"), FR-6/OQ-20 ("a tenant that wants confirmation for sensitive Conversations runs Confirmation Response Mode for all of them"). §0 confronts the `status: final` objection head-on and §8 line 720 reports "only `EXT-HOST-1` is `Committed`" without softening.

### Findings

- **medium** "More restrictive of two policies" and "stricter mode-specific policy" are still not computable (§ FR-26 consequences 4 and 7, lines 575 and 578; FR-26 preamble line 568; FR-33 row line 420) — **still stands, unchanged.** "each retry, approval-time check, and pre-post check uses the more restrictive of the initial attempt's policy and the then-current active policy." Two policy documents with different category sets, thresholds, and handling rules are not totally ordered; the only implementation is "must pass both", which the text never says. An implementer will choose between "pass both" and "pass the newer" and either choice is defensible from the page. *Fix:* Replace with "the content must pass every applicable policy version — the initial attempt's and the then-current active policy; a mode-specific policy is applied in addition to, never instead of, the platform policy." Mirror in OQ-9's last sentence.
- **medium** FR-31's assertion category blocks the summaries UJ-2 exists for, and OQ-9 states a narrower rule than FR-31 (§ FR-31 consequence 2, line 587; OQ-9 line 865; UJ-2 line 56; FR-17 consequence 4, line 382) — **still stands, and has acquired an internal drift.** FR-31 blocks content "that asserts a decision, commitment, or approval on a Party's behalf"; OQ-9 says only "asserts a decision on a Party's behalf". Milan's job is "interpreting the prior discussion"; "Milan agreed to ship Friday" asserts a commitment on Milan's behalf, and because FR-17 scans human-edited versions "on the same terms", an Approver who writes "the team approved this plan" is blocked at approval time. No classifier separates reporting from asserting, so the rule is a no-op or blocks the core use. *Fix:* Narrow both to first-person impersonation ("content written in the voice of a named Party or presented as that Party's own statement") and state that reporting a Party's position from Conversation content is permitted. Make FR-31 and OQ-9 say the same thing.
- **medium** The Agent Call still has no public state contract, and the shipped code has two competing ones (§ FR-8; FR-10; FR-12; FR-23 consequence 4; FR-25 consequence 2, line 544; §10 line 789 "Agent Call status") — **still stands, and is sharper for a brownfield PRD than the gate run recorded.** FR-18 adopts the shipped `ProposedAgentReplyState` by name; nothing does the same for the call, yet FR-25 requires status to "distinguish configuration errors, authorization failures, context policy failures, content safety failures, Provider failures, generation failures, pending approvals, and posting failures" and §10 exposes "Agent Call status". `src/Hexalith.Agents.Contracts/AgentInteraction/AgentInteractionStatus.cs` declares 28 values (`Requested`, `Authorized`, `Denied`, `Blocked`, `ContextReady`, `ContextBlocked`, `Generated`, `GenerationFailed`, `SafetyFailed`, `Posted`, `PostingFailed`, plus 16 `Proposal*` values that duplicate FR-18's machine), `src/Hexalith.Agents.UI/Components/Shared/AgentCallStatus.cs` declares a different 14-value set with `Unknown` last rather than `= 0`, and `AgentInteractionContextMode` has `Unknown | Full | Bounded` with no `Blocked` (FR-9 says `Blocked` is additive, which is consistent). FR-9's `Blocked` and FR-12's `Indeterminate` name two values but not the set they belong to. UX will draw status chips and stories will write acceptance criteria against whichever enum they find first. *Fix:* Add an FR-8 consequence that names the public Agent Call state contract the way FR-18 does — either adopt `AgentInteractionStatus` minus the `Proposal*` duplicates, or declare a new set (accepted; blocked-by authorization / context / safety / cost / rate limit / approver / membership; generating; generated; `Indeterminate`; posted; posting failed) — mark which are terminal, and place the UI-only enum and the duplicated `Proposal*` values on the FR-23 non-conformance list.
- **medium** p99 over 30 executions is the sample maximum, stated in three places (§ NFR-9 line 697; FR-28 consequence 6, line 617; OQ-5 line 861; §11 line 818) — **still stands, unchanged.** With n = 30 the 99th percentile is the largest sample or an interpolation between the top two, so "p99 ≤ 120 seconds" is either "no single run exceeds 120 s" or method-dependent, and §11 delegates the percentile method to a downstream measurement contract. The gate's meaning depends on a choice the PRD does not make. *Fix:* Either keep p95 only in the `RQ-1` gate with n ≥ 30 and make p99 a launch-health observation, or raise the p99 minimum to a size that supports it (≥ 300) — and name the percentile method (nearest-rank or linear interpolation) in NFR-9. Apply the same edit to FR-28 and OQ-5 so the three stay in step.
- **medium** An external removal detected at the pre-post check has two different outcomes (§ FR-2 consequences 4 and 9, lines 148 and 153; FR-18 consequence 2, line 392; FR-18 pre-post consequence, line 397; FR-28 kill-switch consequence, line 622) — **new; introduced by the FR-2 repair.** FR-2 line 153: a removal performed directly in Conversations "is observed at the next membership step — at acceptance or before posting — and that step sets the block itself and fails the call or post closed with `RemovedInConversations`", and line 148 says the detecting step "abandon[s] non-terminal proposals for that Conversation". FR-18 line 392 lists `RemovedInConversations` as a system-abandonment reason. But FR-18 line 397 says a pre-post failure — including "`hexa` is still a member of and not blocked" — "moves the proposal to `PostingFailed` rather than posting stale content", and line 150 says `MembershipUnavailable`/`MembershipRejected` are the posting-failure reasons for that re-validation. So the proposal being posted when removal is detected ends either `Abandoned(RemovedInConversations)` or `PostingFailed(MembershipRejected)`, and the two states have different exits, different SM-3 treatment (`Abandoned` leaves the denominator; `PostingFailed` counts as decided), and different kill-switch handling (line 622 lets `Approved`/`PostingPending` "complete or fail on their own terms", which abandonment overrides). *Fix:* State in FR-18's pre-post consequence: "except that a detected removal or Agents-owned block moves the proposal to `Abandoned` with reason `RemovedInConversations` under FR-2, not to `PostingFailed`", and scope `MembershipUnavailable`/`MembershipRejected` in FR-2 line 150 to transient or authorization failures that are not a removal.
- **low** Residual adjective-only phrasing (§ FR-1 consequence 3, line 137 "prior value where safe to expose"; FR-4 consequence 2, line 178 "A documented migration state may allow temporary read-only inspection"; FR-20 consequence 3, line 456 "at a level sufficient to explain"; FR-22 consequence 3, line 486 "clearly distinguishes"; FR-25 consequence 3, line 545 "support launch monitoring of adoption and approval workflow metrics") — unchanged since the gate; each is bounded elsewhere or low-stakes. *Fix:* FR-1: "excluding secret references (NFR-6)". FR-4: name the migration state or delete the sentence. FR-25: "exposes the SM-2, SM-3, SM-7, SM-C4, and SM-C5 inputs defined in §12."
