## New contradictions introduced

Checked pairwise: FR-18 table vs FR-2/FR-7/FR-28 prose; FR-33 rows vs FR-1/FR-24/FR-30; FR-21/§8 vs FR-28/FR-34; glossary vs FR-33; SM-C4 vs FR-28 trigger. Findings, most important first.

- **N-1 (FR-18 prose vs FR-18 table vs FR-7 scope) — a `PostingFailed` system exit the table does not allow.** FR-18 line 423 lists as an exit from `PostingFailed`: "or the system abandons it under FR-7 on an authoritative answer that the Source Conversation is gone". But (a) the FR-7 re-check (line 246) "runs over every awaiting proposal", and awaiting is defined (line 397) as `Pending`, `Edited`, `Regenerated` — `PostingFailed` is not awaiting; (b) the table row `PostingFailed` → `Abandoned` (line 415) names only "Eligible Approver; Tenant Agent Administrator (FR-33)" as actors, and the only System row into `Abandoned` from `PostingFailed` is the `RemovedInConversations` row (line 414); (c) line 402 says "any other (from, to) pair is rejected". So no rule yields a System `Abandoned(SourceConversationUnavailable)` from `PostingFailed`, and the prose exit is unreachable — the same "always has an exit" gap C-3 was meant to close, for the gone-Conversation case. Fix: either extend the FR-7 re-check scope to `PostingFailed` and add "System (FR-7, authoritative answer only)" to the line-415 actor list, or drop that clause from line 423.

- **N-2 (FR-28 / OQ-27 kill-switch effect vs FR-18 pre-post guard) — `Approved` proposals cannot "complete on their own terms" while suspended.** FR-28 line 673 and OQ-27 say pulling the switch "lets `Approved` and `PostingPending` proposals complete or fail on their own terms". FR-18 line 426 makes pre-post re-validation check "its tenant not `Suspended`", and the table row `Approved` → `PostingPending` (line 412) is guarded on "Pre-post re-validation passed". Under those rules every `Approved` proposal in a suspended tenant fails re-validation into `PostingFailed` (a "reason that is not a removal or block"), where FR-18 line 425 then pauses the retry clock — so the switch does not let them complete; it converts them to `PostingFailed` and freezes them. Either the pre-post guard should drop the `Suspended` test (letting in-flight posts land, as FR-28 intends) or FR-28/OQ-27 should say "are moved to `PostingFailed` and held" instead of "complete on their own terms". FR-3 line 170 is consistent with FR-18, so it is FR-28/OQ-27 that is out of step.

- **N-3 (FR-2 clear authority vs system-set block) — who clears an `ExternallyRemoved` block is undefined.** FR-2 line 153 and 161 have the membership step itself "set the Agents-owned block" when it detects an external removal; line 160 and FR-33 line 448 permit clearing "only by the authority that set it or by the Tenant Agent Administrator". For a system-detected removal "the authority that set it" is nobody, so only the Tenant Agent Administrator can clear it — meaning a Conversation Facilitator who removed `hexa` directly in Conversations cannot re-admit it through Agents even though the same Facilitator could have blocked and cleared it through Agents. Not a contradiction in the strict sense, but a new decidability gap created by the C-2 repair; the FR-33 row should say who clears an `ExternallyRemoved` record (recommend: Tenant Agent Administrator or the current Conversation Facilitator).

- **N-4 (§8 `Available` definition vs FR-21 seam-execution ban) — bootstrap circularity now inside the PRD.** §8 line 787 defines `Available` as "its executable compatibility command passes with live Level 4 evidence"; FR-21 line 506 says "No runtime, test, or qualification path may execute a consumed external seam until its register entry is `Available` ... a path that would execute a seam whose entry is not `Available` fails closed with the typed outcome `DependencyNotAvailable`". The compatibility command is a test path that executes the seam, so as written nothing can ever become `Available`. The register may carve out the compatibility command; the PRD now restates the rule without the carve-out. One clause in FR-21 ("the compatibility command itself is the one execution permitted against a `Committed` entry") would close it.

- **N-5 (§3 "Release Operator" vs FR-33 release row) — release is not a trigger-review decision.** The glossary line 114 says the Release Operator "pulls or releases the kill switch as the recorded decision of a trigger review"; FR-33 line 454 and FR-28 line 673 say release needs "audited justification" from the Platform Operator or Release Operator, with no trigger review. Wording drift only; the FR-33 row governs.

- **N-6 (FR-1/FR-33 provisioning vs FR-2 "provision") — two roles "provision" identity.** FR-1 line 132 and FR-33 line 443 have the Platform Operator "provision `hexa` ... establishing Agent identity"; FR-2 line 143 still says "Agent Administrators can provision or link the Agent's Party identity", and FR-33 line 444 gives "identity" to the Tenant Agent Administrator's configure row. Whether the Party identity is created at Platform provisioning or later by the Tenant Agent Administrator is not decidable from the text. Pre-existing FR-2 sentence, made ambiguous by the CONS-4 fix.

- **N-7 (FR-27 vs amended OQ-18) — FR-27 still states the broader "no exclusion path" rule.** OQ-18 (line 948) now says "no Agents-side redaction or exclusion path; where Conversations permits it, a Participant may edit or delete the offending message there"; FR-27 line 644 still says "V1 provides no redaction or exclusion path for individual historical messages (OQ-18)" without the "Agents-side" qualifier. A one-word fix to FR-27.

- **N-8 (FR-33 preamble vs matrix) — "one row" is now inexact.** The CONS-10 fix changed the preamble (line 437) to "one row uses [the Facilitator] as an authority", but the matrix now has two rows naming the Conversation Facilitator (block, line 447; clear, line 448). Trivial; say "two rows" or "the block and clear rows".
