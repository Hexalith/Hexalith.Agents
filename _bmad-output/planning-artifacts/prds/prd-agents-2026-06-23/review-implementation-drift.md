# Implementation Drift Review — Hexalith Agents PRD

Reviewed: `prd.md` (frontmatter `updated: 2026-09-08`, 834 lines, revised 2026-09-09 to name shipped contract values) against `src/` and `test/` at HEAD of `main` on 2026-09-09. Submodules under `references/` were not descended into. The previous review (`review-implementation-drift-2026-09-08-validate.md`) is the baseline; claims it verified and that the PRD did not touch are not re-litigated here except where the revision changed the PRD's position.

Classification key: IMPLEMENTED-AS-SPECIFIED · IMPLEMENTED-DIFFERENTLY · NOT-YET-IMPLEMENTED · CONTRADICTED · PRD-NAMES-NONEXISTENT-MEMBER · ADDITIVE-REQUIRED (the PRD names a member that does not exist and FR-23 permits adding it).

## Verdict

The revision closes the two identifier-level contradictions the previous review rated critical/high: FR-18 now lists the ten shipped `ProposedAgentReplyState` values by their code names, and FR-7 / OQ-14 record `ApproverPolicySourceKind.ConversationOwner` as the frozen wire identifier behind the "Conversation facilitator" label, both of which the code matches exactly. Where the PRD names a member that does not yet exist — `ProhibitedCostControlPosture`, `AgentInteractionContextMode.Blocked`, `AgentGenerationOutcome.Indeterminate`, `NoEligibleApprover`, an FR-2 `Membership` gate check — it now says so and declares the value additive, so those are ADDITIVE-REQUIRED rather than contradictions. Two shipped behaviours still contradict text the PRD states as binding: readiness recording accepts `ReportingOnlyMonitoring` / `AcceptedLaunchRisk` (rejecting only `Unknown`), and configuration accepts `ContentSafetyFailureHandling.BlockWithAuditableOverride`, although both are on the FR-23 deprecate-and-reject register that says they are "rejected server-side with a typed rejection wherever presented". A third contradiction is inside the UI: `ProposalDetail.razor` treats `PostingFailed` (and `Posted`) as terminal and offers no retry, while the aggregate, the approval orchestrator, `ProposalQueue.razor` and now the PRD all treat `PostingFailed` as non-terminal with a retry available; the PRD sides with the domain, and the detail page plus its test are the outliers. Everything else the PRD asserts as a required change (context-budget terms, pre-Provider membership, segregation of duties, compliance inspection, the safety-verdict cache, the FR-33 role split, expiry defaults) is not yet wired, which the PRD now generally acknowledges; those are recorded as NOT-YET-IMPLEMENTED or IMPLEMENTED-DIFFERENTLY at Medium or Low. FR-30, FR-31 and FR-32 remain without code footprint, which is expected and is not counted as drift.

## Findings

### Critical

- **Readiness recording still accepts the two postures the PRD puts on the deprecate-and-reject register** — FR-28 (§4.10, line 592), FR-23 (line 475), NFR-10 (line 671), OQ-6 (line 818). The PRD: "both values ... are rejected at readiness recording with a typed rejection ... Rejecting only an absent posture does not satisfy this requirement." Code: `src/Hexalith.Agents/Agent/AgentAggregate.cs:1009-1012` rejects only `CostControlPosture.Unknown` ("A cost-control posture must be specified.") and stores any other value; `src/Hexalith.Agents/Agent/AgentLaunchReadinessPolicy.cs:73-76` adds `MissingCostControlPosture` only for `Unknown`, so `EnableProductionLikeGeneration` passes with `ReportingOnlyMonitoring` or `AcceptedLaunchRisk`. The enum (`src/Hexalith.Agents.Contracts/Agent/CostControlPosture.cs:23-36`) declares exactly the three hard values the PRD names — `Quotas`, `Budgets`, `ProviderModelLimits` — and the two prohibited ones, so the PRD's naming is accurate. **Classification:** CONTRADICTED (rejection rule); IMPLEMENTED-AS-SPECIFIED (value names). **Fix (code):** in `ValidateAndNormalizeLaunchReadiness` reject the two register values with a typed `AgentLaunchReadinessRejection` reason, and in `ComputeLaunchReadinessBlockers` emit the new blocker for a previously recorded prohibited posture (see the ADDITIVE-REQUIRED finding below).

### High

- **`ContentSafetyFailureHandling.BlockWithAuditableOverride` is accepted at configuration, not rejected** — FR-23 register (line 475), FR-27 (line 573). The PRD lists the value as deprecate-and-reject, "rejected server-side with a typed rejection wherever it is presented". Code: `src/Hexalith.Agents.Contracts/Agent/ContentSafetyFailureHandling.cs:25-26` declares it with an XML comment promising an Approver override path "(enforced in Story 3.5)"; `src/Hexalith.Agents/Agent/AgentAggregate.cs:852-855` (`ValidateAndNormalizePolicy`) rejects only `Unknown`, so a policy carrying the override value is stored and forwarded to the evaluator port (`src/Hexalith.Agents.Server/Ports/ContentSafetyEvaluationRequest.cs:27`). No override is executed today (the deferred evaluator blocks everything: `src/Hexalith.Agents.Server/Ports/DeferredContentSafetyEvaluator.cs:20`), but the configuration surface accepts a value the PRD says must be refused. **Classification:** CONTRADICTED. **Fix (code):** reject `BlockWithAuditableOverride` in `ValidateAndNormalizePolicy` with a typed `InvalidAgentConfigurationRejection` reason and mark the member `[Obsolete]` with a comment pointing at FR-23; rewrite its XML summary so it no longer advertises an override path.

- **`ProposalDetail.razor` treats `PostingFailed` as terminal and offers no retry; the PRD (and the domain) say it is non-terminal with a bounded retry** — FR-18 (lines 365, 369, 373), §6.1 (line 641), SM-3 (line 793). The PRD's terminal set is `Posted`, `Rejected`, `Abandoned`, `Expired`; `PostingFailed` is "posting failed; bounded retry available" and "every surface uses this one terminal set". Domain: `src/Hexalith.Agents/AgentInteraction/AgentInteractionAggregate.cs:504-509` lets `ApproveProposedAgentReply` proceed from `Approved`, `PostingPending`, `PostingFailed`; `src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionProposalApprovalOrchestrator.cs:103-109` (`IsApprovableOrRetryable`) does the same; `src/Hexalith.Agents/AgentInteraction/AgentProposalApprovalPolicy.cs:29-32` re-emits `Approved` then `PostingFailed` on a retried failure. UI: `src/Hexalith.Agents.UI/Components/Pages/ProposalDetail.razor:249-251` puts `Posted` **and** `PostingFailed` in `_terminalStates`; `:245-246` and `:293` limit `CanActOn` to `Pending`/`Edited`/`Regenerated`, so a `PostingFailed` proposal shows "start a new Agent Call" and no retry; `test/Hexalith.Agents.UI.Tests/ProposalDetailTests.cs:126-131` locks that in. `src/Hexalith.Agents.UI/Components/Pages/ProposalQueue.razor:302-305` uses a third set (`Rejected`, `Abandoned`, `Expired` only). The PRD sides with the aggregate/orchestrator; the queue's omission of `Posted` is harmless for its "start a new call" affordance but is still not "this one terminal set". **Classification:** CONTRADICTED (detail page); IMPLEMENTED-DIFFERENTLY (queue). **Fix (code):** remove `PostingFailed` from `_terminalStates`, add it to the act-on set with a retry (re-approve) affordance and the FR-18 retry-budget message, update the test theory, and align `ProposalQueue.IsTerminal` to the four-state set.
