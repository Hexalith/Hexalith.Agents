# Implementation Drift Review — Hexalith Agents PRD

Reviewed: `prd.md` (updated 2026-09-08, 762 lines) against `src/` and `test/` at HEAD of `main` on 2026-09-08. Submodules under `references/` were not descended into. Classification key: IMPLEMENTED-AS-SPECIFIED, IMPLEMENTED-DIFFERENTLY, NOT-YET-IMPLEMENTED (only a finding when the PRD phrases it as current behaviour), CONTRADICTED.

## Verdict

The PRD's structural spine matches the code well: the FR-29 acceptance stages (`Submitted` / `AuthoritativePending` / `ProjectionConfirmed`) exist verbatim as `AgentSetupTruthState`, the `CapabilityVersion` optimistic-concurrency rule is implemented exactly as written, the FR-5 selection-eligibility set maps one-to-one onto `ProviderSelectionValidationStatus`, and the context policy fails closed on oversize with no silent truncation. The drift is concentrated in three places that will mislead an implementer or QA reader. First, the PRD names public contract values that the code does not use and that FR-23 forbids renaming: the proposal state machine (`PostFailed` vs the code's `PostingFailed`, plus three extra states `Edited`, `Regenerated`, `PostingPending`), and the Approver Policy source `ConversationOwner`, which the PRD says no contract field may imply. Second, two behaviours the PRD asserts as binding are contradicted by the code today: reporting-only / accepted-risk cost postures are accepted at readiness recording and pass the production-like gate, and a reused pricing version is accepted rather than rejected. Third, several "today" statements describe behaviour that is not yet wired — the 24-hour default expiry (code fails open to unbounded), approval-time and pre-post safety re-checks (absent), and join-at-first-call membership (code checks membership at posting, after Provider work). FR-29 is implemented as specified; FR-30, FR-31 and FR-32 (added today) have no code footprint, which is expected for a PRD and is not counted as drift.

## Findings

- **[critical]** Proposal state names and count do not match the public `ProposedAgentReplyState` enum (§4.6 FR-18, §12 SM-3; `src/Hexalith.Agents.Contracts/AgentInteraction/ProposedAgentReplyState.cs`, `src/Hexalith.Agents.UI/Components/Shared/ProposedAgentReplyStatePresentation.cs`) — The PRD says a proposal "occupies exactly one of these states: `Pending`, `Approved`, `Posted`, `PostFailed`, `Rejected`, `Abandoned`, `Expired`". The shipped, JSON-serialized-by-name public enum has ten non-sentinel values: `Pending`, `Edited`, `Regenerated`, `Approved`, `PostingPending`, `Posted`, `PostingFailed`, `Rejected`, `Abandoned`, `Expired`. `PostFailed` does not exist anywhere in `src/` or `test/`; `Edited` and `Regenerated` are first-class states set by `AgentInteractionState.Apply(ProposedAgentReplyEdited/Regenerated)`, and `PostingPending` is emitted between `Approved` and `Posted` by `AgentProposalApprovalPolicy`. FR-23 forbids renaming or removing public enum values within V1, so the PRD cannot be satisfied by renaming the code. SM-3's terminal/in-flight partition also omits the three extra states. *Fix (PRD):* adopt the code's names — `PostingFailed` for `PostFailed`; list `Edited`, `Regenerated` and `PostingPending` as non-terminal states (or explicitly as sub-states of "awaiting decision"); and extend SM-3's in-flight set to `Approved`, `PostingPending`, `PostingFailed`. If product insists on seven states, FR-23's deprecate-and-reject path must be named explicitly.

- **[critical]** Reporting-only and accepted-risk cost postures are accepted at readiness recording and pass the production-like gate (§4.10 FR-28, §7 NFR-10, §13 OQ-6; `src/Hexalith.Agents.Contracts/Agent/CostControlPosture.cs`, `src/Hexalith.Agents/Agent/AgentAggregate.cs` `Handle(RecordAgentLaunchReadiness)` and `ValidateAndNormalizeLaunchReadiness`, `src/Hexalith.Agents/Agent/AgentLaunchReadinessPolicy.cs`) — The PRD (amended today) says "A recorded cost-control posture of reporting-only monitoring or explicitly accepted launch risk, like an absent posture, ... is a rejected input at readiness recording. Only hard enforcement postures satisfy the gate." The public enum declares `ReportingOnlyMonitoring` and `AcceptedLaunchRisk`; the aggregate rejects only `CostControlPosture.Unknown` ("A cost-control posture must be specified."); `ComputeLaunchReadinessBlockers` adds `MissingCostControlPosture` only for `Unknown`, so `EnableProductionLikeGeneration` succeeds with either forbidden posture. The code's "hard" postures are `Quotas`, `Budgets`, `ProviderModelLimits`, which the PRD never names. *Fix (code, with a PRD note):* the code is the one in the wrong under the amended decision; per FR-23 the two values must remain declared but be rejected server-side with a typed rejection, and the readiness blocker list needs a value for a prohibited posture. The PRD should state this is a deprecate-and-reject case and name which enum values count as "hard enforcement".

- **[high]** The public Approver Policy source is `ConversationOwner`; the PRD forbids any contract field implying an owner (§3 Glossary "Conversation Facilitator", §4.3 FR-7, §9, §13 OQ-14; `src/Hexalith.Agents.Contracts/Agent/ApproverPolicySourceKind.cs`, `src/Hexalith.Agents.UI/Resources/AgentsResources.resx` line 267) — FR-7 says "No admin UI text, API/client contract field, or Audit Evidence record may state or imply that a distinct Conversation owner was resolved". The wire value is literally `ConversationOwner` (serialized by name), documented in XML as "resolved by the V1 facilitator-based resolver". The UI relabels it "Conversation facilitator", so UI and API disclose different names for the same basis — itself a FR-7 parity breach ("API/client contracts and admin UI use the same disclosure category for the same approval-policy basis"). `ParticipantRole.Facilitator` is not referenced anywhere in `src/`; the resolver is `DeferredApproverPolicyResolver` (fails closed). *Fix (PRD):* record that the stable wire identifier for the Facilitator source is `ApproverPolicySourceKind.ConversationOwner` (legacy name, cannot be renamed under FR-23), scope the "may not imply an owner" rule to human-readable text and evidence narrative, or require adding `ConversationFacilitator` and deprecating `ConversationOwner` per FR-23.

- **[high]** Membership is verified at posting time, after Provider work, not established at first accepted call (§4.1 FR-2, §13 OQ-16; `src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionPostingOrchestrator.cs` `EnsureMembershipAsync`, `.../AgentInteractionProposalApprovalOrchestrator.cs`, `src/Hexalith.Agents.Server/Ports/ConversationClientResponsePoster.cs`, `src/Hexalith.Agents.Contracts/AgentInteraction/AgentResponsePostingFailureReason.cs`) — FR-2 says the Agent joins "at first accepted Agent Call in that Conversation, before generation" and "Membership failure fails the Agent Call closed and creates neither Provider work, a Proposed Agent Reply, nor a Conversation Message". The code has no membership step in the request or gate orchestrators; `EnsureMembershipAsync` runs only inside the posting and approval orchestrators, after generation (and after a proposal exists), and an absent membership resolves to `SeamUnavailable` → `MembershipUnavailable` / `MembershipRejected`, which are *posting* failure reasons. There is no "platform Agents service principal"; membership reads use `ActorUserId` (the authenticated caller). This is partially explained by EXT-CONV-AI-1 being `Uncommitted`, but the PRD describes the join as a call-acceptance step, so today's code spends Provider budget on calls that then fail at posting. *Fix (PRD):* state that until EXT-CONV-AI-1 lands, membership is verified (not established) at posting, and that the gate must gain a `Membership` check moving the failure before generation; keep `MembershipUnavailable`/`MembershipRejected` as posting reasons for the pre-post re-validation only.

- **[high]** Safe Context Budget omits Agent Instructions and the safety margin; blocked calls record `Mode = Unknown`, not `Blocked` (§3 Glossary "Safe Context Budget", §4.4 FR-9, §4.9 FR-24; `src/Hexalith.Agents/AgentInteraction/AgentInteractionContextPolicy.cs`, `src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionContextOrchestrator.cs` `ModelBudget`, `src/Hexalith.Agents.Contracts/AgentInteraction/AgentInteractionContextMode.cs`) — The PRD defines the budget as input limit minus reserved output, minus Agent Instructions, minus a fixed configured safety margin. The code computes `availableContextBudget = ContextWindowTokenLimit - ReservedOutputTokenCount` where `ReservedOutputTokenCount` is the catalog `MaxOutputTokenLimit`; no instruction token count and no margin exist in `AgentInteractionContextMeasurement` or `AgentInteractionContextEvidence`. The PRD also says calls record "the resulting context mode — full Source Conversation, an Approved Bounded Context Behavior, or blocked"; the enum is `Unknown | Full | Bounded` and a blocked call records `Unknown` plus an `AgentInteractionContextBlockReason`. Tokenizer measurement is deferred (`DeferredConversationContextTokenMeasurer`). *Fix (PRD):* either mark the instructions/margin subtraction as a required change to the context policy (and name the evidence fields to add), or align the definition to the shipped formula; describe the blocked case as "mode `Unknown` with a recorded block reason".

- **[high]** `Unknown` as a typed terminal Provider outcome collides with the FR-23 sentinel convention, and per-model `MaxRetries` conflicts with at-most-once (§4.5 FR-12, §4.10 FR-28, §7 NFR-11; `src/Hexalith.Agents.Contracts/AgentInteraction/AgentOutputGenerationResult.cs` `AgentGenerationOutcome`, `src/Hexalith.Agents.Contracts/ProviderCatalog/ProviderModelTimeoutPolicy.cs`, `src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionGenerationOrchestrator.cs`) — FR-12/NFR-11 say an attempt whose outcome cannot be determined "resolves to a typed `Unknown` terminal outcome". In every public enum `Unknown = 0` is the "not set" sentinel mandated by FR-23, and the generation orchestrator never emits it: a thrown adapter becomes `AdapterFailure`, a content-less success becomes `GenerationError`. There is no indeterminate outcome. Separately, `ProviderModelTimeoutPolicy.MaxRetries` (0–10, UI default 3) is validated by the catalog and handed to the provider adapter as a retry budget, which is the "silent retry" the PRD prohibits unless a confirmed no-usage outcome is proven. *Fix (PRD):* name a distinct value (e.g. `OutcomeIndeterminate`) instead of overloading `Unknown`, and either drop `MaxRetries` from the FR-4 capability-limit list or constrain it to confirmed-no-usage retries under the same reservation.

- **[medium]** Pricing version is server-assigned and a reused version is accepted, not rejected (§4.2 FR-4; `src/Hexalith.Agents/ProviderCatalog/ProviderCatalogAggregate.cs` `ValidatePricing`, `AssignPricing`) — The PRD says "a pricing version that starts at 1 on create and strictly increases. ... a decreased or reused pricing version is a typed rejection". The aggregate accepts `0` or `1` on create, rejects only `PricingVersion < current` on update (equal is accepted), treats `0` as "server-assign", ignores any caller-supplied higher value, and bumps the version only when currency or unit prices change (`unitsChanged`). Unchanged pricing with the same version is an idempotent no-op. *Fix (PRD):* describe the pricing version as server-assigned, monotonic per unit-price change, with a caller-supplied value below the stored value rejected and `0`/omitted meaning "server-assign".

- **[medium]** Expiry defaults to none (unbounded), not 24 hours, and approved-but-unposted proposals never expire (§4.6 FR-18, §13 OQ-3; `src/Hexalith.Agents.Server/Ports/DeferredProposalExpiryPolicyReader.cs`, `.../AgentInteractionProposalExpiryOrchestrator.cs` steps (c) and `IsExpirable`, `src/Hexalith.Agents/AgentInteraction/AgentInteractionAggregate.cs`) — The PRD states "The default expiry duration is 24 hours" and that a proposal past `ExpiresAt` "is treated as `Expired` on every read and every command". The code has no expiry configuration on the Agent aggregate, the expiry reader returns `None`, proposals are created with `ExpiresAt = null`, and the orchestrator resolves that to `NoExpiryPolicy` → no transition ("fail closed to no-expiry", which is fail-open for the proposal). The aggregate never inspects `ExpiresAt` on approve/edit/regenerate; only the explicit `ExpireProposedAgentReply` command with a server-supplied timestamp transitions. `IsExpirable` excludes `Approved`, `PostingPending`, `PostingFailed`, so those non-terminal states cannot expire, contrary to "`ExpiresAt` passed while non-terminal". *Fix (PRD):* mark the 24-hour default and expired-on-read as unimplemented requirements (not current behaviour) and decide explicitly whether `Approved`/`PostingPending`/`PostingFailed` may expire.

- **[medium]** Approval posts without re-running Content Safety on the approved version, and without segregation-of-duties or access re-check (§4.6 FR-17, §4.10 FR-27, §4.3 FR-7; `.../AgentInteractionProposalApprovalOrchestrator.cs` `ApproveAndPostAsync`) — The approval path checks proposal state, resolves the Approver Policy, reads the version, party and membership, then appends. `EvaluateSafetyAsync` is called only in the generation and regeneration orchestrators on generated output; there is no pre-Provider scan of prompt/context and no approval-time or pre-post scan, so a human-edited version (`AgentGenerationKind.Edited`) is posted unscanned today — exactly what FR-27 says "no edit path" may do. The approver is not compared to `AgentGeneratedVersion.EditorPartyId`, and the caller-not-sole-approver rule is not validated in `ValidateAndNormalizeApproverPolicy`. These are requirements, so not drift per se, but FR-26 refers to them as "the third and fourth of the four application points in OQ-9" as if the points were an established mechanism. *Fix (PRD):* phrase the four application points as required additions and cite the seam (`IContentSafetyEvaluator` in the approval orchestrator); no wording change needed for segregation of duties beyond noting `EditorPartyId` is already recorded.

- **[medium]** Disclosure category is per policy, not per source, and `Unknown` is rejected rather than defaulting to operator-only (§4.3 FR-7; `src/Hexalith.Agents.Contracts/Agent/AgentApproverPolicy.cs`, `ApproverPolicySource.cs`, `AgentAggregate.cs` `ValidateAndNormalizeApproverPolicy`) — FR-7 says "Every configured Approver Policy source declares its disclosure category at configuration time. Absent an explicit choice, the category is operator-only". The contract is `AgentApproverPolicy(Sources, DisclosureCategory)` with one category for the whole policy; `ApproverPolicySource(Kind, PartyId, TenantRole)` carries none; and an unspecified category is a typed rejection ("Approver policy disclosure category must be specified."), not a default. *Fix (PRD):* say the category is declared once per Approver Policy and is required (fail closed), or mark per-source categories and the operator-only default as a contract change (additive field, per FR-23).

- **[medium]** The only working invocation surface is an Agents-owned, administrator-gated page (§4.4, §13 OQ-1; `src/Hexalith.Agents.UI/Components/Pages/ConversationCall.razor`) — OQ-1 says the sole V1 entry is a Conversation-owned **Call hexa** action and "No ... alternate entry point is in V1"; FR-8 says Conversation Participants call it. The module ships `/agents/conversation-call` under `AgentsAdministratorPolicy`, whose own comment says the Conversation-owned wiring "is deferred to PRD OQ-1". The Conversations contribution contract (EXT-CONV-UI-1) is `Uncommitted`. *Fix (PRD):* acknowledge the transitional in-module page and require it to be removed or demoted to a qualification-only surface before production enablement, so OQ-1's "sole entry" claim is testable.

- **[medium]** `ContentSafetyFailureHandling.BlockWithAuditableOverride` is a declared public value for a behaviour the PRD forbids (§4.10 FR-27 "Approvers cannot override a Content Safety Policy failure"; `src/Hexalith.Agents.Contracts/Agent/ContentSafetyFailureHandling.cs`) — The value is declared and accepted by `ValidateAndNormalizeContentSafety`; nothing consumes it, so no override exists yet, but an integrator reading the contract will assume one is planned. *Fix (PRD):* list it as a deprecate-and-reject candidate under FR-23 (or clarify that "override" here means the FR-32 administrative cost-cap override path and rename nothing).

- **[medium]** "Agent Call" and "Global Providers Aggregate" are PRD-only names; the code's established names are `AgentInteraction` and `ProviderCatalog` (§3 Glossary; `src/Hexalith.Agents/AgentInteraction/AgentInteractionAggregate.cs`, `src/Hexalith.Agents/ProviderCatalog/ProviderCatalogAggregate.cs` `[EventStoreDomain("provider-catalog")]`, API routes `/interactions/{agentInteractionId}/...`) — Every aggregate, command (`RequestAgentInteraction`), event (`InteractionRequested`), route and status enum (`AgentInteractionStatus`) uses "interaction"; "call" survives only in `AgentCallRequestResult`, `AgentCallOperationStatus` and UI copy. Likewise there is no "Global Providers Aggregate" type; UJ-1 even says "global providers catalog". *Fix (PRD):* add glossary aliases — "Agent Call (code: `AgentInteraction`)" and "Global Providers Aggregate (code: `ProviderCatalogAggregate`, domain `provider-catalog`)".

- **[low]** FR-23 sentinel rule is violated by two public enums (§4.8 FR-23; `src/Hexalith.Agents.Contracts/Agent/AgentSetupWriteResult.cs` `AgentSetupWriteStatus.Submitted = 0`, `src/Hexalith.Agents.Contracts/ProviderCatalog/ProviderModelCapabilityFlags.cs` `None = 0`) — "Public enums define `Unknown = 0`". `AgentSetupWriteStatus` (shared by `ProviderCatalogWriteResult`) makes `Submitted` the zero value, so a default-initialized result reads as accepted. The `[Flags]` enum's `None = 0` is conventional and defensible. *Fix (PRD):* carve out `[Flags]` enums explicitly; flag `AgentSetupWriteStatus` for the code owners.

- **[low]** "Secret reference" is `ConfigurationReferenceId` in the contract (§4.2 FR-4, §13 OQ-7; `src/Hexalith.Agents.Contracts/ProviderCatalog/ProviderCatalogEntryView.cs`, `ProviderConfigurationState.cs`) — The PRD says each model "records its secret reference and whether the Provider is configured". The code models an opaque `ConfigurationReferenceId` (regex-validated, ≤128 chars) and `ProviderConfigurationState { NotConfigured, Configured }`; the word "secret" is deliberately absent from the contract surface (NFR-6 non-disclosure trait). *Fix (PRD):* say "configuration (secret) reference, `ConfigurationReferenceId`".

- **[low]** Lifecycle has a `Draft` state the PRD never names (§4.1 FR-3, §4.8 FR-22; `src/Hexalith.Agents.Contracts/Agent/AgentLifecycleStatus.cs`) — Code: `Draft | Active | Disabled`. FR-22 asks the UI to distinguish "active, disabled, invalid"; `Draft` is the created-but-never-activated state and `InvalidConfiguration` is a readiness status, not a lifecycle state. *Fix (PRD):* add `Draft` to FR-3 and clarify "invalid" is a readiness classification (`AgentReadinessStatus.InvalidConfiguration`).

- **[low]** Status surface cannot yet distinguish content-safety or cost-cap blocks per FR-25 (§4.9 FR-25; `src/Hexalith.Agents.Contracts/Operations/AgentCallOperationStatus.cs`) — The public call status has `ContextBlocked`, `GenerationFailed`, `Generated` but no safety- or cost-specific value, and stops before posting; `SafetyFailed` exists only on the internal `AgentInteractionStatus`. NOT-YET for cost; for safety the PRD's "distinguish ... content safety failures" needs an additive enum value. *Fix (PRD):* none required; note the additive value is expected.
