## Findings

### Critical

1. **Launch-readiness register still gates `RQ-1` on SM-1 through SM-6 real attainment, which the PRD moved out of the gate.** (cross-artifact)
   - `launch-readiness-register.md` line 79: "`LR-PRODUCT-METRICS` | Versioned SM-1 through SM-6 calculation and real rolling-window/cohort attainment"; line 239: "`product-metrics` | SM-1 through SM-6 rolling-window/cohort calculations"; line 139: "The `ReleaseQualificationGateSet` contains all 18 minimum GateIds. Only current `Pass` records for the complete set ... allow `RQ-1` READY". SM-7 does not appear in the register at all.
   - `prd.md` FR-28 line 613: "Production enablement remains blocked until `RQ-1` records READY from ... SM-1, SM-4, SM-5, SM-6"; line 615: "SM-2, SM-3, and SM-7 are launch-health metrics. Only real usage can produce them, so they are not `RQ-1` inputs"; OQ-22 line 878 says the same; §12 lines 826–839 define SM-7.
   - Impact: the register is the machine-testable authority `RQ-1` evaluates (Spine AD-17 line 198: "`launch-readiness-register.md` is the normative readiness authority for ... measurement contracts"). As written it requires real SM-2/SM-3 attainment before enablement, which is exactly the deadlock OQ-19 resolved, and it has no measurement contract for SM-7. `epics.md` Story 8.5 (2583–2584) and the `RQ-1` gate text (2780) already follow the PRD split, so the register is the odd one out.
   - Fix (`launch-readiness-register.md`): change `LR-PRODUCT-METRICS` and `product-metrics` to "pre-enablement gate metrics SM-1, SM-4, SM-5, SM-6 (gate inputs) plus launch-health SM-2, SM-3, SM-7 and SM-C1..SM-C5 (calculated and reported, never gate inputs)", and add the SM-7 measurement contract.

### High

A reader of the status line alone undercounts the blockers by one. (`review-rubric.md` line 63 already flags this as medium; it is High here because §0 is the summary readers act on.)

4. **Who creates `hexa`: PRD FR-1/FR-33 say the Tenant Agent Administrator; Spine AD-2/AD-30 say the Platform principal at tenant enablement.** (cross-artifact)
   - `prd.md` FR-1 line 131: "Agent Administrators can create or enable `hexa`"; FR-33 row 414: "Configure `hexa`: identity, ... | Tenant Agent Administrator | Tenant"; FR-33 line 408: "Every authorization rule in this PRD resolves to one of six Agents roles"; OQ-21 (877): "FR-33 is the authoritative role matrix for every authorization rule".

   - Impact: an implementer following the Spine denies tenant administrators the create path FR-1 grants, and FR-33 has no row for a Platform-Operator provisioning step, so the matrix is not the complete authority it claims to be.
   - Fix: Product decides. If the Spine's model stands (it was approved after the PRD text), amend `prd.md` FR-1 to "enable and configure `hexa`, which the Platform Operator provisions at tenant enablement" and add an FR-33 row "Provision `hexa` at tenant enablement | Platform Operator | Tenant"; otherwise amend Spine AD-2/AD-30.

### Medium

5. **FR-18 lists "kill switch" as a typed system-abandonment reason; FR-28 and the Spine say the kill switch never system-abandons.** (internal; cross-artifact)
   - `prd.md` FR-18 line 392: "A proposal abandoned by the system carries its typed reason (`NoEligibleApprover`, `SourceConversationUnavailable`, `RemovedInConversations`, or kill switch)".
   - `prd.md` FR-28 line 622: pulling the kill switch "lets proposals awaiting a decision be rejected or abandoned but not approved, lets `Approved` and `PostingPending` proposals complete or fail on their own terms, and deletes no proposal" — no system abandonment. FR-7 (236) and FR-2 (153) define only the three named reasons. Spine AD-5 line 126: "System abandonment carries a typed reason (`NoEligibleApprover`, `SourceConversationUnavailable`, `RemovedInConversations`)"; AD-12 line 168: the kill switch "never system-abandons or deletes anything".
   - Fix (`prd.md` line 392): drop "or kill switch"; the FR-28 effect (human reject/abandon only) already governs.

6. **FR-28 names the wrong register as the readiness authority; the PRD never names the launch-readiness register.** (internal; cross-artifact)
   - `prd.md` FR-28 line 621: "The external dependency register's launch-readiness gate records are the readiness authority."
   - `external-dependency-register.md` holds no gate records; they live in `launch-readiness-register.md` (frontmatter `release_gate: RQ-1`; lines 17, 247–266), which Spine AD-17 line 198 calls "the normative readiness authority". The PRD's only other pointer is NFR-12 line 700 "visible in the readiness registry", and §0 line 14 says "build readiness is owned by the external dependency register and the `RQ-1` gate".
   - Fix (`prd.md` line 621): "The launch readiness register's gate records are the readiness authority; the external dependency register is the commitment authority for `EXT-*` entries."

7. **The launch-readiness register defines neither `UnretiredAssumption` nor `ProhibitedCostControlPosture`, which FR-28 requires `RQ-1` to record.** (cross-artifact)

   - `launch-readiness-register.md` blocker codes in use (lines 247–266) are only `EvidenceNotRecorded` and `DependencyUncommitted`; no gate, record, or blocker names assumptions or postures (grep for either code returns nothing; line 104 mentions one architecture assumption in prose only).
   - Fix (`launch-readiness-register.md`): add both codes to the blocker vocabulary and state which gate (or the `RQ-1` evaluation itself) emits them.

8. **PRD asserts a non-conformance record exists for any story completed against an `Uncommitted` entry; the register has none, though Story 5.3 qualifies.** (cross-artifact)

   - `external-dependency-register.md` contains no non-conformance record (no occurrence of "non-conform"). Story 5.3 shipped (`sprint-change-proposal-2026-09-09.md` line 47) while `EXT-PROVIDER-1` was `Uncommitted` and listed it as a consumer (proposal line 183, OLD text: "`EXT-PROVIDER-1` is a story dependency"); the register instead narrowed the consumer list (line 107: "Story 5.3 published catalog truth adapter-free and is not a consumer").
   - Fix (`external-dependency-register.md`): add a "Non-Conformance Records" section with the 5.3 / `EXT-PROVIDER-1` / completion-date row (reopening 5.3 does not clear it per FR-21), or, if Product rules 5.3 never consumed the seam, say so explicitly there so §8's assertion is verifiable.
