## Overall verdict

This is a rigorous, chain-top PRD: the thesis in §1 is specific, every FR carries testable consequences, the Decision Register names what was given up (OQ-10, OQ-17, OQ-18), and the glossary and ID scheme are clean enough for UX, architecture, and story extraction to source from directly. What is at risk is the `final` label rather than the content: the PRD's own register records that a primary success metric is unattainable under a permitted configuration and that the metric set does not validate the thesis (OQ-19), §8 records seven of eight critical external dependencies as `Uncommitted`, and the document carries zero `[ASSUMPTION]` tags while naming external contract members that do not yet exist. The PRD is decision-ready as a build specification and not yet decision-ready as a launch instrument; the fixes are concentrated in §12 and §13, not spread across the FRs.

The adversarial and implementation-drift reviewers materially sharpen the picture. The adversarial pass would not sign off: it finds that FR-7's segregation-of-duties, access-guarantee, and configuration-time-rejection rules, read together, leave Confirmation Response Mode (UJ-3, the governance thesis) with no valid configuration or with orphan proposals nobody may approve; that the `RQ-1` gate depends on adoption metrics (SM-2, and a circular SM-1) that can only exist after the enablement they gate; and that FR-24's "current read access" rule for audit content defeats the Compliance Operator job and orphans 365-day evidence once the Conversation is deleted. The drift pass confirms the FR-29 truth model, `CapabilityVersion` concurrency, and the fail-closed context policy are implemented as written, but shows the PRD naming public contract values the code does not use and FR-23 forbids renaming (`PostFailed` vs `PostingFailed` plus three extra proposal states; `ApproverPolicySourceKind.ConversationOwner`), and two binding rules the code contradicts today (reporting-only and accepted-risk cost postures pass the readiness gate; reused pricing versions are accepted). Together the three reviewers converge on the same verdict: the PRD is a strong build specification whose `final` label is not yet earned, with the blocking work concentrated in FR-7, FR-18, FR-24, §12, and §13.

## Findings by severity

### Critical (6)

**[Decision-readiness]** — Primary metric SM-3 is known-unattainable under permitted configuration and left in force (§ §12 SM-3; §13 OQ-3, OQ-19; FR-28)
OQ-3 permits expiry "from 1 hour through 30 days"; SM-3 requires "95% of Proposed Agent Replies ... reach a terminal state within 26 hours" and counts `Expired` as terminal, so the metric measures expiry configuration, not approval behavior, and cannot be met by a 30-day-expiry Agent unless 95% are decided by humans within 26 hours regardless. OQ-19 records both defects and defers them. A `final` PRD whose launch gate depends on a metric it declares broken cannot support a READY/NOT READY decision.
Fix: Either (a) re-express SM-3 in terms of human-decision latency (e.g. "95% of proposals receive an Approver decision — `Approved`, `Rejected`, or `Abandoned` — within N hours of creation, measured on proposals whose expiry is ≥ N hours") with expiry rate as a separate counter-metric, or (b) constrain OQ-3's range to ≤ 24 hours for launch tenants and re-open the range post-launch. Whichever is chosen, mark SM-3 as provisional in §12 until the OQ-19 escalation lands, so `RQ-1` is not evaluated against a metric the PRD disowns.

**[Adversarial review]** — Segregation-of-duties and access-guarantee rules make Confirmation Response Mode unconfigurable or produce orphan proposals (§ FR-7, UJ-3, OQ-14)
FR-7 says "The caller may not be the sole Approver of their own Agent Call, and the approving Party must differ from the Party that last edited the version being approved. A policy configuration that cannot satisfy this segregation of duties is rejected at configuration time." Whether the caller is the sole Approver is only knowable at *call* time (it depends on who calls). A Facilitator-only policy is fine for Milan's call and violated for the Facilitator's own call. Two literal readings, both wrong: (a) reject Facilitator-only at configuration time because a Facilitator *could* call — then UJ-3's default configuration is illegal and, because the same FR also rejects "a bare tenant role whose holders are not guaranteed Conversation access" (predefined Parties are equally not guaranteed access), no single-source policy survives validation; (b) accept it and at call time either reject the Facilitator's call with no stated reason code, or create a `Pending` proposal that no Party may approve, which sits until `Expired` and pollutes SM-3's expiry rate. The edit rule has the same hole: with a single Approver, the moment she edits, the proposal becomes unapprovable ("a second authorized Approver would have to approve") and nothing says edit must be refused when no second Approver exists.
Fix: Split the rule into a configuration-time check (policy must be able to yield ≥2 distinct Parties *or* must include a fallback source) and explicit call-time and edit-time behaviors: if the resolved Approver set for this proposal is {caller} → typed rejection of the call before Provider work; if an edit would leave zero eligible approvers → typed rejection of the edit. Define "bare tenant role" or delete the phrase; decide whether predefined Parties are permitted at all under the access-guarantee rule.

**[Adversarial review]** — Adoption metrics gate production enablement but can only be produced after it (§ FR-28, SM-1, SM-2, §11, §12)
FR-28: "Production enablement remains blocked until `RQ-1` records READY from the required live evidence and launch metrics" and "When a primary metric evaluates to `InsufficientEvidence`, `RQ-1` records NOT READY". SM-2 is a primary metric requiring "At least 20% of eligible Conversations ... record one or more accepted Agent Calls during a rolling 30-day window, measured only when the cohort contains at least 50 eligible Conversations." Before production enablement the only source is "production-like launch validation", where the population of Conversations and the callers are the test team. Either the qualification team scripts 50 conversations with 20% calls (metric is gamed and measures nothing) or a real single-tenant launch (SM-1 needs one tenant) with fewer than 50 eligible Conversations returns `InsufficientEvidence` → NOT READY indefinitely. SM-1 is also circular: it requires the tenant "satisfies launch-readiness gates", and readiness requires SM-1.
Fix: Move SM-2 and SM-3 out of the `RQ-1` gate into post-enablement launch-health review (they are outcome metrics, not readiness evidence); keep in the gate only what can be produced pre-enablement (latency, isolation, safety, audit completeness on the qualification cohort). Strip "satisfies launch-readiness gates" from SM-1.

**[Adversarial review]** — Audit content access rule defeats the Compliance Operator job and orphans evidence when the Conversation goes away (§ FR-24, §9, §2.1, FR-30)
FR-24: "Inspecting Audit Evidence that contains Conversation-derived content additionally requires current read access to that Source Conversation, and fails closed otherwise." §2.1 JTBD: "As a Tenant or Compliance Operator, prove who called the Agent, what it generated, what changed during approval, who approved it, and what was finally posted." A compliance operator is not a participant of every Conversation, so "what it generated" and "what changed" are unreadable unless the operator is injected into every Conversation, which is itself a governance violation. FR-30/§9 require an operator to "request authorized export" and apply legal hold to content the same rule forbids them to read. When Hexalith.Conversations deletes the Conversation under its own retention ("Posted Conversation Messages remain governed by Hexalith.Conversations retention"), "current read access" is impossible for everyone, so 365 days of retained Agent content becomes permanently uninspectable while still being retained.
Fix: Define a distinct compliance-inspection authorization (tenant-scoped role, audited, justification-required) that bypasses the participant check; define the behavior when the Source Conversation no longer exists (evidence remains inspectable under compliance authorization; participant-based access is simply unavailable).

**[Implementation drift review]** — Proposal state names and count do not match the public `ProposedAgentReplyState` enum (§ §4.6 FR-18, §12 SM-3; `src/Hexalith.Agents.Contracts/AgentInteraction/ProposedAgentReplyState.cs`, `src/Hexalith.Agents.UI/Components/Shared/ProposedAgentReplyStatePresentation.cs`)
The PRD says a proposal "occupies exactly one of these states: `Pending`, `Approved`, `Posted`, `PostFailed`, `Rejected`, `Abandoned`, `Expired`". The shipped, JSON-serialized-by-name public enum has ten non-sentinel values: `Pending`, `Edited`, `Regenerated`, `Approved`, `PostingPending`, `Posted`, `PostingFailed`, `Rejected`, `Abandoned`, `Expired`. `PostFailed` does not exist anywhere in `src/` or `test/`; `Edited` and `Regenerated` are first-class states set by `AgentInteractionState.Apply(ProposedAgentReplyEdited/Regenerated)`, and `PostingPending` is emitted between `Approved` and `Posted` by `AgentProposalApprovalPolicy`. FR-23 forbids renaming or removing public enum values within V1, so the PRD cannot be satisfied by renaming the code. SM-3's terminal/in-flight partition also omits the three extra states.
Fix: adopt the code's names — `PostingFailed` for `PostFailed`; list `Edited`, `Regenerated` and `PostingPending` as non-terminal states (or explicitly as sub-states of "awaiting decision"); and extend SM-3's in-flight set to `Approved`, `PostingPending`, `PostingFailed`. If product insists on seven states, FR-23's deprecate-and-reject path must be named explicitly.

**[Implementation drift review]** — Reporting-only and accepted-risk cost postures are accepted at readiness recording and pass the production-like gate (§ §4.10 FR-28, §7 NFR-10, §13 OQ-6; `src/Hexalith.Agents.Contracts/Agent/CostControlPosture.cs`, `src/Hexalith.Agents/Agent/AgentAggregate.cs` `Handle(RecordAgentLaunchReadiness)` and `ValidateAndNormalizeLaunchReadiness`, `src/Hexalith.Agents/Agent/AgentLaunchReadinessPolicy.cs`)

**[Adversarial review]** — Safe Context Budget formula omits the caller's prompt (§ glossary, FR-9)
"the selected model's input limit ... minus the reserved output allowance, the Agent Instructions, and a fixed configured safety margin." FR-8 says the call carries "a user prompt or request"; FR-27 says the prompt is scanned; nothing subtracts it from the budget. An engineer who implements exactly the stated formula — and the PRD insists it is recorded as evidence "for every call" — admits a Conversation that fits the budget and then overflows the model once the prompt and any framing tokens are appended, producing a Provider rejection *after* reservation and after the fail-closed point the PRD promised. The "fixed configured safety margin" has no default or range, so it cannot be relied upon to absorb this.
Fix: Add the caller prompt and any system framing to the subtraction; give the safety margin a default and range (e.g., 5% of input limit, 1–25%).

**[Adversarial review]** — Per-Conversation safety-verdict cache is unversioned and conflicts with "future calls use the new policy" (§ FR-27, FR-26, OQ-9, OQ-18)
FR-27: the pre-Provider scan reuses "a cached per-Conversation verdict for already-scanned history". FR-26: "Content Safety Policy changes are auditable and affect future Agent Calls only." A new call after a policy tightening is a future call and must use the new policy, but a cache keyed only on Conversation returns the old policy's verdict for the history. Nothing keys the cache on policy version, and nothing invalidates it when a Conversation message is edited or deleted in Hexalith.Conversations. Both are silent under-scanning, which is exactly what the safety section claims can never happen. OQ-18 also relies on this cache: "a single historical message that fails the active policy blocks generation in that Conversation permanently" — permanence depends on the cache never being re-evaluated, so a fix to OQ-18 and a fix to this finding pull in opposite directions unless the cache contract is written down.
Fix: Cache key = (Conversation, message content version, policy version); state that a policy publication invalidates cached verdicts tenant-wide; record the policy version the cached verdict came from in Audit Evidence.

**[Implementation drift review]** — `Unknown` as a typed terminal Provider outcome collides with the FR-23 sentinel convention, and per-model `MaxRetries` conflicts with at-most-once (§ §4.5 FR-12, §4.10 FR-28, §7 NFR-11; `src/Hexalith.Agents.Contracts/AgentInteraction/AgentOutputGenerationResult.cs` `AgentGenerationOutcome`, `src/Hexalith.Agents.Contracts/ProviderCatalog/ProviderModelTimeoutPolicy.cs`, `src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionGenerationOrchestrator.cs`)

### Medium (27)

**[Adversarial review]** — `CapabilityVersion` concurrency semantics are inverted relative to convention and "not regressed" has no referent (§ FR-4, FR-5)

## Reviewer verdicts

### Adversarial review

I would not sign off. The document is unusually precise about *what must never happen* (silent truncation, unapproved posting, secret leakage) and unusually vague about the things an implementer must actually decide on day one: who holds "Agent call permission", who owns cost caps, whether `hexa` is one Agent per tenant, what "accepted" means relative to membership and fail-closed checks, and how a proposal moves through its states when the Agent is disabled or the Conversation removes it. The single biggest way this PRD gets misbuilt is FR-7: read literally, its three simultaneous constraints — configuration-time rejection of any policy that "cannot satisfy" segregation of duties, rejection of any source "whose holders are not guaranteed Conversation access", and "the caller may not be the sole Approver" — make every realistic Approver Policy (Facilitator-only, a single named Party, a tenant role) either unconfigurable or capable of producing proposals no one is permitted to approve. A fully compliant implementation of §4.3 leaves Confirmation Response Mode, the product's central governance thesis (UJ-3), without a valid configuration. Close behind it: the release gate (FR-28 → `RQ-1`) is wired to adoption metrics that can only be produced after the enablement they gate.

Notes:

- `EXT-*` status: §8 says only `EXT-HOST-1` is `Committed`; every consuming story is blocked from `ready-for-dev` under FR-21/OQ-17. The PRD is therefore `final` for a product no story can currently start. That is a process fact, not a defect in the text, but it makes the many "production-like" evidence requirements untestable for the foreseeable future.
- Evidence Level 4 requires "an actual ... Provider ... process". Every Level 4 run costs real Provider money and counts against whatever cap the qualification tenant has; nothing exempts qualification from FR-32's "unconfigured cap blocks production-like generation", so qualification needs its own configured caps. Worth a sentence.
- NFR-9's 2 s pre-Provider rejection includes the context-budget check, which requires loading and tokenizing the entire Conversation. For Conversations near the budget on large models this is the slowest pre-Provider step; the gate is testable but may be unrealistic for the exact cases it matters most.
- NFR-11 "Provider attempts are at-most-once" is tautological per attempt; the intended invariant is "at most one Provider attempt with possible usage per Agent Call". FR-28 already states this correctly; NFR-11 should mirror it.
- `Approved` → `Expired` is possible when `ExpiresAt` passes between approval and post; SM-3 then counts a human-decided proposal as `Expired`. Small, but it argues for freezing `ExpiresAt` semantics at `Approved`.

### Implementation drift review

The PRD's structural spine matches the code well: the FR-29 acceptance stages (`Submitted` / `AuthoritativePending` / `ProjectionConfirmed`) exist verbatim as `AgentSetupTruthState`, the `CapabilityVersion` optimistic-concurrency rule is implemented exactly as written, the FR-5 selection-eligibility set maps one-to-one onto `ProviderSelectionValidationStatus`, and the context policy fails closed on oversize with no silent truncation. The drift is concentrated in three places that will mislead an implementer or QA reader. First, the PRD names public contract values that the code does not use and that FR-23 forbids renaming: the proposal state machine (`PostFailed` vs the code's `PostingFailed`, plus three extra states `Edited`, `Regenerated`, `PostingPending`), and the Approver Policy source `ConversationOwner`, which the PRD says no contract field may imply. Second, two behaviours the PRD asserts as binding are contradicted by the code today: reporting-only / accepted-risk cost postures are accepted at readiness recording and pass the production-like gate, and a reused pricing version is accepted rather than rejected. Third, several "today" statements describe behaviour that is not yet wired — the 24-hour default expiry (code fails open to unbounded), approval-time and pre-post safety re-checks (absent), and join-at-first-call membership (code checks membership at posting, after Provider work). FR-29 is implemented as specified; FR-30, FR-31 and FR-32 (added today) have no code footprint, which is expected for a PRD and is not counted as drift.
