# Spine Pair Review — Hexalith Agents

Reviewer: rubric walker. Run date: 2026-09-08. Inputs: `DESIGN.md` (2026-08-02), `EXPERIENCE.md` (2026-08-02), `.memlog.md`, all 16 `sources:` paths (all resolve), calibration examples and `design-md-spec.md`. `imports/` is empty; there is no `mockups/` or `wireframes/` folder; `.working/validation-2026-06-23/` is an archived prior run and was ignored.

## Overall verdict

The pair is a consumable contract: every `{path.to.token}` reference resolves, all 19 component names are identical across the DESIGN frontmatter, DESIGN `## Components`, and EXPERIENCE `## Component Patterns`, all four PRD journeys are carried verbatim with protagonist, numbered steps, climax, and failure path, and the Fluent-by-name color inheritance is a defensible application of the spec's UI-system rule (all eight `BadgeColor` names verified against Fluent UI Blazor v5). What keeps it from *strong* is one uncommitted load-bearing surface — the high-impact confirmation/pending-command surface used by six operation families has no named component and its rules sit under an unrelated heading — plus a cluster of medium gaps a story-dev would otherwise decide alone: no home for proposal-expiry configuration, no offline/concurrency treatment, no pinned Fluent package or per-role icon/appearance/contrast statement, and NFR-14 thresholds restated in six places. No critical findings.

## 2. Token completeness — adequate

Checked: every key in `DESIGN.md` frontmatter (8 colors, 5 typography roles, `rounded` note, 6 spacing steps, 19 components) against every `{...}` reference in both spines. `DESIGN.md` uses 19 distinct references (`colors.*` ×8, `spacing.1/2/3/4/6/8`, `typography.body/label/heading/caption/mono`); all resolve. `EXPERIENCE.md` uses no `{}` references; it names roles as `Success`/`Warning`/`Severe` etc., which map by name to `colors.status-*`. `rounded` is a platform note and is never referenced — fine.

**Inheritance judgment.** The eight `Inherit Fluent BadgeColor.X` notes are a defensible inheritance, not an unresolved gap: `design-md-spec.md` § UI-system inheritance says to "reference the system's tokens by name rather than restating values", the notes carry the semantic delta (what each role *means* for Agents), and every name (`Brand`, `Danger`, `Important`, `Informative`, `Severe`, `Subtle`, `Success`, `Warning`) exists in the Fluent UI Blazor v5 `BadgeColor` enum. Light/dark pairs are correctly left to Fluent. This matches the Tenants precedent that `DESIGN.md` names as its model. The absence of hex is therefore **not** a critical finding. The gaps are around what the inheritance leaves unanchored:

### Findings
- **medium** No pinned Fluent UI Blazor package version is stated. `DESIGN.md § Colors` (line 157) says the icon vocabulary "should be verified against the pinned Fluent UI package at build", but nothing in either spine says which pin (Tenants' DESIGN.md pins `5.0.0-rc.4-26180.1` inline). Without the pin, "inherit by name" has no fixed referent. *Fix:* one line in `DESIGN.md § Brand & Style` or a frontmatter comment: the package/version or the central-package-management file that owns it.
- **medium** No contrast target and no per-role badge appearance. `DESIGN.md § Colors` (line 157) mandates "role + icon + visible text" under WCAG 2.2 AA but never states 4.5:1 text / 3:1 non-text/focus, nor which `BadgeAppearance` (Tint vs Filled) each role uses — and Tint-on-surface vs Filled have different contrast outcomes. Tenants specified `Tint (default) · Filled (Danger + Severe)`. *Fix:* add an `appearance` line per badge component in frontmatter and one sentence under `§ Colors`: "AA 4.5:1 text, 3:1 non-text; inherited Fluent pairs are assumed AA at the pinned version and re-verified when the pin changes".
- **medium** The icon half of "role + icon + text" is unspecified: no icon is named for any of the seven status roles or for the readiness/provider/proposal badge states. Downstream will pick eight icons ad hoc across three badge components, breaking the "consistent meaning" goal stated in `DESIGN.md § Brand & Style`. *Fix:* a small role→icon table in `DESIGN.md § Colors` (Fluent icon names) or an explicit delegation ("icon set is owned by story X; roles must share one icon per role across all three badges").
- **low** Frontmatter `components.*.color` values are pipe-separated lists (`'{a} | {b} | {c}'`) and `base`/`layout` are free text. A flattening resolver will not resolve these; humans will. Same form as Tenants, so it is a known convention — note only (`DESIGN.md` lines 59, 63, 67).

## 4. State coverage — adequate

Checked: walked all 14 IA surfaces against empty, cold-load, focus, error, offline, permission-denied, stale-projection, and concurrency. Coverage is unusually rich for readiness, provider, call, proposal, launch-evidence, and audit-availability state machines; `§ List And Detail Surfaces` gives grids and detail views loading / empty / filtered-empty / error / permission-denied / stale generically; focus is delegated to FC-A11Y with a return-focus rule.

### Findings
- **medium** No offline / connection-lost / reconnecting state anywhere (grep: 0 hits for offline/reconnect/connection). The whole `submitted → authoritative pending → projection-confirmed terminal` contract depends on receiving projections; the only treatment is "a client timeout forces refresh" (`EXPERIENCE.md` line 185). Unstated: what the pending indicator shows while disconnected, whether **Call hexa** and the six high-impact actions are disabled, whether the advisory lock survives reconnect. *Fix:* one row in `§ State Patterns` (global): "connection lost → status region notice, pending items stay pending (never fail, never succeed), high-impact submit disabled with reason, lock re-evaluated from authoritative status on reconnect".
- **medium** No concurrent-edit / stale-detail treatment for `Proposal detail/editor`. Two approvers on one proposal is the normal Confirmation-mode case; `EXPERIENCE.md` line 185 says EventStore optimistic concurrency "remains authoritative" but not what the UI does when a command is rejected for version conflict or when the proposal reaches a terminal state under the viewer (Drift's example: "Updated by {user}. Refresh."). *Fix:* add a `stale proposal` row: preserve the viewer's unsaved edit text, show the authoritative state and who changed it, offer refresh; approve/reject disabled until refreshed.
- **low** `Conversation invocation`: when `hexa` is `active, not proven callable` or `disabled`, it is not stated whether **Call hexa** is hidden, shown-disabled with reason, or shown and rejected on submit. `§ Agent Readiness` says "block calls"; `§ Interaction Primitives` says "checks permission before Provider invocation" (`EXPERIENCE.md` lines 130–136, 220). *Fix:* one clause: visible-but-disabled with the safe blocker text (consistent with "no required denial reason is hover-only").
- **low** The prompt surface's own states (empty prompt, over-length prompt, submit-disabled) are unspecified. *Fix:* two words in `conversation-agent-call`: "prompt required; no client-side length limit (context budget is server-owned)".
