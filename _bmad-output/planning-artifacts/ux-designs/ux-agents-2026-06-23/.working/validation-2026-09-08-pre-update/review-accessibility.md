# Accessibility Review — Hexalith Agents

Reviewer lens: accessibility (WCAG 2.2 AA binding, whole-string EN/FR parity binding per `.memlog.md`). Inputs: `DESIGN.md`, `EXPERIENCE.md`, `.memlog.md`, FrontComposer `front-composer-shell.md`, `navigation.md`, `datagrid.md`, `page-toolbar.md`, `settings.md`, `_bmad-output/project-context.md`, `docs/accessibility-verification/README.md`, FrontComposer Shell source for `FcPageHeader`, `FcDestructiveConfirmationDialog`, and live-region components, PRD `prd.md` (FR-18, FR-22, NFR-13, NFR-14) and `addendum.md`.

## Overall verdict

The spines are strong on *semantics* (no-color-only, Success discipline, whole-string copy) and weak on *mechanics*: they delegate focus, live regions, and contrast to FrontComposer, but the cited FrontComposer docs only back skip links, shell shortcuts, nav landmarks, and shell-owned status surfaces. A Blazor developer following these spines would have to guess where focus goes when an Approve button disables itself and the row leaves the queue, who renders the `aria-live` node that announces "Approved. Posting is pending.", what "nearing expiry" means, and what the French strings are. The viewport fail-closed rule as written locks out desktop users at 400% zoom from governed approval, which is a WCAG 1.4.10 conflict the spines do not acknowledge. Two findings are critical because they block a keyboard or low-vision approver from completing UJ-3.

## Findings

- **[critical]** The fail-closed responsive rule makes `ProposalResolution` and the other five high-risk families "unavailable" at the most restrictive viewport. A desktop user at 400% browser zoom (WCAG 1.4.10 Reflow, 320 CSS px) lands in the Phone tier and loses the ability to approve. Nothing in the spines says the required decision context must be *made* presentable at 320 px before falling back; the rule is written as a lockout, not a last resort, and no "essential" exception is claimed or evidenced (EXPERIENCE.md § Responsive & Platform; DESIGN.md § Layout & Spacing). *Fix:* require that proposal detail, version history, and confirmation controls stack to a single column and remain operable at 320 CSS px width / 400% zoom; reserve the unavailability branch for cases where content genuinely cannot render (and require a visible reason plus a "review on a wider viewport" path). Add 1.4.10 reflow evidence at 320 px to `LR-UI-CONFORMANCE`.

- **[critical]** Focus is lost at the single most important keyboard moment. The pending-lock rule says to *disable* the same-resource action while pending (EXPERIENCE.md § Interaction Primitives, § High-Risk Pending Commands). A disabled `FluentButton` is unfocusable, so a keyboard approver who presses Approve has focus dropped to `<body>`. Meanwhile projection polling may re-sort or remove the row from a "needs my action" filter, and the dialog "return focus to the trigger" contract (§ Accessibility Floor) has no target when the trigger is gone. No fallback focus target and no announcement of `approved` / `posting pending` are specified; the 4.1.3 list in § Accessibility Floor announces `posted` and `posting failed` but not the intermediate states the user actually waits in. *Fix:* specify (a) `aria-disabled="true"` or a replacement pending control that keeps focus, never `disabled` on the activated control; (b) on resolution, move focus deterministically (status region of the same proposal, then next row, then grid heading `h1` via `FcPageHeader.FocusHeadingAsync`); (c) polite announcements for `authoritative pending`, `approved`, `posting pending`, and `regenerated version available`; (d) polled re-renders must not steal or drop focus from the focused row.

- **[high]** Live-region delegation is not backed by the cited docs. `front-composer-shell.md` documents `aria-live` only for shell-owned surfaces (projection connection, pending commands, density announcer); `datagrid.md` covers grid notices. There is no documented adopter-facing announcer for domain events, and `project-context.md` explicitly tells adopters to keep their own `<div>` for sr-only `aria-live` regions. The spine's "Use FrontComposer FC-A11Y primitives: ... status live regions" (EXPERIENCE.md § Accessibility Floor, § FrontComposer Readiness) therefore delegates something the domain must build. The politeness per event is also unspecified beyond "avoid assertive for pending" (EXPERIENCE.md § Accessibility Floor). *Fix:* state that Agents owns one page-level polite `role="status"` node and one `role="alert"` node (rendered before first mutation, skip-first-render), and give a per-event table: alert for `denied`, `generation failed`, `posting failed`, `expired`; status for `authoritative pending`, `proposal created`, `approved`, `posting pending`, `posted`, `regenerated`, `context blocked`, and the expiry warning. Note that NFR-14 `LiveRegionAnnouncedTick` depends on this node existing.

- **[high]** No route heading or post-navigation focus rule. `FcPageHeader.FocusHeadingAsync()` is page-invoked and throws unless `HeadingTabIndex="-1"` is set (FrontComposer `FcPageHeader.razor.cs`); the shell does not move focus on route change or on opening a detail panel. The spines never require an `h1` per route, a heading hierarchy inside accordion items, or focus placement when the proposal editor opens from the queue or notification (EXPERIENCE.md § Information Architecture, § Accessibility Floor; WCAG 2.4.3, 2.4.6, 1.3.1). *Fix:* every Agents route renders `FcPageHeader` with a non-blank `Heading`, `HeadingTabIndex="-1"`, and a Blazor `PageTitle` (EN/FR); on navigation and on opening proposal detail, focus the heading; accordion item titles are `h2`, in-panel sections `h3`.

- **[high]** Forms have no error contract. `agent-config-form`, `approver-policy-builder`, `provider-catalog-grid` edit, `content-safety-policy-editor`, and `cost-control-editor` say "inline blockers" and "validates" (EXPERIENCE.md § Component Patterns; DESIGN.md § Components) but never specify: error text programmatically associated with the field (`aria-describedby`, `aria-invalid`), an error summary with focus moved to it or to the first invalid field on submit, instructions for numeric units (currency, per-call cap unit, budget period), suggestion text, how a write-only secret field exposes "configured / not configured" to AT, or the accessible names of add/remove/reorder controls on policy-source rows (WCAG 3.3.1, 3.3.2, 3.3.3, 4.1.2). *Fix:* add a Forms subsection to § Accessibility Floor: label every control, associate errors, focus the first error on submit, state units in the label or description, name secret fields with their configured state ("API key, configured"), and give each policy-source row an accessible name that includes its basis.

- **[high]** Contrast is delegated in a circle and never verified. EXPERIENCE.md § Accessibility Floor says "Visual contrast and icon/color pairing live in `DESIGN.md`"; DESIGN.md § Colors only says "Inherit Fluent" and never states 4.5:1 text / 3:1 non-text targets. Load-bearing combinations with no check: badge label text on `Warning`, `Severe`, `Important`, and `Subtle` fills in light and dark themes; `{typography.caption}` and `{typography.mono}` metadata (Fluent `NeutralForeground3/4` roles are the usual 4.5:1 failures); focus ring on the brand-accent-selected `response-mode-toggle` (3:1); forced-colors mode. FrontComposer's CI accessibility gate proves only `/__frontcomposer/specimens/*` routes (`accessibility-verification/README.md`), so nothing upstream will catch Agents surfaces. *Fix:* DESIGN.md states the AA targets explicitly; EXPERIENCE.md § FrontComposer Readiness / `LR-UI-CONFORMANCE` requires an Agents-owned axe lane over every interactive V1 route in Light/Dark and forced-colors, plus the manual AT matrix FrontComposer itself requires (NVDA+Firefox, JAWS+Chrome, VoiceOver+Safari).

- **[high]** French does not exist in the spines. Parity is binding, yet the Voice and Tone table (EXPERIENCE.md § Voice and Tone) and every state name are English-only and FR is nowhere deferred *or* delivered. Missing rules: pluralization for the pending count ("1 proposal / 2 proposals" vs "1 proposition / 2 propositions", zero handling), culture-formatted dates for `ObservedAt`/`ValidUntil`/timestamps (UTC vs local, FR `dd/MM/yyyy HH:mm`), currency and percent for the cost editor (`1 234,56 €`, `80 %` with NBSP), and whether architecture tokens such as `Ready / Callable / None`, `InsufficientEvidence`, `Stale` are displayed raw (untranslated) or mapped to localized labels. `FcDestructiveConfirmationDialog` hard-codes the literal `Cancel` (FrontComposer source), so reusing it for high-risk confirmation breaks parity unless Agents supplies its own labels. Fluent UI Blazor's built-in ARIA strings (grid sort, pagination) also need an FR check. *Fix:* add the FR column to the microcopy table or explicitly mark FR authoring as a launch blocker with an owner; require ICU-style or per-count keys for plurals; require `CultureInfo`-formatted dates/numbers/currency via named placeholders; require a localized display label for every architecture token; forbid reusing shell dialogs with unlocalized literals.

- **[high]** Expiry timing has no accommodation and an undefined trigger. Expiry is configurable from 1 hour to 30 days (EXPERIENCE.md § UX Closure Decisions; PRD FR-18). "Proposal nearing expiry" (DESIGN.md § Colors; `proposal-queue-grid` expiry column) never defines the threshold, the presentation (static "Expires at 14:30" vs a ticking countdown), or whether a warning is announced. A live countdown in a grid cell is auto-updating content (WCAG 2.2.2) and must not sit inside an `aria-live` node; WCAG 2.2.1 requires either an essential-exception claim or a warn-and-extend mechanism. The 24 h default clears the 20-hour exception, the 1 h floor does not. *Fix:* define the warning threshold (e.g., 10% of the expiry window or 1 h, whichever is smaller), render expiry as an absolute localized timestamp plus a static relative label refreshed at most once per minute outside live regions, announce the warning once per proposal, and record a 2.2.1 position (governance time limit is essential; no extension) with Product sign-off.

- **[medium]** Proposal editor keyboard choreography stops at a capability list. "Fully keyboard-operable: edit, select version, compare metadata, regenerate, approve, reject, abandon, and exit without committing" (EXPERIENCE.md § Accessibility Floor) does not say what control selects a version (radio group, listbox, or selectable `FluentDataGrid` rows each need different semantics), where focus goes and what is announced when regeneration finishes and the editor content changes under the user, what "compare metadata" is operationally, or whether `Esc` inside the textarea (§ Interaction Primitives: "`Esc` closes transient UI without committing") can discard unsaved edits. *Fix:* version selection is a radio group whose labels include version kind, author, and timestamp; regeneration keeps focus on the Regenerate control, then announces "Version N generated" and offers a "Go to new version" action; "exit without committing" is an explicit button with an unsaved-changes confirmation, and `Esc` never discards editor content.

- **[medium]** High-risk confirmation dialogs are under-specified. "Explicit confirmation ... keyboard/focus/live-region behavior" (DESIGN.md § Components, EXPERIENCE.md § Interaction Primitives) does not state that initial focus lands on Cancel (FrontComposer's `FcDestructiveConfirmationDialog` does this, but Agents cannot rely on it given the unlocalized label), that Enter on the body must not commit, or what "incomplete restrictive deletion confirmation" looks like. If a type-to-confirm pattern is chosen, note that WCAG 3.3.7 Redundant Entry permits it under the security exception. *Fix:* state initial focus on the non-committing action, destructive action is never the default button, and the confirmation body names the resource and the future-only effect in a single localized string.

- **[medium]** Grid status carrier contradicts DESIGN. `datagrid.md` says generated `[ProjectionBadge]` cells render `FcStatusIcon` with an accessible label and a hover/focus tooltip, i.e., icon-first, while DESIGN.md § Colors mandates "Fluent semantic role plus icon plus visible text" for every status. The proposal queue and provider catalog are FC-TBL grids (DESIGN.md § Components), so the developer must choose without guidance. *Fix:* decide per grid: either accept `FcStatusIcon` (icon + accessible name + tooltip, compliant under 1.4.1 but not under the spine's own rule) or require a visible text column; do not leave both rules standing.

- **[medium]** Pending-count badge has no accessible name contract. `navigation.md` says badge labels are shell-owned and rendered from `IBadgeCountService`; the spine calls for "an accessible pending-count badge" (DESIGN.md `proposal-notification`) that AT will read as "3" unless the domain can name it. The notification "status entry" role and where it lives are also unspecified. *Fix:* verify the shell exposes a localizable badge label or wrap the count in a domain-named link ("3 proposals pending approval"); define the status entry as a link inside a named region.

- **[medium]** Hover-revealed row actions are not required to reveal on focus. "Hover may reveal secondary actions on desktop" (EXPERIENCE.md § Interaction Primitives) only guarantees that *required* actions are not hover-only; secondary actions still vanish for keyboard users unless `:focus-within` reveals them (WCAG 2.1.1, 1.4.13). *Fix:* any hover-revealed action must also render on row focus-within and be dismissible; tooltips are hoverable and dismissible via `Esc`.

- **[medium]** WCAG 2.5.8 Target Size is unaddressed under FrontComposer density settings. The shell offers Compact/Comfortable/Roomy density (`settings.md`); filter chips, row action icons, version-history rows, and badge triggers can drop below 24 x 24 CSS px in Compact. *Fix:* require 24 px minimum (or 24 px spacing exception) for every actionable target in all three densities and add a Compact-density check to the conformance lane.

- **[medium]** Forced client refresh after timeout destroys context silently. "A client timeout forces refresh and never implies success" (EXPERIENCE.md § High-Risk Pending Commands) says nothing about restoring focus or announcing what happened. *Fix:* after a forced refresh, focus the route heading and announce a localized status ("Status refreshed. Approval is still pending.").

- **[medium]** Command palette entries are not specified. § Interaction Primitives says the palette "remains available" and domain shortcuts must not conflict, but never states whether Agents registers palette commands (Approve, Open queue), how they are policy-gated, or that any `g x` sequence shortcut is subject to WCAG 2.1.4. *Fix:* list the Agents palette entries (or state there are none for V1) and their authorization behavior.

- **[medium]** Override diagnostics are presented as coverage for hand-authored pages. HFC1050–1055 apply to FrontComposer customization overrides (`front-composer-shell.md`, `datagrid.md`); the spine's "Required for all custom proposal/editor overrides" (EXPERIENCE.md § FrontComposer Readiness) leaves plain Agents `.razor` pages with no build-time accessibility check at all. *Fix:* state that diagnostics cover overrides only and that hand-authored surfaces rely on the Agents axe/keyboard lane and manual AT matrix from the contrast finding.

- **[low]** WCAG 2.4.11 Focus Not Obscured: `pinnedColumns` on both grids, the proposal editor "action rail", and MessageBar status regions could be sticky and overlap focused rows. *Fix:* declare that no sticky element overlaps the content scroll area, or set `scroll-padding` equal to sticky heights.

- **[low]** WCAG 2.5.7 Dragging Movements: policy-source row ordering and column prioritization are the only candidates; FC-TBL's prioritizer is a popover, but the approver-policy builder ordering is unspecified. *Fix:* state that row order is edited with buttons or a menu, never drag-only.

- **[low]** WCAG 3.2.6 Consistent Help and 3.3.8 Accessible Authentication: neither applies to the Agents domain as written (no help mechanism is introduced; authentication is shell/account-menu owned). *Fix:* record both as N/A with the reason, so the conformance lane does not report them as gaps.

- **[low]** RTL: nothing forbids it. FrontComposer uses logical properties for page measure; the spine's "version and action rail" and pinned columns should also be described in logical terms (inline-start/end). *Fix:* one sentence in DESIGN.md § Layout & Spacing.

## What is done well

- No-color-only is stated as mandatory with a concrete carrier rule (role + icon + visible text + accessible name), and every status token has a defined meaning that a text label can carry.
- Success discipline (`posted` only, Degraded is Warning, pending never Success) is precisely the kind of state clarity screen-reader users need; the copy table gives usable, non-jargon strings.
- Whole-string localization with named placeholders and a ban on runtime sentence assembly is exactly right.
- Reduced motion, hover-not-required for essential actions, `Esc` as non-committing, focus return to trigger, and provider-secret exclusion from accessible names and announcements are all called out.
- NFR-14 ties terminal render to a localized live-region mutation, which makes announcement a measured launch gate rather than a wish.
- The FluentAccordion rule preserves a single primary region and never collapses sole content, which keeps heading structure and focus order predictable.
