# Governance & Audit Review — Hexalith Agents

Reviewer lens: governance, authorization, audit. Inputs: `DESIGN.md`, `EXPERIENCE.md`, `.memlog.md`, PRD + addendum, sprint change proposal 2026-08-02, `ARCHITECTURE-SPINE.md`, `launch-readiness-register.md`, and the downstream Story 5.3 spec plus the shipped `ProviderCatalog.razor` it produced. Assumption throughout: a story-dev agent builds exactly what the spines say and nothing more.

## Overall verdict

The spines are disciplined about the one thing the 2026-08-02 correction targeted — Success is never rendered for anything short of proven callability or a projection-confirmed post, and failed generation never masquerades as a proposal. They are far weaker at the edges where governance actually fails in operation: two approvers on one proposal, a reload mid-pending, a deep link to another tenant's id, a pricing row that says `0 USD`, and a provider disable with no confirmation. Story 5.3 has already demonstrated the cost of that silence: the story-dev invented an 8-second poll timeout, relabelled projection lag as `Stale`, defaulted pricing to zero, and shipped provider enable/disable with no confirmation or pending lock — all without violating a single sentence of the spines.

## Findings

- **[critical]** Provider/model pricing is a cost-governance control with no UX rule at all: no validation (positive, non-zero, currency matches the tenant budget currency), no confirmation, no future-only-effect copy, no "affects reservations from next attempt" statement, and no visible pricing version on the grid. The shipped 5.3 editor defaults `_inputPrice`/`_outputPrice` to `"0"` and `_currency` to `"USD"`; a zero price is "priced" under AD-10/AD-21, so the model is eligible, reservations are 0, and the 80%/100% caps never fire while the grid reads as healthy. (DESIGN.md § Components › provider-catalog-grid, cost-control-editor; EXPERIENCE.md § Component Patterns › provider-catalog-grid, § Interaction Primitives). *Fix:* add a pricing sub-rule to provider-catalog-grid: no default values; input/output units must be > 0; currency must equal the tenant budget currency or the row renders `status-important` "pricing/budget currency mismatch — reservations blocked"; pricing edits are `ProviderCatalogMutation` high-risk with explicit confirmation showing old → new units, effective version, and "applies to attempts prepared after confirmation"; the grid pins a pricing-version column.

- **[high]** `ProviderCatalogMutation`, `AgentSetupMutation`, and `AgentActivation` are operation families in the register's `OperationGateMatrix` but are absent from the six-family high-risk list, so they get no explicit confirmation, no session/resource/family pending lock, and no double-submit protection. Disabling a provider blocks every Agent selecting it (FR-4) yet the shipped page has no dialog and no blast-radius display. (EXPERIENCE.md § State Patterns › High-Risk Pending Commands, § Interaction Primitives; DESIGN.md § Components › provider-catalog-grid). *Fix:* extend the high-risk list to the register's full family inventory, or state explicitly which families are exempt and why; require the disable confirmation to list the Agents whose callability will be blocked; require future-only copy for enable/disable.

- **[high]** Concurrent approver conflict has no UI state. AD-13 makes EventStore concurrency authoritative, but the Proposal Lifecycle table has no `superseded`/`conflict` entry, the advisory lock is per-session so the second approver is never locked, and the live-region list omits "proposal state changed by another Party". A story-dev will show a generic error or, worse, leave the stale `pending approval` row rendered with an enabled Approve button. (EXPERIENCE.md § State Patterns › Proposal Lifecycle, § Accessibility Floor). *Fix:* add a `superseded by another decision` outcome for every proposal action: render the authoritative current state, name the deciding actor where the disclosure category allows, disable all resolution controls, announce via live region, and never show the rejected local action as pending.

- **[high]** Approve-with-uncommitted-edits is unspecified. UJ-3 says Anika "selects the version that should be posted" and approves, but nothing forbids approving while the editor holds unsaved text, and the confirmation pattern never requires the dialog to show the exact `VersionId`, its kind (generated/edited/regenerated), author, and content that will post. The editor and the approve action can disagree silently. (EXPERIENCE.md § Component Patterns › proposal-editor, § Key Flows › UJ-3; DESIGN.md § Components › proposal-editor). *Fix:* approval is disabled while the editor is dirty; the approval confirmation renders the selected version's id, kind, author, timestamp, and full content in the same bounded preview style; the approved-version marker in version-history must match that id after projection confirmation.

- **[high]** Pending-lock survival across reload, navigation away, and a second tab is undefined. "User session" is not defined (browser session, Blazor circuit, tab?), the client timeout has no value, and there is no rule for what the UI renders after a forced refresh if the projection still shows no terminal state. Story 5.3 invented `ProjectionPollingTimeout = 8s` and, after timeout, sets `Freshness = Stale` — reusing the register's `Stale` (contract expired) for mere projection lag. (EXPERIENCE.md § State Patterns › High-Risk Pending Commands, § FrontComposer Readiness). *Fix:* define session = authenticated user + tab/circuit; on reload the UI must re-derive pending state from the authoritative status projection (`agent-interaction-status`, `provider-capability-pricing`, etc.) and re-arm the lock if a pending command for that resource/family exists; a second tab renders the resource as "pending in another session" with actions disabled; name the timeout value and the post-timeout state (`awaiting projection`, not `Stale`); add a distinct `duplicate submission (idempotent)` outcome.

- **[high]** No "approval authority indeterminate" state. AD-12 resolves approver rights from the policy snapshot *plus current dependency availability* (Tenants projection, Conversations detail). `status-important` is reserved in Colors for "missing/stale policy basis" but no component color list except agent-readiness-badge includes it, the Proposal Lifecycle table has no matching state, and proposal-editor only distinguishes authorized vs read-only. When Tenants/Conversations are unavailable a story-dev either leaves Approve enabled (UI fails open until the server rejects) or shows a generic error. (DESIGN.md § Colors, § Components › proposal-state-badge, proposal-editor; EXPERIENCE.md § State Patterns › Proposal Lifecycle). *Fix:* add `authority unresolved` to the proposal editor/state table using `status-important`; all resolution controls disabled; copy names the unavailable dependency safely; add `status-important` to proposal-state-badge's color list.

- **[high]** Deep links, the command palette, and grid filters have no tenant-isolation rule. "Empty must not leak unauthorized records" covers grids only. Route ids (`AgentInteractionId`, `ConversationId`, `ProviderId/ModelId`) pasted from another tenant must render an indistinguishable not-found/denied state; Agents-registered palette entries and search must be policy-gated and tenant-scoped; caller/Party filter suggestions must not enumerate cross-tenant Parties. None of this is written. (EXPERIENCE.md § State Patterns › List And Detail Surfaces, § Interaction Primitives, § FrontComposer Readiness › Policy-gated nav). *Fix:* add a "Detail And Deep-Link Surfaces" rule: unauthorized or foreign ids render one `not available` state with identical copy, status code class, and timing for missing vs denied; Agents palette/search entries obey the same policy gate as nav and never return records outside the current tenant scope.

- **[high]** Provider catalog scope is undeclared. The catalog key is global (AD-10), FR-19 allows platform-scoped records "when explicitly platform-scoped and authorized", and Story 5.3 had to invent "never disclose another tenant's existence, rows, or counts". The spines never say whether the grid, its audit trail, or the disable blast radius are tenant- or platform-scoped. (EXPERIENCE.md § Information Architecture › Provider catalog; DESIGN.md § Components › provider-catalog-grid, audit-evidence-panel). *Fix:* state the scope explicitly, and if platform-scoped, state that any cross-tenant impact (Agents using a model in other tenants) is rendered as an aggregate count or omitted per disclosure category, never as tenant names.

- **[high]** Secret handling is under-specified at the UI level. "Secret fields use write-only or configured-state presentation" invites a story-dev to build a secret-value input, yet there is no masking rule, no never-echo-on-edit rule, no "never in URL/query/route/error text/validation message/clipboard" rule, and no statement whether the secret *reference* itself is displayable (Story 5.3 chose never to render `ConfigurationReferenceId`; the shipped editor uses a plain `FluentTextInput` for it). (DESIGN.md § Components › provider-catalog-grid; EXPERIENCE.md § Component Patterns › provider-catalog-grid, § Accessibility Floor). *Fix:* forbid secret-value entry in the Agents UI entirely (reference only, resolved through `EXT-SECRETS-1`); declare the reference id operator-only; require masked input with autocomplete off if any secret-adjacent field is editable; require that validation and error copy never echo submitted field values.

- **[medium]** `Pass` and `Ready / Callable / None` can render Success past `ValidUntil` on an open page. Both carry exclusive `ValidUntil`, but no rule tells the client to re-evaluate `T` on a cadence or to demote to `Stale`/`checking` when validity lapses without a fresh projection. (EXPERIENCE.md § State Patterns › Launch Readiness Evidence, § Provider And Model; DESIGN.md § Components › provider-status-badge, launch-readiness-panel). *Fix:* require client-side validity re-evaluation on poll/focus; when `T >= ValidUntil` and no newer observation is rendered, the badge shows `Stale — re-observation required`, never the prior Success.

- **[medium]** Agent readiness Success does not distinguish "callable under `QualificationExecutionGateSet`" from "production-enabled after `RQ-1` READY". A production-like profile can show `hexa is callable` in Success while the register says NOT READY, and an operator will read it as launch-ready. (EXPERIENCE.md § State Patterns › Agent Readiness, § Key Flows › UJ-5; DESIGN.md § Components › agent-readiness-badge). *Fix:* the badge and overview carry the evaluated `EnvironmentProfile`, gate-set name, matrix version, and `RegistryRevision`; production enablement is a separate indicator that is never Success unless `RQ-1` is READY.

- **[medium]** Regeneration failure on an existing proposal is undefined. The lifecycle table covers only successful `regenerated`; if regeneration (Story 7.3, under fresh gates) fails, is the proposal still `pending approval` with prior versions selectable, or does it enter a failed state? A story-dev may mark the proposal failed and strand approvable versions. (EXPERIENCE.md § State Patterns › Proposal Lifecycle, § Generation Failure Record). *Fix:* state that regeneration failure leaves the proposal non-terminal with all prior versions intact, records a separate failure record linked to the proposal, announces it, and keeps approve/reject/abandon available on existing versions.

- **[medium]** `posting failed` is unclassified: the table marks rejected/abandoned/expired as terminal but not `posting failed`, and "show recovery/status" never says whether an approver may retry posting, re-approve, or must start a new call. (EXPERIENCE.md § State Patterns › Proposal Lifecycle; DESIGN.md § Components › proposal-state-badge, operational-status-panel). *Fix:* declare it terminal-for-this-approval; the only recovery is a new Agent Call (or, if architecture permits, an explicit idempotent `retry posting` under `ProposalResolution` reusing the deterministic `MessageId`) — pick one and write it.

- **[medium]** Terminal-proposal enforcement is server-side only in the spine. "Cannot post" is a treatment note; nothing says edit/regenerate/approve/reject/abandon controls are removed or disabled on `rejected`/`abandoned`/`expired`/`posted`, and FR-16's "regeneration is blocked after terminal" is not restated. (EXPERIENCE.md § Component Patterns › proposal-editor, § State Patterns › Proposal Lifecycle). *Fix:* on any terminal state the editor is read-only, all resolution actions are absent (not merely disabled), and the sole action is "Start a new Agent Call".

- **[medium]** Expiry: "nearing expiry" Warning has no threshold, which cannot be a fixed number when expiry ranges 1h–30d; expiry racing approval has no UI outcome (`approved` then `expired`, or approval rejected because expired); and the expiry-duration configuration surface required by FR-18/OQ-3 is missing from the IA and the agent-config-form field list. (DESIGN.md § Colors, § Components › agent-config-form; EXPERIENCE.md § Information Architecture, § UX Closure Decisions). *Fix:* define nearing as a percentage of the proposal's own lifetime (e.g., final 10% or 1h, whichever is larger); add an "approval rejected — proposal expired at `ExpiresAt`" outcome; add expiry duration to `hexa` configuration with future-only copy and the stored `ExpiresAt` on every proposal.

- **[medium]** Approval policy basis and its FR-7 disclosure category (user-visible, operator-only, redacted, omitted) are not carried into version-history or audit-evidence-panel; the audit panel lists approver and timestamp but not the policy basis that authorized the decision, and no component says how a redacted/omitted basis renders. (DESIGN.md § Components › audit-evidence-panel, version-history; EXPERIENCE.md § Component Patterns › approver-policy-builder). *Fix:* each approval-related decision row shows policy basis rendered by disclosure category with a whole-string placeholder for redacted/omitted; API and UI use the same category.

- **[medium]** Projection-lag vocabulary collides with register `Stale`. Read surfaces (overview, queue, detail) never show projection version or "as of"; grids get "stale/degraded where relevant" with no definition; the shipped page maps not-caught-up → `Freshness.Stale`. (EXPERIENCE.md § State Patterns › List And Detail Surfaces; DESIGN.md § Components › operational-status-panel). *Fix:* reserve `Stale` for expired evidence/contracts; use `catching up` for projection lag; every authoritative read surface exposes projection id + version in `{typography.mono}` so audit references can be correlated.

- **[low]** agent-readiness-badge's color list includes `status-important` but the Agent Readiness state table maps no state to it; a story-dev has no trigger for it. (DESIGN.md § Components › agent-readiness-badge; EXPERIENCE.md § State Patterns › Agent Readiness). *Fix:* add `ambiguous Party identity` / `policy basis unresolved` rows mapped to Important, or drop the color.

- **[low]** Policy-gated nav says "hide or deny"; the two produce different disclosure profiles. (EXPERIENCE.md § FrontComposer Readiness). *Fix:* choose hide for unauthorized entries and deny-with-safe-copy for direct navigation.

- **[low]** Budget 80%/100% basis is unspecified (usage only vs usage + open reservations). (DESIGN.md § Components › cost-control-editor). *Fix:* state that thresholds evaluate usage plus outstanding reservations and label both figures.

- **[low]** Response-mode change copy is future-only but does not say pending proposals remain proposals when switching to Automatic. (EXPERIENCE.md § Component Patterns › response-mode-toggle). *Fix:* add that sentence to the confirmation copy.

## What is done well

- Success is unambiguously reserved: `posted`, proven `callable`, current `Pass`, and projection-confirmed completion only; `approved`/`posting pending` are progress; `Degraded` is Warning strictly under `Callability == Callable`. The Do/Don't table and Voice table repeat the rule in operator language.
- The `submitted -> authoritative pending -> projection-confirmed terminal` chain is defined with precise seams and tied to the NFR-14 sample kinds, so a story-dev cannot promote optimistic state.
- Failed generation is walled off from the proposal workflow in the queue, editor, notifications, version history, and audit panel alike.
- Version history preserves every generated/edited/regenerated version with author/source and provider/model, and approval selects one version.
- Launch readiness rendering is exact: `InsufficientEvidence` and `Stale` never degrade to Pass, and the 30-sample, monotonic-clock, live-region evidence rules are stated in UI terms.
- Grid surfaces already require permission-denied and no-leak empty states; the shipped 5.3 page honours them (`AgentSurfaceKind.PermissionDenied`).
