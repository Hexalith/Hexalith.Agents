# Accessibility Review — Hexalith Agents

Reviewer lens: accessibility as a buildable contract (WCAG 2.2 AA binding; whole-string EN/FR parity binding). Run: 2026-09-09, against the spines updated 2026-09-09. Inputs read in full: `DESIGN.md`, `EXPERIENCE.md`, `.memlog.md`, `reconcile-validation-2026-09-09.md`, the predecessor review `.working/validation-2026-09-09-pre-update/review-accessibility.md`, and `references/Hexalith.AI.Tools/hexalith-ux-instructions.md`. Verified against source rather than against the reconciliation's claims: FrontComposer `FcPageHeader.razor(.cs)`, `FcAggregateDetailPage.razor(.cs)`, `FcStatusFilterChips.razor(.cs)`, `FrontComposerNavigation.razor(.cs)`, `FcFluentIcons.cs`, `FrontComposerShell.razor`, every Shell component emitting `role="status"`/`role="alert"`/`aria-live`; Fluent UI Blazor v5 `FluentButton`, `FluentRadio`/`FluentRadioGroup`, `FluentMessageBar` parameter surfaces; and the shipped `src/Hexalith.Agents.UI` tree.

## Overall verdict

The Update run did real work and most of it holds: the icon inventory is now true against `FcFluentIcons.cs` (all seven status roles bind to shipped 16 px factory *methods*, and they are seven visually distinct glyphs), `FluentMessageBar.AriaLive` really does carry `Off`, `FcPageHeader` really does supply an `h1`, a `PageTitle`, a `HeadingTabIndex`, and a `FocusHeadingAsync()` that fails loudly rather than silently, `FcProjectionConnectionStatus` really is rendered by `FrontComposerShell` so the shell really can own the connection-lost announcement, and the confirmation-never-opens-on-a-selection-event generalisation closed the whole class of arrow-key traps. Sixteen of the twenty-two prior findings are genuinely closed. But the two rewrites the run is proudest of both bought their tidiness with a mechanism that does not exist. The live-region rewrite hands the entire post-submit announcement set for UJ-2 — `denied`, `generation failed`, `capacity rejected`, `Posted` — to a pair of nodes that live inside a dialog the same sentence says closes on Submit, on a seam whose two declared artifact kinds host no persistent Agents region anywhere else; that is a blind participant pressing Submit on the product's only V1 invocation path and hearing nothing, ever, and it is worse than the gap it replaced because it now reads as solved. The `aria-disabled` binding rule is stated spine-wide as `FluentButton.DisabledFocusable`, then applied to version radios — and `DisabledFocusable` exists on `FluentButton` and `FluentCompoundButton` only, not on `FluentRadio`. Underneath both sits the same unexamined assumption: that a focusable disabled control with a *nearby* reason is an explained control. Nothing in either spine programmatically associates a single blocked control with its blocker — no `aria-describedby`, anywhere — so a screen-reader user who tabs to Approve hears "Approve, unavailable" and must go hunting for why, on nine confirmation families, six rail actions, the version radios, **Call hexa**, export, and deletion. And the editor's dirty-state rules now block Approve and the version radios "until you save or discard" while the action rail contains neither a Save nor a Discard control. One critical, nine high.

## Findings

### Live regions and announcement ownership

- **[critical]** The `ConversationAgentCallPanel` live-region pair is destroyed by the very event it exists to announce. `EXPERIENCE.md:183` puts one polite and one assertive node inside the panel, "placed after Submit in DOM order", and in the same sentence: "On Submit the dialog closes, focus returns to **Call hexa** … `submitted`, `authoritative pending`, `denied`, `capacity queued`, `generation failed`, `PostingPending`, and `Posted` each announce through those nodes." `EXPERIENCE.md:95` makes the panel *the dialog body* ("Conversations owns the **Call hexa** trigger … Agents owns the dialog body, which is `ConversationAgentCallPanel`"), and `DESIGN.md:315` renders the status as `FluentBadge` rows inside that same panel. So at the moment of Submit the panel unmounts, and with it both live nodes and every status row: a removed live region announces nothing, and there is no visible status either. Every outcome of the call — including the two that matter most, `denied` and `generation failed` — is announced into a node that no longer exists, for every user. The seam cannot rescue this: `EXPERIENCE.md:92` declares `EXT-CONV-UI-1` to carry exactly two artifact kinds, an action contribution and a per-message decoration slot keyed by `MessageId`, and neither can host a persistent Agents-owned status region beside the trigger. `EXPERIENCE.md:429` and `reconcile-validation-2026-09-09.md § 2` both record this as applied and closed. It is not. *Fix:* split the artifact. The dialog body stays the prompt surface; a separate persistent Agents-owned status region (the `AgentsPageStatusRegion` carrier, or a named sibling) is contributed to the Conversation surface next to **Call hexa**, mounted for the lifetime of the Conversation view and not for the lifetime of the dialog, and carries both nodes plus the status rows. Add that region as a **third** artifact kind on `EXT-CONV-UI-1` alongside a focus-return contract for the Conversations-owned trigger (the panel cannot focus a foreign component without one), and state that the panel announces only what happens while it is open.

- **[high]** Events that no node owns, on the exact states users wait in. `EXPERIENCE.md:433-436` is presented as exhaustive ("every event is announced by exactly one node"), yet the spine's own vocabulary contains announced-nowhere states: `Submitted` (only `authoritative pending` is listed) and, worse, **`awaiting projection`** — the catch-up-exhaustion outcome after an 8-second wait on every high-risk write (`EXPERIENCE.md:265`, `EXPERIENCE.md:363`, `EXPERIENCE.md:367`) — plus `pending in another session` (`EXPERIENCE.md:366`), `safety blocked at approval`, `stale proposal`, `regeneration ceiling reached`, `duplicate submission (idempotent)` (`EXPERIENCE.md:346-349`), and the *recovery* half of connection loss (`EXPERIENCE.md:397` restores the controls "with focus preserved" but announces nothing, leaving an assertive "unavailable" as the user's last information). In every one of these cases the state change is carried by an adjacent `FluentBadge` whose text changes — and `EXPERIENCE.md:424` forbids that badge from being a live region ("no badge, panel, or row component carries `role="status"` of its own"). The user is focused on a `DisabledFocusable` button whose label did not change, beside a badge that mutated silently. *Fix:* add the missing events to the politeness table — `Submitted`, `awaiting projection` (polite, with the refresh action named), `pending in another session`, connection restored, and each display-only outcome — or state explicitly which of them are deliberately silent and why the focused control's own accessible description carries them instead.

- **[high]** The Shipped-code corrections inventory materially undercounts the drift for both new rules, so the stories that absorb them will not deliver them. `EXPERIENCE.md:635` names one live-region divergence — "Per-badge `role="status"` on five badge components" → Story 8.6. The shipped tree carries live regions in **twenty** files: the five badges, plus `AuditEvidencePanel`, `LaunchReadinessPanel`, `OperationalStatusPanel`, `AgentSurfaceState` (the not-available/empty/error surface, which also puts an `h2` inside a live region), `AgentCallStatusFeedback`, `ProposalTransitionAnnouncer`, `ProposalEditor`, `ProposalRegenerator`, and one each on `ProposalApprover`, `ProposalRejector`, `ProposalAbandoner` — i.e. a private polite/assertive node per resolution command, on the exact controls whose announcements `AgentsPageStatusRegion` now owns — plus three `aria-live` paragraphs on `ProviderCatalog.razor:42,48,54` and `ApproverPolicy`, `LaunchReadiness`, `ProposalDetail`. Double announcement at the approval moment is the defect the rewrite exists to prevent, and it survives a story-dev who works the drift table honestly. `EXPERIENCE.md:636` has the same problem for the second rule: it names `Disabled` "on the regenerate control", where the shipped tree uses `Disabled` on at least a dozen blocked-but-explicable controls (`ProviderCatalog.razor:33,66,71,112,117,209,214,220`, `AgentConfiguration.razor:91,135,201,207`, `LaunchReadiness.razor:135`, and `Disabled="true"` on the response-mode toggle inside `ConversationAgentCallPanel.razor:42`). *Fix:* restate both rows as inventories with counts and file lists, or as "every `role="status"`/`aria-live` node in `src/Hexalith.Agents.UI` outside `AgentsPageStatusRegion` is removed under 8.6" and "every `Disabled` on a blocked-but-explicable control is converted under its owning story"; a per-control audit belongs in the story acceptance criteria, not in a one-line pointer.

- **[medium]** The allow-list of FrontComposer speakers is written as if closed but is not. `EXPERIENCE.md:426` permits `FcFilterEmptyState` and `FcExpandInRowDetail` to speak. The Shell ships eight more nodes a grid page can pick up without violating any spine rule: `FcFilterSummary` (`role="status"`), `FcMaxItemsCapNotice` and `FcSlowQueryNotice` (polite bars — and the queue's page size is 25, `EXPERIENCE.md:180`, precisely the cap case), `FcNewItemIndicator` (polite, per new row — which would defeat the aggregated `{count} proposals changed` rule at `EXPERIENCE.md:180`), `FcExpandedRowHiddenBanner`, `FcLifecycleWrapper`, `FcProjectionLoadingSkeleton`/`FcProjectionEmptyPlaceholder`, and `FcStatusBadge`, whose `role="status"` would silently re-create the per-badge defect Story 8.6 is removing — including on the deterministic focus target, where a `role="status"` container is the one element that must not receive focus. *Fix:* make the list closed: name the permitted speakers, then state that no other FrontComposer component carrying `role="status"`, `role="alert"`, or `aria-live` is used on an Agents route without being silenced, and name `FcStatusBadge` and `FcNewItemIndicator` as forbidden.

- **[medium]** Most announced strings have no key, and the parity gate cannot catch it. `EXPERIENCE.md:433-436` lists roughly twenty-four announced events; the Voice and Tone table (`EXPERIENCE.md:112-138`) supplies EN/FR whole strings for about eight of them. There is no string for the nearing-expiry warning, `Version {n} generated`, `awaiting projection`, `catching up`, `pending in another session`, the connection-loss consequence, or the queue's expiry aggregate. `AgentsResourcesParityTests` enforces EN/FR *parity of keys that exist* (`EXPERIENCE.md:159`), so a hard-coded English announcement passes the gate. The announced strings are the only UI a screen-reader user has for these states. *Fix:* state that every event in the politeness table has a named `Agents.<Surface>.<Item>` key, and add the missing rows (at minimum the expiry warning, the queue aggregate, `awaiting projection`, and the connection-loss consequence) to the Voice and Tone table with their French forms.

- **[low]** The carrier's nodes must exist before their content changes; the spine does not say so. `EXPERIENCE.md:424` places `AgentsPageStatusRegion` "once per page body" but never states that both nodes are rendered empty from first render. A node inserted at the same commit as its text is not announced by most AT. The shipped `ProposalTransitionAnnouncer.razor` gets this right (persistent `<section>`, conditional `<p>`); the spine should pin it. *Fix:* one sentence — both nodes render on first paint, empty, and only their text content mutates.

- **[low]** An embedded panel's pair can collide with a host route's carrier, on exactly one surface. The harness `/agents/conversation-call` (`EXPERIENCE.md:79`) is an Agents route until Story 6.7 deletes it, and it hosts the panel, so that route can hold two polite and two assertive nodes with the same events flowing through both. It is delisted and excluded from `LR-UI-CONFORMANCE`, which is why this is low rather than high, but developers use it. *Fix:* state that the panel suppresses its own pair when hosted on an Agents route, or that the harness renders no `AgentsPageStatusRegion`.

### The `aria-disabled` binding rule and blocked-state reasons

- **[high]** No blocked control anywhere in the spine is programmatically associated with its reason. `EXPERIENCE.md:413` justifies the rule precisely — `Disabled` and `Loading` "remove the control from the tab order and take the reason with it" — and then never brings the reason back. Every blocked state renders its explanation as an *adjacent* element: `DESIGN.md:359` ("an adjacent `FluentBadge` … reads `Submitted`, then `AuthoritativePending`"), `DESIGN.md:291` (blockers "inline beside the field"), `EXPERIENCE.md:101` (**Call hexa** "with the safe blocker text"), `EXPERIENCE.md:216` (Approve/Regenerate "with the reason"), `EXPERIENCE.md:189` (export "with `authority unresolved` treatment"), `EXPERIENCE.md:397` (high-risk submits "with the reason"). Visual adjacency is not an accessible description. A screen-reader user tabs to Approve, hears "Approve, unavailable", and must leave the control and explore the region to find out whether they are blocked by a dirty editor, by segregation of duties, by expiry, by a lost connection, or by another Approver — five different recoveries. A focusable disabled button with no reachable reason is the same dead end as an unfocusable one, reached by a longer route. *Fix:* add to `EXPERIENCE.md § Interaction Primitives`: wherever a control is `aria-disabled`, its reason is a localized whole string referenced by `aria-describedby` from the control itself, and the same string is the visible adjacent text; make "every `aria-disabled` control exposes its reason through `aria-describedby`" an assertion in the `LR-UI-CONFORMANCE` lane and the AT matrix.

- **[high]** `DisabledFocusable` does not exist on `FluentRadio`, so the version-radio rule cannot be built as written. `EXPERIENCE.md:182` and `EXPERIENCE.md:216` require "version radios are `DisabledFocusable` with the reason while the editor is dirty"; `DESIGN.md:311` binds version history to `FluentRadioGroup`. At the pin, `DisabledFocusable` is declared on `FluentButton` and `FluentCompoundButton` only — `FluentRadio`'s public surface is `Disabled`, `Value`, `Label`, `LabelTemplate`, and layout properties. The spine's own escape hatch (`EXPERIENCE.md:413`, "or the `aria-disabled` attribute with the control left focusable and its activation suppressed on a hand-authored one") means hand-authoring a radiogroup with roving `tabindex` and arrow-key handling, which the binding UX law tells you not to do when a Fluent component exists — and which reintroduces the original hazard, because in a radiogroup the arrow key *is* the selection, so "focusable but activation suppressed" requires suppressing the browser's own selection semantics. Note the shipped code has the opposite defect (a custom listbox, `EXPERIENCE.md:632`), so Story 7.2 will be told to move *to* a component that cannot express the rule. *Fix:* choose a buildable binding. Either the version list becomes a `FluentButton`-per-version selection (each `DisabledFocusable` while dirty, with `aria-describedby` reason), or the group stays a `FluentRadioGroup` and dirtiness is handled by the unsaved-changes confirmation on selection change rather than by disabling the radios — and say which, because the two have different keyboard contracts.

- **[high]** The editor blocks Approve and version selection "until you save or discard", and neither control exists. `EXPERIENCE.md:216` blocks Approve while dirty; `EXPERIENCE.md:182` blocks the version radios while dirty and says "the reader saves or discards first". The action rail is enumerated three times — `EXPERIENCE.md:212`, `EXPERIENCE.md:216-220`, `DESIGN.md:307` — as Edit, Regenerate, Approve, Reject, Abandon, Retry posting. There is no Save and no Discard. `EXPERIENCE.md:181` offers only "Exit is an explicit button with unsaved-changes confirmation", i.e. the sole way out of the dirty state is to leave the page. A keyboard or screen-reader user who types one character into the editor now faces a blocked Approve pointing at a Save that is not there and blocked radios pointing at a Discard that is not there. This is a self-inflicted dead end created by the Update's own dirty-state rules. *Fix:* put Save (creates the new preserved version) and Discard (reverts the draft) in the rail in all three enumerations, give each an announcement in the politeness table, and state where focus lands after each.

- **[high]** The justification gate does not say which binding it uses, and the wrong one empties the dialog's tab cycle. `EXPERIENCE.md:189` requires a typed justification "before Confirm becomes available" for five families, and `EXPERIENCE.md:193`/`DESIGN.md:355` make the confirmation focus-trapped with Cancel auto-focused. An empty justification is a textbook blocked-but-explicable state, so `EXPERIENCE.md:413` requires `DisabledFocusable` — but the confirmation rows never say so, and a developer reaching for `Disabled` produces a focus-trapped dialog in which the only reachable controls are the textarea and Cancel, with nothing explaining that Confirm exists or what unlocks it. *Fix:* state that Confirm is `DisabledFocusable` while the justification is empty or whitespace, with an `aria-describedby` reason ("Explain why this operation is required before confirming"), and that the same rule governs every gated Confirm.

- **[high]** `superseded by another decision` and the action-rail table give opposite answers, and the loser loses focus. `EXPERIENCE.md:342` says on a concurrency rejection the authoritative state renders and "resolution controls `aria-disabled`". `EXPERIENCE.md:217` says that once `Approved` is projection-confirmed, "Edit, Regenerate, and Approve are **absent**". For the second Approver — who activated nothing and is simply sitting on the detail page while it polls — the state becomes `Approved` by someone else's write, and the two rules disagree about whether their Approve button becomes aria-disabled or vanishes. If it vanishes while focused, focus falls to `document.body` and the page is silent, because the deterministic focus rule (`EXPERIENCE.md:364`) is scoped to "focus after resolution", i.e. the resolution *this* session submitted. *Fix:* rule for the non-actor explicitly: on a poll-driven transition that removes a control the user is focused on, focus moves per the deterministic focus rule (item status cell) and the polite node announces the authoritative state. Then reconcile the two rows: for a viewer who did not act, `aria-disabled` with the `superseded` reason wins; absence is reserved for a fresh render.

- **[medium]** The deterministic focus target may be nameless to AT. `EXPERIENCE.md:364` targets "the same item's **status cell or badge container** with `tabindex="-1"` and an accessible name carrying the item identity and the new state". A bare `div`/`td` container has the generic role, and ARIA prohibits an accessible name on `role="generic"` — `aria-label` there is ignored by conforming AT, so the identity-plus-state string the whole pattern turns on can be silently dropped, leaving the user focused on an unnamed cell. *Fix:* give the target a role that permits a name — `role="status"` is forbidden here, so use `role="group"` (or a visually-hidden text node inside the cell that is the name via `aria-labelledby`) — and make "focus target announces item identity and new state" an assertion in the AT matrix rather than an assumption.

### Route headings and the detail-route split

- **[high]** Nothing re-focuses the heading when a detail route changes state slot, and the previous heading element is destroyed. Verified in source: `FcAggregateDetailPage.razor` routes each non-ready state to a *separate* caller-supplied `RenderFragment`, so the domain's `FcPageHeader` in `LoadingContent` and the one in `ReadyContent` are two component instances with two `h1` elements and two `ElementReference`s. `EXPERIENCE.md:442` requires a header in every slot and `EXPERIENCE.md:444` moves focus to the heading "on navigation, when proposal detail opens from the queue, and after a forced refresh" — none of which is a state-slot swap. The ordinary cold load of all eight Constrained routes is exactly that swap: focus lands on the loading slot's `h1`, the read resolves, the slot is replaced, and focus is lost to `document.body` with no announcement. The same happens on Ready→`Unavailable` (a dependency drops) and Ready→`NotFound` (access is revoked mid-session). `FcPageHeader.FocusHeadingAsync()` also throws rather than no-ops when `HeadingTabIndex` is null, so a slot whose header omits it fails at the focus call, in production, on the error path. *Fix:* add the transition to the focus rule — when `FcAggregateDetailState` changes, focus moves to the newly rendered slot's heading and the polite node announces the new state (loading excepted) — and require `HeadingTabIndex="-1"` on the header in *every* slot, not just the ready one.

- **[medium]** Read literally, the rule puts two `h1`s and two `<PageTitle>`s on the Degraded state. `EXPERIENCE.md:442` says the domain renders `FcPageHeader` "as the first child of **every** state slot, so `not available`, loading, and degraded each keep an h1". But `Degraded` is not a slot: `FcAggregateDetailPage.razor` renders `DegradedBanner` *above the ready body*, which already contains the ready header. A developer following the sentence adds a header to the banner and ships a route with two `h1` elements and two competing `PageTitle` components on the degraded path. *Fix:* say it exactly — the domain renders `FcPageHeader` in `LoadingContent`, `UnauthorizedContent`, `NotFoundContent`, `UnavailableContent`, and `ReadyContent`; `StaleBanner`/`DegradedBanner` render above the ready body and carry no heading (and `Stale` is unused per `EXPERIENCE.md:391`).

- **[low]** Three loose ends around the detail-route chrome, each small alone. (a) The `not available` slot's `h1` string is unbound: `EXPERIENCE.md:140` gives exactly two keys, `…NotAvailable.Title` and `…NotAvailable.Message`, and the spine never says whether the `h1` is the route name or the Title — and `FcPageHeader` suppresses the `h1` entirely on a blank `Heading`, after which `FocusHeadingAsync()` throws. (b) `BackLinkLabel` is required (`EXPERIENCE.md:443`, correctly) but `BackHref` is not, and it defaults to `string.Empty` — a named link to the current URL, rendered by the wrapper *outside* the state slots so it is present and self-referential even on `not available`. (c) `FcPageHeader.HeadingId` plus `FrontComposerShell.ContentLabelledBy` is the shell's documented way to name the single `main` landmark by the route heading; the spine uses neither, so every Agents route ships an unnamed main landmark. *Fix:* bind the `not available` heading string, require a non-empty `BackHref` per detail route (the parent list), and set `HeadingId` with the shell's `ContentLabelledBy`.

- **[low]** Three Constrained routes are bound to no page component at all. `EXPERIENCE.md:501` splits the world into `FcAggregateListPage` (has heading parameters) and `FcAggregateDetailPage` (has none), but `DESIGN.md:120-135` binds Conversation context policy, Content safety, Cost controls, and Audit governance only to "Fluent form primitives inside `FluentAccordion`". Which component carries their `h1`, `PageTitle`, and focus target is unstated; the general "every route renders a non-blank localized heading" (`EXPERIENCE.md:442`) covers the obligation but not the mechanism. *Fix:* name `FcPageHeader` (or `FcAggregateDetailPage`) explicitly for those routes.

### Timing and WCAG 2.2.1

- **[medium]** The essential-exception argument as written is not a 2.2.1 argument, and it will be cited as one. `EXPERIENCE.md:468`: "proposal expiry is an essential governance limit … no in-UI extension … The warning that makes the limit workable is the nearing-expiry threshold … and its 15-minute floor **is required for the exception to hold**." That conflates two independent 2.2.1 allowances. The *warning* allowance (2.2.1 "Extend") requires at least 20 seconds' warning **and** the ability to extend the limit at least ten times — the spine explicitly has no extension, so the warning earns nothing under it. The *essential* exception requires no warning at all; a 15-minute floor neither strengthens nor is required by it. Two further weaknesses the sign-off should see rather than inherit: the window is tenant-configurable from 1 hour to 30 days (`EXPERIENCE.md:177`), which means it is adjustable by an administrator and *not* by the Approver who meets it, so the "Adjust" allowance is unavailable too; and the essential claim itself is unargued — the spine asserts it rather than saying why removing the limit would invalidate the activity (context staleness, policy-version pinning, reservation settlement). As the deferred item stands, Product is being asked to sign a conformance position stated on the wrong ground. *Fix:* rewrite the bullet as an essential-exception claim on its own merits (name why the limit is essential to governed approval), state that the 15-minute floor is a usability commitment and not a 2.2.1 mechanism, and record in the deferral that neither "Turn off", "Adjust", nor "Extend" is satisfied.

- The threshold arithmetic itself is sound and now buildable: `min(10% of window, 1 hour)` floored at 15 minutes, computed from `ExpiresAt` + configured window + server read time (`EXPERIENCE.md:336`), with the two missing contract fields owned by Stories 7.1/7.2 (`EXPERIENCE.md:619`), and `Expired` likewise compared against server time (`EXPERIENCE.md:334`). No browser clock survives anywhere in the expiry path. That part is closed.

### Status conveyed by more than colour

- **[medium]** The nearing-expiry chip is the one status in the system with no text. `DESIGN.md:283` says "nearing expiry adds a `{colors.status-warning}` chip" to `proposal-state-badge`, and `EXPERIENCE.md:336` says the flag "adds a `{colors.status-warning}` chip … and announces once per proposal". Neither states the chip's visible string, and no such string exists in the Voice and Tone table. `DESIGN.md:213` makes text mandatory ("Every status renders as a Fluent semantic role plus one glyph plus visible whole-string text and an accessible name"), so a chip with a colour and a `Warning16` glyph and no string breaks the spine's own no-colour-only rule at the one place a time limit is being communicated — and in forced-colors, where `DESIGN.md:211` says "icon plus text carry the meaning alone", a triangle alone is left carrying it. *Fix:* define the chip's whole string and its French form (e.g. `Expires in {duration}` / `Expire dans {duration}`, culture-formatted), and define the announcement string separately since the two have different phrasings.

- Otherwise this area is genuinely closed, and I checked it rather than took it: `FcFluentIcons.cs` exposes all thirteen 16 px entries as **methods** exactly as `DESIGN.md:172` claims, the seven role bindings at `DESIGN.md:217-225` all resolve, and the seven glyphs are visually distinct shapes (check-circle, sync-arrows, warning triangle, minus-circle, dismiss-circle, question-circle, info) so forced-colors degradation still separates them. `IconLabel` unset with a text-only accessible name (`DESIGN.md:213`) kills the "checkmark circle, Posted" double read. Contrast targets are stated at 4.5:1/3:1 across Light, Dark, and forced-colors with a per-route axe lane plus a three-AT manual matrix as evidence (`DESIGN.md:211`, `EXPERIENCE.md:469`) — an assumption about the pinned RC package, but one with a named re-verification trigger and a test lane behind it.

### Grids, filters, navigation glyphs, and the id-entry surface

- **[high]** `FcStatusFilterChips` is still mandatory on the Provider catalog, where its label contract can never be satisfied. `EXPERIENCE.md:203` keeps it in the mandatory set "where its label contract allows"; the Update exempted only the proposal queue (`EXPERIENCE.md:180`). In source, `FcStatusFilterChips.razor` renders `label = HumanizeSlotName(slot)` and `HumanizeSlotName(BadgeSlot slot) => slot.ToString()`, with the accessible name built as `StatusFilterChipAriaLabelTemplate(label, stateLabel)`. The label is *always* an unlocalized English enum name, for every slot, on every grid — the condition "where its label contract allows" describes an empty set. A developer who honours the mandate on the catalog ships readiness filters visibly reading `Success`, `Warning`, `Danger` on a French tenant (breaking the binding parity gate at `EXPERIENCE.md:159`/`EXPERIENCE.md:470`), announced as "Success, filter inactive" — a colour name where a readiness meaning belongs. *Fix:* extend the queue's disposition to both grids: `FcStatusFilterChips` is not used until the domain-keyed-slots-with-localized-labels request lands (already deferred to FrontComposer in `reconcile-validation-2026-09-09.md § 4`); until then both grids render filters as Agents-owned `aria-pressed` toggles inside a named `role="group"`. Then delete "where its label contract allows", which currently reads as permission.

- **[medium]** "Renders without a glyph" is not reachable through the registration contract; the shell substitutes Overview's glyph. `DESIGN.md:193`: "Until a request lands, the nav entry keeps the glyph listed under 'Glyph today' or renders without a glyph; it never reuses another entry's glyph." In source, `FrontComposerNavigation.ResolveNavEntryIcon(string? iconKey, bool filled)` returns `FcFluentIcons.Apps20(...)` whenever `TryCreate` fails — including for a null key. `Apps20` is the Overview entry's own glyph (`DESIGN.md:180`). So the six entries listed with "Glyph today: none" (Conversation context policy, Content safety, Cost controls, Launch readiness, Audit evidence, Audit governance) all render Overview's glyph, and in the icon-only rail — where `FrontComposerNavigation.razor:98,198` supplies the localized manifest name as `aria-label` — seven Agents tiles are visually identical and distinguishable only to AT and to whoever hovers. The spine's assertion is false against the shell it inherits, and it is the assertion that was supposed to prevent glyph reuse. *Fix:* state the truth (an unset key renders `Apps20`, which duplicates Overview) and decide: either accept the duplication with the six glyph requests raised, or hold those entries out of the icon-only rail, or request a null-icon path from FrontComposer. Do not leave a rule the shell silently contradicts.

- **[medium]** The audit-evidence id-entry surface has no accessibility contract at all. `EXPERIENCE.md:72` and `DESIGN.md:241` declare `/agents/audit` "an id-entry surface, not a grid: it accepts an interaction, proposal, or governance-operation reference and routes to the detail, so it declares no list contract, columns, filters, or sort and the mandatory FC-TBL set does not apply". Removing it from FC-TBL also removed its state contract, and nothing replaced it: the input's visible label, which of the three reference kinds it accepts and how the user is told, whether an unrecognised or unauthorized reference renders `not available` inline or navigates, and — if inline — which node announces it, since no such event is in the politeness table. ## What is genuinely closed

Named as closed because it is, not to soften the above.

- The icon contract. Two access paths, twelve `TryCreate` names, thirteen 16 px factory **methods**, `DevMode`/`DeveloperBoard` as one glyph — all verified line-for-line against `FcFluentIcons.cs`. All seven status roles bind to shipped factories, so no status badge ships text-only waiting on a request, and the seven glyphs stay distinguishable in forced-colors.
- The silencing mechanism is real: `FluentMessageBar.AriaLive` accepts `Off`, `Polite`, `Assertive` at the pin, and `Animation` is null by default.
- Shell ownership of connection loss is real: `FcProjectionConnectionStatus` is rendered inside `FrontComposerShell.razor:149`, not by the domain, so Agents can defer to it without a placement rule.
- `FcPageHeader` is a genuine focus contract: it renders a real `h1`, suppresses a blank heading rather than shipping an empty one, emits `role="presentation"` so it never competes with the shell's single banner, and `FocusHeadingAsync()` throws rather than silently no-oping when `HeadingTabIndex` is missing.
- "A confirmation is never opened by a selection event", generalised from the response-mode defect, closes the whole arrow-key-opens-a-modal class in one sentence.
- The dialog contract now names every behaviour Fluent does not provide, including the custom-action-button caveat that breaks default `Esc`, and keeps Confirm reachable at 320 px with a full proposal version in the body.
- Reflow at 320 px / 400% is a positive obligation on every route including the confirmation, with evidence in the launch lane; target size across three densities, focus-not-obscured, no drag-only path, 3.2.6/3.3.8 N/A, and RTL logical properties are all stated as testable rules.
- Localization mechanics are enforceable where keys exist: exact-parity test, per-count plural keys, `CultureInfo` placeholders, a localized label for every architecture token, and the ban on reusing `FcDestructiveConfirmationDialog` with its hard-coded `Cancel`.
- The queue's polled-focus contract (`ItemKey`, deferred re-sort, announced explicit refresh) and the aggregated expiry announcement together fix both halves of the burst-and-steal problem.
- The accordion rule matches the binding UX law: the primary region stays outside the accordion on all four surface families, titles are h2 and in-panel sections h3, and no primary content hides behind a disclosure.
