# Accessibility Review — Hexalith Agents

Reviewer lens: accessibility (WCAG 2.2 AA binding; whole-string EN/FR parity binding). Run: 2026-09-09 against the final spines updated 2026-09-08. Inputs: `DESIGN.md`, `EXPERIENCE.md`, `.memlog.md`, `reconcile-validation-2026-09-08.md`, the archived pre-update review, FrontComposer `project-context.md`, `front-composer-shell.md`, `navigation.md`, `datagrid.md`, `settings.md`, `page-toolbar.md`, `accessibility-verification/README.md`, and FrontComposer Shell source (`FcAggregateListPage`, `FcAggregateDetailPage`, `FcPageHeader`, `FcStatusFilterChips`, `FcExpandInRowDetail`, `FcStatusIcon`, `FrontComposerNavigation`, `BadgeSlot`), plus Fluent UI Blazor v5 component references for `FluentDialog`, `FluentButton`, `FluentRadioGroup`, `FluentDataGrid`, `FluentBadge`, `FluentMessageBar`, `FluentAccordion`, `FluentNumberInput`, `FluentTextArea`.

## Overall verdict

The update did the hard part: both prior criticals are gone, the live regions, route heading, forms, contrast, French, and 2.2.1 position now exist as written rules, and most of the Accessibility Floor could be turned into assertions. What remains is a layer of delegation that the referenced docs do not actually back: `FcAggregateDetailPage` has no `Heading`, `HeadingTabIndex`, or `PageTitle` parameter, so the route-heading rule is unimplementable as written on every Constrained detail route; `FcStatusFilterChips` accepts only the closed `BadgeSlot` enum and renders `slot.ToString()` as the visible label, so the mandatory `needs my action` chip would read `Info` or `Accent` in English on a French tenant; the shell's nav badge is an unlabeled number and the shell's own `role="status"` nodes ship inside every Agents grid page, so "one status node per route" is false on day one. None of these blocks a keyboard user from finishing UJ-3, but a screen-reader user in UJ-2 still has no one who owns the announcement that the call was denied or posted, because the seam surface is not an Agents route. No critical findings; five high.

## Findings

- **[high]** The route-heading rule cannot be implemented on Constrained detail routes as written. `EXPERIENCE.md:345` requires every route to render `FcAggregateListPage` *or* `FcAggregateDetailPage` "with a non-blank localized `Heading`, `HeadingTabIndex=-1`, and `PageTitle`", and `FcAggregateDetailPage` is the binding for `agent-config-form` (`DESIGN.md:81`). `FcAggregateDetailPage` has none of those parameters; it only composes `FcPageLayout`, a stack, a back link, and state-routed slots, and "the consuming domain supplies all headers". Worse, its `Loading`, `Unauthorized`, `NotFound`, and `Unavailable` slots render caller content in place of the ready body, so if the domain puts `FcPageHeader` inside `ReadyContent`, the `not available` state (`EXPERIENCE.md:308`) and the loading state have no `h1`, no `PageTitle`, and no focus target after navigation (WCAG 2.4.2, 2.4.3). Eight of the twelve routes are Constrained (`DESIGN.md:236`). *Fix:* state that on detail routes the domain renders `FcPageHeader` (`Heading`, `HeadingTabIndex=-1`, `PageTitle`) *above* `FcAggregateDetailPage` or as the first child of every state slot, so the heading exists and is focused in every `FcAggregateDetailState`; add "heading present and focused in the `not available` state" to the conformance lane.

- **[high]** The mandatory `needs my action` filter chip is not expressible with `FcStatusFilterChips`, and what it would render is misleading in both languages. `EXPERIENCE.md:155` makes `needs my action` an `FcStatusFilterChips` slot and `EXPERIENCE.md:154` makes the component mandatory for every grid. `FcStatusFilterChips.AvailableSlots` is typed on the closed `BadgeSlot` enum (`Neutral, Info, Success, Warning, Danger, Accent`), and the visible chip text is `HumanizeSlotName(slot) => slot.ToString()`, i.e. the raw English enum name; only the pressed/unpressed suffix is localized. A screen-reader user discovering proposals in UJ-3 step 2 would hear "Accent, filter inactive" for the chip that means "needs my action", and a French tenant would see an untranslated English word, which violates the whole-string parity gate (`EXPERIENCE.md:134`, `EXPERIENCE.md:367`). *Fix:* either raise a FrontComposer request for domain-keyed slots with a localized label (`ViewKey`-scoped `FcStatusFilterChips` accepting `(key, localizedLabel, color)`), and until it lands render the state and `needs my action` filters as Agents-owned `aria-pressed` toggle buttons in a `role="group"` named by `AgentsResources`; or drop `FcStatusFilterChips` from the mandatory list. Do not leave a rule that a developer can satisfy only by shipping `Info`.

- **[high]** "One `role="status"` node per route" is false the moment a mandatory Fc component renders, and the duplication is unmanaged. `EXPERIENCE.md:336` gives Agents one polite `role="status"` and one `role="alert"` per route and says shell live regions "cover shell-owned surfaces only". But the same spine makes `FcFilterEmptyState` and `FcExpandInRowDetail` mandatory on every grid (`EXPERIENCE.md:154`), and both render their own `role="status" aria-live="polite"` nodes inside the Agents page (`FcFilterEmptyState.razor:7`, `FcExpandInRowDetail.razor:23-24`), as do `FcSlowQueryNotice`, `FcMaxItemsCapNotice`, and `FcAggregateDetailPage` stale/degraded banners if built on `FluentMessageBar`. `FluentMessageBar` itself carries an `AriaLive` parameter whose default is intent-driven, so the page-level notices `DESIGN.md:221` allows (`Error` for `posting failed`, `Warning` for `connection lost`) will announce once from the bar and again from the Agents alert node. The shell's `FcProjectionConnectionStatus` already announces connection loss politely; Agents adds an assertive `connection lost` alert (`EXPERIENCE.md:340`). At the approval moment a JAWS user can receive `Approved. Posting is pending.` from the status node while a Success bar says the same thing. NFR-14 measures "the localized mutation in the Agents node", so a duplicate announcement from another node also muddies the evidence. *Fix:* replace "one node per route" with "one *Agents-owned* node of each politeness per route, and every event is announced by exactly one node": page-level `FluentMessageBar`s render with `AriaLive="Off"` when their text is also pushed to the Agents node; `connection lost` is announced by the shell's node only and the Agents alert carries the *consequence* (`Approve is unavailable until the connection returns`) or nothing; list which Fc status nodes are allowed to speak (filter-empty, hidden-expanded-row) and which are silenced.

- **[high]** Nobody owns announcements or post-submit focus on the Conversation seam, so UJ-2 and UX-J6 have no screen-reader path. The live-region rule is per Agents *route* (`EXPERIENCE.md:336`), but **Call hexa**, `submitted`, `authoritative pending`, `denied`, `capacity queued`, `capacity rejected`, `generation failed`, and `Posted` all happen on a Conversation-owned surface with no Agents route (`EXPERIENCE.md:63`, `EXPERIENCE.md:87`). The exported `ConversationAgentCallPanel` (`EXPERIENCE.md:81`) is not told to carry its own status/alert nodes, and `EXT-CONV-UI-1` is uncommitted so nothing can be assumed from Conversations. The dialog itself (`DESIGN.md:307`) says nothing about what happens after Submit: does it close, where does focus land (the now-`aria-disabled` **Call hexa** button? the Conversation composer?), and where do the `FluentBadge` status rows render relative to focus. A blind participant in UJ-2 presses Submit and hears nothing until they hunt for a badge row. *Fix:* make `ConversationAgentCallPanel` self-contained for 4.1.3: it owns one polite and one assertive node (the same politeness table applies), announces `submitted` and `authoritative pending` politely, `denied`/`generation failed`/`capacity rejected` assertively, and `Posted` politely; on Submit the dialog closes and focus returns to **Call hexa** (which is `aria-disabled` while the call is pending in this session); the status rows sit immediately after the button in DOM order. Record the same as an `EXT-CONV-UI-1` requirement so Conversations cannot strip the nodes.

- **[high]** `response-mode-toggle` fires the confirmation on `change`, which in a `FluentRadioGroup` means on the first arrow key. `EXPERIENCE.md:151` binds "change opens `high-impact-confirmation`" and `DESIGN.md:279` makes it a two-option radio group. Native radio semantics (and Fluent's wrapper) move selection with Arrow keys, so a keyboard user who presses Down to *read* the second option has already changed the value and is now in a modal dialog with Cancel focused; on Cancel the spine does not say the radio reverts, so the visible selection and the persisted mode can disagree until the page reloads. Screen-reader users exploring the group get the same trap, and there is no way to hear the helper text of the unselected option without triggering it. This is the only control for a change the spine treats as high-risk (`AgentSetupMutation`). *Fix:* the radio group changes a *draft* value only; the confirmation opens from an explicit `Apply response mode` button (or the form's Save) that is `aria-disabled` until the draft differs; on Cancel the draft reverts to the persisted value and the status node announces `Response mode unchanged: {mode}`. Apply the same rule to every "change opens confirmation" binding.

- **[medium]** The nearing-expiry threshold is a decision without a spine. `proposal-state-badge` takes a "nearing-expiry flag" (`EXPERIENCE.md:150`), the warning colour role names it (`DESIGN.md:197`, `DESIGN.md:275`), and the status node announces it once per proposal (`EXPERIENCE.md:341`), but neither spine says when the flag turns on. The 10 % of window or 1 hour, whichever is smaller, rule exists only in `.memlog.md:34` and `reconcile-validation-2026-09-08.md:64`, which the spine header says are not the spec. With a 1-hour window that is a 6-minute warning for a governed approval; with 30 days it is 1 hour. A developer following the spine alone will invent a threshold, and the announcement timing that WCAG 2.2.1's essential-exception argument depends on is unstated. *Fix:* put the threshold sentence in `proposal-queue-grid` and `proposal-state-badge` (`EXPERIENCE.md` Component Patterns) and in the Timing bullet (`EXPERIENCE.md:365`), and state the floor explicitly (never less than N minutes) so the 1-hour configuration does not produce a warning too short to act on.

- **[medium]** Expiry and warning announcements do not scale on the queue. `expired` is an alert and `expiry warning (once per proposal)` is a status event (`EXPERIENCE.md:340-341`); `Expired` is derived on any read whenever `ExpiresAt` has passed (`EXPERIENCE.md:261`); the queue polls and holds 25 rows sorted nearest-expiry-first (`EXPERIENCE.md:155`). An Approver sitting on the queue at the top of the hour can receive a burst of assertive `This proposal expired at …` alerts and up to 25 polite warnings, each interrupting the row they are reading. *Fix:* scope per-proposal alerts to proposal detail (the proposal in view); on the queue announce an aggregate, at most once per poll cycle, in the status node (`{count} proposals expired since your last refresh`, `{count} proposals nearing expiry`), never as `role="alert"` unless the focused row is the one that expired.

- **[medium]** The `IBadgeCountService` count still renders as a bare number beside the Agents tile, and the spine keeps the label rule conditional. `FrontComposerNavigation.razor` emits `<FluentBadge …>@aggregateCount</FluentBadge>` with no label and the tile's `aria-label` is the manifest name only in icon-only mode (`FrontComposerNavigation.razor:98,128-130,166-168`); `navigation.md` confirms badge labels are shell-owned. The spine's "if the shell exposes no label slot, the count renders inside the Agents overview link instead" (`EXPERIENCE.md:165`, `DESIGN.md:335`) is therefore the actual V1 behaviour, and a screen-reader user still hears "Agents, 3" on the rail with no idea what the 3 is, then finds the real label somewhere on the overview. *Fix:* state the fallback as the V1 rule, not a conditional; say whether Agents suppresses the shell count for its manifest until the localizable label lands (to avoid the unexplained "3"), and keep the FrontComposer request as the deferred item it already is.

- **[medium]** The deterministic focus rule points at a "status region" that is also the name of the live region. `EXPERIENCE.md:289` says focus moves to "the same item's status region"; `EXPERIENCE.md:169` and `DESIGN.md:351` use "the item's status region" for the adjacent `FluentBadge` of `pending-command-indicator`; `EXPERIENCE.md:336` uses "status" for the page-level `role="status"` node. A developer can reasonably focus the live-region `div`, which is the one element that must never receive focus (it would be read twice and lose its polite queue). The rule also does not require the target to be focusable. *Fix:* name the target: the item's status *cell* or badge container with `tabindex="-1"` and an accessible name that includes the item identity and new state (`Proposal {id}: Approved. Posting is pending.`); state that the page-level `role="status"` and `role="alert"` nodes never receive focus and are visually hidden or outside the reading order of the item.

- **[medium]** "Polled re-renders never steal focus" is a promise without a mechanism, and the default sort works against it. The queue sorts nearest-`ExpiresAt`-first within `needs my action` (`EXPERIENCE.md:155`) and polls; `FluentDataGrid` keeps a focused cell only when rows are keyed (`ItemKey`) and does nothing to stop a focused row from moving to page 2 or off the current filter (`FcExpandedRowHiddenBanner` exists for the expanded row, not the focused one). A keyboard user arrowing through cells can have the row under them re-sorted away, which is focus loss by another name. *Fix:* bind `ItemKey` to `AgentInteractionId` on both grids; while focus is inside the grid body, defer re-sort and page shifts and render new/changed rows in place with a `{count} proposals changed. Refresh list` status message plus an explicit refresh action; re-sort only on refresh or when focus leaves the grid.

- **[medium]** Selecting another version while the editor is dirty is unspecified, and the radio group makes it a one-keystroke event. Version selection is a `FluentRadioGroup` (`EXPERIENCE.md:157`, `DESIGN.md:303`) whose value changes on Arrow keys; the editor holds "the selected version" (`DESIGN.md:299`); Approval is `aria-disabled` while dirty (`EXPERIENCE.md:156`); `Esc` never discards editor content (`EXPERIENCE.md:327`). Nothing says what an Arrow key in the version list does to unsaved edits: overwrite (data loss with no confirmation), block (radio appears broken), or preserve (which version is the textarea showing). Also, a version change updates the textarea silently; a screen-reader user who selects "Version 2" hears nothing about which content is now in the editor. *Fix:* while dirty, the version radios are `aria-disabled` with the reason (`Save or discard your edit to view another version`), or the change opens the unsaved-changes confirmation; on a successful version change the textarea's accessible name is the version identity (`Version 2, generated by {provider}, {timestamp}`) via `aria-labelledby`, and the status node announces `Showing version {n}`.

- **[medium]** `high-impact-confirmation` relies on dialog behaviours Fluent v5 does not document. The spine requires initial focus on the non-committing action, focus return to the trigger, `Esc` cancel, and Enter-on-body-never-commits (`EXPERIENCE.md:168`, `DESIGN.md:347`). The Fluent reference documents modal inertness and `PreventDismissOnEscape`, but no initial-focus placement and no focus restoration; it also warns that with custom `ActionTemplate` buttons "the default shortcuts Enter and Escape will no longer work", so `Esc` handling must be verified per pattern. For proposal approval the body renders the *full content* of the selected version (`EXPERIENCE.md:168`); at 320 px / 400 % zoom that is a long scrolling dialog where Confirm and Cancel can be below the fold unless `FluentDialogBody FixedHeaderFooter="true"` is used, and the scrolling content region must itself be keyboard-scrollable (2.1.1). *Fix:* state the domain implements initial focus (`AutoFocus` on Cancel) and focus restoration explicitly; require `FixedHeaderFooter="true"` with a focusable (`tabindex="0"`, named) scroll region for the content; add "Esc cancels with custom action buttons" and "Confirm reachable at 320 px with full content" to the conformance lane.

- **[low]** The `aria-disabled` pending control is specified as an attribute, not as the Fluent binding that produces it. `FluentButton` in v5 exposes `DisabledFocusable="true"` for exactly this (disabled yet keyboard-reachable) and `Loading="true"` which *removes* focusability. A developer who reaches for `Loading` to show the spinner reintroduces the prior critical. *Fix:* bind `pending-command-indicator` to `FluentButton DisabledFocusable="true"` and forbid `Loading`/`Disabled` on the activated control (`DESIGN.md:351`, `EXPERIENCE.md:169`).

- **[low]** Forms state error association but not error content or timing (3.3.1, 3.3.3). `EXPERIENCE.md:349-354` covers `aria-describedby`, `aria-invalid`, and the summary, but not that each error is a whole string naming the field, the fault, and the fix; not that required fields carry a visible required indicator; and not whether validation runs on submit or on blur (on-input `MessageState` changes inside `FluentField` can become noisy live text). *Fix:* add three sentences: error text = field + fault + fix as one localized string; required fields show a visible marker described in the label; validation on submit, with per-field re-validation on blur only after first submit.

- **[low]** Status badges will be read twice if the icon also carries a label. Every status renders "role plus one glyph plus visible whole-string text and an accessible name" (`DESIGN.md:207`); `FluentBadge.IconLabel` sets `aria-label` on the icon, so `checkmark circle, Posted` is the likely output. *Fix:* when visible text is present the glyph is decorative (`IconLabel` unset / `aria-hidden`); the accessible name is the text.

- **[low]** The proposal queue at 320 px has six pinned columns and no stated minimum. `DESIGN.md:295` pins six columns; `EXPERIENCE.md:385` says grids use `FcExpandInRowDetail` for secondary columns but not which columns survive. WCAG 1.4.10 allows contained two-dimensional scrolling for data tables, but the spine should claim it. *Fix:* name the 320 px column set (state, expiry, open action) and state that the grid scrolls horizontally inside its own container, never the page.

- **[low]** `Esc` in the **Call hexa** dialog discards a typed prompt. "Esc closes transient UI without committing and never discards editor content" (`EXPERIENCE.md:327`) protects the proposal editor, not the required prompt `FluentTextArea` (`DESIGN.md:307`). *Fix:* extend the rule to any non-empty text input inside a dialog (confirm before discarding, or keep the draft per session).

- **[low]** `FcAggregateDetailPage.ShowBackLink` defaults to `true` with a nullable `BackLinkLabel`; an unset label yields an anchor with no accessible name (HFC1050 does not fire on framework components). *Fix:* require a localized `BackLinkLabel` (`Back to Proposal queue`) or `ShowBackLink="false"` on every detail route.

- **[low]** Generated and Conversation-derived text has no language-of-parts rule (3.1.2). The editor textarea, preview, and audit evidence show text whose language is the Conversation's, not the UI culture; nothing sets `lang` on those regions. *Fix:* the proposal-editor content region and evidence content carry `lang` from the Provider result or Conversation language when known; otherwise inherit.

- **[low]** Regeneration is a chargeable call but not in the nine high-risk families, so it has no `pending-command-indicator` and no double-activation guard (`EXPERIENCE.md:156`, `EXPERIENCE.md:284`). A keyboard user pressing Enter twice on Regenerate can queue two chargeable generations. *Fix:* apply `DisabledFocusable` plus a local pending badge to Regenerate while a regeneration is in flight, without adding it to the confirmation families.

- **[low]** "If type-to-confirm is used for deletion, the WCAG 3.3.7 security exception is recorded" (`EXPERIENCE.md:168`) is a conditional with no decision. *Fix:* decide (recommended: no type-to-confirm; the `DeletionRequest` confirmation names the scope and count) and delete the "if".

- **[low]** Pointer cancellation (2.5.2) and motion are inherited without being claimed. Fluent buttons activate on `click`, and `FluentMessageBar` animation is opt-in, so both pass by default; the floor should say "no custom `pointerdown`/`mousedown` activation; no `MessageBarAnimation`" so a developer cannot drift.

## What is solid

- The pending control keeps focus and the announcement set covers the states the user actually waits in (`authoritative pending`, `approved`, `posting pending`, `posted`, `regenerated`), with a deterministic fallback order when the trigger disappears (`EXPERIENCE.md:288-289`, `EXPERIENCE.md:341`).
- Reflow is now a positive obligation on every route, including the confirmation dialog and version history, with evidence at 320 px required for launch (`EXPERIENCE.md:358`, `EXPERIENCE.md:385`, `EXPERIENCE.md:390`).
- Every status is role + glyph + visible whole-string text + accessible name; `Filled` is explicitly not a meaning carrier; forced-colors is handled by icon + text (`DESIGN.md:205-207`).
- The Forms subsection is assertable: visible label, `aria-describedby`/`aria-invalid`, focused error summary linked to the first error, units and currency in labels, secret fields named by configured state, policy rows named by kind and basis (`EXPERIENCE.md:349-354`).
- Localization mechanics are enforceable: exact-parity test, per-count plural keys, `CultureInfo` placeholders, localized labels for every architecture token, and a ban on shell dialogs with hard-coded literals (`EXPERIENCE.md:130-140`).
- `FcAggregateListPage` genuinely provides `Heading`, `HeadingTabIndex`, `PageTitle`, and `FocusHeadingAsync`, so the route-heading rule is real on all FullWidth grid routes.
- `FluentButton.DisabledFocusable`, `FluentRadioGroup` labelling, `FluentMessageBar.AriaLive`, `FluentDataGrid` keyboard navigation and `ResizeType`, and `FluentDialogBody.FixedHeaderFooter` exist in the pinned v5 line, so every fix above is a binding decision, not a component request.
- 2.4.11, 2.5.7, 2.5.8 across densities, 3.2.6/3.3.8 N/A, RTL logical properties, hover-revealed actions on focus-within, and reduced motion never hiding state changes are all stated as testable rules.
- The 2.2.1 position is written down with an owner rather than left implicit, and the expiry label is kept out of live regions and refreshed no more than once a minute.
