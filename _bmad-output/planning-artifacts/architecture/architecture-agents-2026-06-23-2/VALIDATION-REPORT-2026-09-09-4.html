Security

C-6 — The versioned DigestKey model never binds a stored digest to the key version that produced it

The round-4 fix made DigestKey rotation genuinely usable (versioned, retained indefinitely, unrestricted and content-free). But no record carrying a sensitive-content digest carries the DigestKeyVersion it was computed under — HMAC-SHA-256 is one-way, so nothing can tell which retained version to recompute against after a rotation.

Idempotency false-conflict: a retried command after a rotation recomputes against the current key, producing a different fingerprint than the original — a legitimate retry is misclassified as a conflict. Audit-evidence unverifiability (the more serious component): a reviewer reconstructing an inspection years later, after content is legitimately erased, has no way to know which key version to recompute against without brute-forcing every version — quietly breaking the tamper-evidence guarantee the digest scheme exists to provide.

This is a direct, foreseeable consequence of the round-4 fix, not a leftover of the bug it replaced.

Fix: tag every persisted digest with the DigestKeyVersion used to compute it, alongside the digest value.
