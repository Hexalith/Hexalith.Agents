# Security / Data-Integrity Review (v8) — Hexalith Agents Architecture Spine

**Verdict:** The three claimed fixes from earlier today (legal-hold/deletion symmetry in the register, the redesigned `DigestKey` rotation model, and the HMAC-SHA-256 fingerprint/digest specification) were each re-derived independently against the live text rather than trusted. Two hold up. The `DigestKey` rotation redesign solves the problem it was built to solve (rotation is no longer practically blocked for an active tenant) but does so by introducing a new, unaddressed gap: nothing in the spine ties a stored digest to the specific `DigestKey` version it was computed under, so nothing can deterministically re-verify or re-match that digest once rotation has occurred. That undermines both idempotency correctness and — more seriously given this system's stakes — the verifiability of the compliance audit trail the digest scheme exists to protect. This is a new Critical finding, not a residual echo of the v7 finding it replaces.

## Re-verification of the three claimed fixes

### 1. AD-22/ARCH-A-10 legal-hold / deletion symmetry — VERIFIED, HOLDS

Re-read live: `launch-readiness-register.md` line 108 (`LR-AUDIT-PROTECTION-DELETION` row) states evidence is required that "a `LegalHold` **or a `DeletionRequest`** either propagates to (or has a confirmed accepted-risk waiver for) the posted copy of held **or erased** content in Conversations." `ARCHITECTURE-SPINE.md` AD-22 (line 261) and `ARCH-A-10` (line 784) both name `LegalHold` and `DeletionRequest` together as the same class of named residual risk, gated the same way. This is genuinely symmetric in the live text, not just asserted to be. The underlying gap itself (Agents cannot purge or preserve a posted Conversation Message; AD-6 forbids writing to Conversations streams) remains open, but it is an explicitly disclosed, tracked, waiver-able residual risk in both directions, not a silent asymmetry. **No finding.**

Separately re-checked: hold-vs-deletion is internally symmetric within Agents' own state. `ApplyHold` pins DEKs before becoming `Active`; erasure "reads the interaction's own pinned-hold set at its expected revision"; "a class-scoped deletion enumerates the in-range interactions and is rejected in full if any is pinned." So a pinned interaction cannot be erased, and (per the two-phase apply) a hold cannot silently no-op against an interaction already scheduled for erasure — the checkpoint-and-pin-confirmation design means an erasure that has already destroyed a DEK leaves nothing for a later hold to pin, which would surface as a pin failure/incomplete-hold state rather than a falsely `Active` hold over already-erased content, consistent with "becoming `Active` only when every pin is confirmed." No exploitable ordering gap found here.

### 2. Fingerprint/digest algorithm specification (HMAC-SHA-256 under per-tenant `DigestKey`) — VERIFIED CONSISTENT

Checked every place the spine names an algorithm for a sensitive-content digest: AD-13's Provider-attempt fingerprint (line 201: "computed as HMAC-SHA-256 under the per-tenant `DigestKey`... never the identity canonicalizer's unkeyed SHA-256"), AD-29's command-payload fingerprint (line 303: same), AD-29's closing blanket rule (line 303: "Every digest of sensitive content stored outside a `ProtectedContent` envelope... is an HMAC-SHA-256 under a per-tenant `DigestKey`... unkeyed SHA-256 is used only for identities derived from identifiers"), and the Consistency Conventions table row (line 476: same). All four are consistent with each other, and the algorithm is now stated concretely (not hand-waved as "a digest" or "a hash"). The export manifest's "SHA-256 of exported bytes" (AD-22, line 261) is correctly *unkeyed* SHA-256, and correctly so: it hashes already-encrypted export bytes for transport-integrity checking, not plaintext sensitive content, so it falls outside AD-29's "identities derived from identifiers" carve-out is not even needed — it's a different class of hash (ciphertext checksum) that AD-29 doesn't purport to govern. No inconsistency found. **No finding on algorithm choice or its consistency.**

However, see Critical Finding 1 below: while the *algorithm* is now fully specified, the *key-version binding* needed to make that algorithm's output usable across a rotation is not.

### 3. `DigestKey` rotation model (AD-22/ARCH-A-12) — NEW GAP (Critical, see Finding 1)

The v7-flagged problem (rotation practically impossible for any operationally active tenant, because the only non-waiver path required zero unerased protected content) is genuinely gone: AD-22 (line 261) now states the key is "versioned, not singular," `EXT-SECRETS-1` "custodies every issued version indefinitely," and "rotation mints a new current version for future digests without invalidating or requiring recomputation of any digest already recorded under an earlier version." `ARCH-A-12` (line 786) confirms rotation is now "unrestricted and content-free." Rotation is no longer gated on erasure state, so the specific unsatisfiability bug from v7 is fixed. But the redesign has a hole — detailed below.

## Critical

### Finding 1 — The versioned `DigestKey` model never states that a stored digest carries the key version it was computed under, so nothing can deterministically know which of the (now multiple, all-retained) key versions to use when re-matching or re-verifying that digest after a rotation

**Quoted text (AD-22, line 261):**

> The per-tenant `DigestKey` that keys every sensitive-content digest under AD-29 is versioned, not singular: `EXT-SECRETS-1` custodies every issued version indefinitely, never destroying one while any digest recorded under it survives in an unpurged EventStore stream, and rotation mints a new current version for future digests without invalidating or requiring recomputation of any digest already recorded under an earlier version... A short-lived digest... is never compared across a rotation boundary and so carries no rotation risk; a long-lived digest embedded in an immutable audit or idempotency record keeps its originating version's comparability forever, since that version is never destroyed while the record survives.

**What is missing:** the rule asserts a long-lived digest "keeps its originating version's comparability forever" — but comparability requires knowing *which* version to recompute against. HMAC-SHA-256 is one-way: given only the stored digest and the plaintext it was computed from, you cannot tell which of N retained `DigestKey` versions produced it without trying each one. Nowhere does AD-29 (the identity/digest derivation authority), AD-22, or AD-13 add a `DigestKeyVersion` field to the records that carry these digests — not to the `ProviderAttempt` descriptor, not to the AD-29 idempotency record, not to an `AuditEvidence`/`audit-evidence` entry, not to the per-message digests embedded in the AD-13 fingerprint. "Rotation mints a new current version for future digests" tells you what key *new* writes use; it never tells a later reader which key an *existing* stored digest used.

**Concrete failure scenario A — idempotency false-conflict (High-severity component):** AD-29's API command idempotency is "authoritative across sessions, tabs, retries, replay, and restarts," keyed by (tenant, principal, operation family, client key) plus a payload fingerprint that is itself an HMAC-SHA-256 under the per-tenant `DigestKey` (AD-29, line 303). A client submits a lock-bearing command (e.g. `ExportRequest`), the client crashes before receiving the response, and resubmits the byte-identical command after the Platform Operator has since rotated that tenant's `DigestKey` (now unrestricted and content-free per the very fix this round validates — rotation can happen at any time, including between the two submissions). The retry recomputes the fingerprint "from the shared canonicalizer" — nothing in the text says to use the *original* key version rather than *current* — producing a different HMAC output for byte-identical payload content. AD-29's own rule: "the same tuple with a different fingerprint is a conflict." The legitimate idempotent retry is now misclassified as a 409 conflict against its own earlier self, purely because the key rotated, not because the payload changed. This is "fail closed" rather than a duplicate side effect, so it is not a security breach on its own, but it is a concrete correctness/availability regression that the "unrestricted, content-free" rotation promise (ARCH-A-12) directly enables and does not guard against.

**Concrete failure scenario B — audit-evidence unverifiability (the Critical component, given this system's stakes):** the entire reason AD-22 stores digests instead of content in `audit-evidence`, per-message fingerprints, and idempotency records is so that, after content is legitimately erased (365-day retention expiry, or a `DeletionRequest`), the *fact* that specific content once existed and matched a specific description remains independently verifiable without retaining the content itself — this is explicitly the design AD-22 describes as evidence that "survives loss of the Source Conversation and erasure of the inspected interaction." A Compliance Inspector, an external auditor, or a legal-hold review reconstructing an inspection years later needs to recompute a digest from surviving reference material and confirm it matches the stored one. If the tenant's `DigestKey` has rotated one or more times since that digest was recorded — which, given rotation is now unrestricted and can happen for any operational reason (routine hygiene, suspected compromise, personnel change) — the verifier has no way, from the spine's own rules, to know which of the "every issued version" retained keys to use. The only way to "verify" would be to brute-force every retained version, which (a) is never specified as the procedure, (b) degrades linearly and unboundedly as rotations accumulate over a multi-year retention/legal-hold horizon, and (c) is not distinguishable from "digest does not match, evidence may be tampered" without exhausting every version — turning a designed-to-be-cheap tamper-evidence check into an unspecified, unbounded, and here undocumented procedure. For a system whose explicit design goal is that this evidence "survives... erasure" and is trustworthy for legal-hold and compliance purposes, silently losing the ability to deterministically re-verify it after a routine, now-encouraged key rotation is a materially worse gap than the "rotation is blocked" problem it replaces — that problem was inconvenient; this one is a quiet integrity hole in the audit trail itself.

**Why this is a new finding, not the same one restated:** v7's finding was that rotation was *practically impossible*. That specific claim is now false — re-derivation confirms rotation genuinely works as an operation. The new problem only exists *because* rotation now genuinely happens: it is a direct, foreseeable consequence of the fix, not a leftover of the old bug, and the spine text nowhere acknowledges or resolves it.

**Fix:** Tag every persisted digest (idempotency fingerprint, `ProviderAttempt` fingerprint retained past its attempt, per-message digest inside `audit-evidence`, verdict-cache key if it is ever retained past invalidation) with the `DigestKeyVersion` used to compute it, alongside the digest value, in the same event/record. Re-verification and idempotency-conflict comparison then look up the recorded version and recompute against that specific version rather than "current." This is a small, additive schema change (one more field) consistent with the versioned-key model already adopted, and it is the missing piece that actually makes "keeps its originating version's comparability forever" true rather than merely asserted.

## Low

### Finding 2 — AD-22's stated reason for exempting `DigestKey` rotation from the AD-12 lock-bearing-family session lock is factually inconsistent with the same sentence's own premise

**Quoted text (AD-22, line 261):**

> Rotation is Platform Operator-initiated, audited, and content-free... and is not one of AD-12's nine lock-bearing families, **since it targets no tenant-scoped resource requiring a session lock**.

But the same rule opens by calling this "**the per-tenant** `DigestKey`" — it is explicitly a tenant-scoped resource (one key lineage per tenant), which is exactly why AD-29 calls it "a per-tenant `DigestKey`" throughout. The stated justification for the lock exemption is self-contradictory on its face: the resource being rotated is tenant-scoped, so "targets no tenant-scoped resource" is not the reason it's safe to exempt from locking. The actual reason it's safe (rotation is purely additive/append-a-new-version, so two concurrent rotations for the same tenant cannot conflict or corrupt state, only produce an ordering the EventStore stream revision already resolves deterministically) is different from, and more defensible than, the reason given. This does not create an exploitable gap — the exemption's practical effect (no lock needed for an append-only, non-conflicting operation) is likely correct — but the stated rationale should be corrected so a future reader doesn't generalize the wrong principle ("tenant-scoped resources never need locks") to a case where it would actually be wrong.

**Fix:** Replace "since it targets no tenant-scoped resource requiring a session lock" with something like "since minting a new version is a purely additive operation with no conflicting concurrent write to reject or merge, unlike the other nine families' read-modify-write mutations."

## Additional areas re-derived independently for this round (no new findings)

- **Payload/content protection fail-closed coverage:** AD-14's second-update attestation (line 209) plus AD-22's `Apply`-time `Erased` typed value, plus AD-27's reference-only execution-state boundary, plus the register's NFR-14 browser-metrics prohibition on raw content/secrets/PII (register line 262) together cover events, projections, workflow execution state, logs/telemetry, and browser telemetry with no path found that a content-bearing value could reach an unprotected surface without an explicit closing rule. No gap found.
- **Secret handling:** AD-9's opaque `SecretReference` (never a vault address/URI), in-memory-only resolution scoped to the generation activity, and AD-22's export-envelope-key delivery "never in an Agents response, manifest, log, or projection" were each re-checked against every place a "key" or "secret" term appears in the document; no path was found where provider credentials, vault addresses, or the export envelope key could reach a public contract, event, log, or export. The export manifest's "key versions" field was checked specifically — it is a protection-key (DEK/KEK) version reference, not key material, and is a different concept from AD-9's provider-secret handle. No gap found.
- **Tenant isolation:** AD-2's mandatory `TenantId` component and uniform absent-key response, with its single named carve-out (`EntryMissing`/reason-coded `Blocked` for the Agent's own previously-snapshotted or selected Provider entry) explicitly bounded as "the one named carve-out," plus AD-17's explicit ordering guarantee that "the AD-2 tenant-ownership check on a keyed read always strictly precedes any `Freshness`/`RevisionLag` computation" to close the staleness/absence timing side-channel, were re-checked and hold. `LaunchReadinessGate`'s `TenantScope` grammar explicitly forbids `tenant:system` as a spoofable cohort. No gap found.
- **Authorization fail-closed:** AD-12's re-read-before-every-side-effect rule and AD-30's never-cached/never-token-embedded role-freshness rule for `User`, `Administrator`, and `Platform` were re-checked; the `PausedDuration` union-not-sum merge rule (AD-12, line 193: "the two causes accrue against the same `PausedDuration` field as the union of wall-clock time either cause was active... counts once, never twice, and the clock resumes counting down only once both causes have cleared") resolves v7 Medium Finding 2 — the deadline is now unambiguous even when the kill switch and a disabled Agent overlap. **Verified fixed.**
- **Audit evidence completeness:** every lock-bearing-family command's change-evidence event, `AuditInspection`'s own durability past Source Conversation loss and erasure, and the register's `ObservationId`/`RegistryRevision` supersession discipline were re-checked; the one open gap in this area is Finding 1 above (digest re-verifiability after rotation), not a missing evidence-emission path.
