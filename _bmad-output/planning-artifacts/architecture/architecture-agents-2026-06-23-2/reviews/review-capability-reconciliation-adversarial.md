# Capability-Version Reconciliation Adversarial Review

Verdict: **Fail — AD-4/AD-10 now make the request-time capability version a clear floor, but they do not yet define one deterministic context-to-generation contract.** Lower/equal/higher behavior at the context read is decidable; readiness, audit provenance, generation-time revalidation, and retry behavior are not.

Attack fixture: snapshot `ProviderCapabilityVersion = 5`, fixed snapshotted `ProviderId`/`ModelId`, and two independently built units that both implement the literal rule in `ARCHITECTURE-SPINE.md:90-95,127-132`:

- **Unit A — frozen reconciled handoff.** At context build it rejects a missing entry or live version `4`, accepts version `5` or `6`, requires `Enabled && Configured && SupportsTextGeneration`, uses the accepted entry's live context/output/timeout limits, and records live version `5`/`6`. It durably hands that reconciled bundle to generation. Generation and all transport retries use the same content identity, version, limits, readiness verdict, and deterministic attempt id. A catalog change after `ContextReady` affects a new interaction, not this already reconciled invocation.

- **Unit B — live-at-each-step reconciliation.** At context build it also rejects missing/version `4`, accepts version `5` or `6`, and records the accepted live version and limits. It interprets readiness as `IsSelectableForNewActiveUse && SupportsTextGeneration`; configuration is left to the adapter because AD-10 lists configured state but never makes it part of the predicate. At generation and on every retry it re-reads content and catalog, requires only `live CapabilityVersion >= snapshot floor 5`, and uses that read's current output/timeout values. Context evidence records the live context version, while generation evidence records snapshot version `5`, because AD-4 says it was snapshotted. It never retargets provider/model.

Both units implement the explicit lower/equal/higher rule exactly: `4` blocks as `ModelBudgetUnavailable`; `5` is accepted; `6` is accepted without equality pinning and supplies live limits. They nevertheless produce different provider calls and audit trails in the cases below.

Findings:

- **[Critical] “Current readiness” has no normative predicate.** AD-10 enumerates enabled state, configured state, and text-generation capability, then says to use “current readiness,” but never states whether runtime-ready means `Status == Enabled`, `ConfigurationState == Configured`, non-empty configuration reference, `SupportsTextGeneration`, `IsSelectableForNewActiveUse`, or a precise conjunction. Unit A blocks an enabled-but-unconfigured version `5`; Unit B reaches the adapter. Both can defend their reading. Define one fail-closed predicate and say whether a configuration reference is required when credentials may also come from host configuration.

- **[High] Equal version does not mean equal readiness.** The shipped capability version is explicitly unchanged by enable/disable (`src/Hexalith.Agents.Contracts/ProviderCatalog/ProviderCatalogEntryView.cs:24-27`), and enable/disable mutates status without incrementing it (`src/Hexalith.Agents/ProviderCatalog/ProviderCatalogState.cs:82-101`). Therefore snapshot `5` and live `5` may describe opposite enabled states. AD-10 correctly requires a live readiness read, but audit evidence containing only version `5` cannot prove which state was evaluated. Either version every readiness-affecting transition or record the evaluated readiness fields plus an authoritative entry revision/read watermark.

- **[High] The current “selectable” projection is not a safe substitute for runtime readiness.** `IsSelectableForNewActiveUse` is currently derived only from `entry.IsEnabled` (`src/Hexalith.Agents/ProviderCatalog/ProviderCatalogInspection.cs:84-98`), ignoring configured state and text-generation capability. A builder using that canonical-looking field and a builder recomputing readiness from the enumerated metadata will diverge while both appear architecture-compliant. AD-10 must name the authoritative predicate or value object, not an English concept.

- **[High] The context-time implementation already demonstrates the ambiguity.** The budget read accepts any successful text-capable entry without checking `Status`, `ConfigurationState`, `IsSelectableForNewActiveUse`, or the snapshot floor (`src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionContextOrchestrator.cs:196-213`). Its test named `Disabled_or_non_text_capable_entry_returns_context_blocked` supplies an enabled entry with text generation disabled, so it does not cover the disabled branch (`test/Hexalith.Agents.Server.Tests/AgentInteractionContextOrchestratorTests.cs:150-161,414-428`). Fixing only `liveVersion >= snapshotVersion` would still leave Story 2.3 non-conformant with the amended “current readiness” wording.

- **[Critical] AD-10 fixes the check “at context build” but does not say whether that decision remains valid for the provider side effect.** AD-4 says current constraints may tighten or block an in-flight interaction, while AD-10 names only context build. Unit A treats `ContextReady` as the durable authorization to invoke with its reconciled bundle; Unit B rechecks immediately before generation. If the entry is disabled at the same capability version after context, A invokes and B blocks. State explicitly whether readiness and floor checks are required only for context measurement, again at every provider invocation, or both.

- **[Critical] No normative context-to-generation handoff ties the approved budget to the eventual provider input.** The current context step discards raw content and records counts/limits/version, while generation re-reads the Conversation and catalog (`src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionGenerationOrchestrator.cs:130-154`). The generation request does not consume context evidence. A longer Conversation or smaller context window can therefore exist at generation even though the aggregate is already terminally `ContextReady`. Unit A can freeze a content identity and reconciled budget; Unit B can rebuild and revalidate. The spine must choose one and require generation to prove that the exact provider payload fits the capability version/limits it invokes under.

- **[High] The floor can move backwards between steps.** Suppose context accepts live version `8` against snapshot floor `5`, then a lagging generation projection returns version `6`. Unit B accepts `6` because `6 >= 5`; Unit A continues with `8`. AD-10 does not say whether context evidence advances the minimum trusted version for all later steps. Require each later read to be at least the maximum of the snapshot floor and every previously accepted durable capability version, or declare the reconciled context bundle immutable and do not re-read it.

- **[High] “ProviderCapabilityVersion” has two incompatible audit meanings once a higher live version is accepted.** AD-4 snapshots version `5`; AD-10 requires context evidence to record live version `6`. The context evidence field means “version backing the budget” (`src/Hexalith.Agents.Contracts/AgentInteraction/AgentInteractionContextEvidence.cs:21-33`), while generation evidence also claims to be the version “backing the attempt” (`src/Hexalith.Agents.Contracts/AgentInteraction/AgentGenerationAttemptEvidence.cs:14-24`). Current generation nevertheless writes the snapshot/request version into the provider request and durable result while taking limits from the live catalog (`src/Hexalith.Agents.Server/Application/AgentInteractions/AgentInteractionGenerationOrchestrator.cs:181-190,235-238,255-263,327-336`). At live version `6`, the audit can falsely say version `5` backed limits from `6`. Split the names into `SnapshotCapabilityFloor` and `Evaluated/InvocationCapabilityVersion`, and persist both where provenance matters.

- **[High] A lower-version rejection is not auditable with the current evidence shape.** AD-10 assigns `ModelBudgetUnavailable` to missing/lower state, but `AgentInteractionContextEvidence` has only one capability-version slot. An implementation that zeroes the unavailable budget loses the observed lower version; one that records the lower version makes that field look like a trusted budget version. Add separate expected-floor and observed-version fields, plus a safe reconciliation outcome, so audit can distinguish missing, lower, invalid limits, and unavailable projection without leaking details cross-tenant.

- **[High] Retry identity is deterministic while retry inputs are not defined as deterministic.** AD-13 fixes attempt ids, but AD-10 says to use current catalog data and AD-18 delegates retries to the durable owner. Unit A retries the same immutable reconciled request under the same attempt id; Unit B reuses the id with changed content, capability version, output limit, timeout, and retry count. A provider deduplicating by attempt id can return the first result for a later different request. Specify that all retries of one attempt reuse a hashed/frozen invocation bundle, or derive a new deterministic attempt generation whenever any governed input changes.

- **[Medium] Timeout policy and `MaxRetries` fall between “safe limits” and ordinary metadata.** AD-10 lists timeout policy but explicitly calls out only current readiness and safe limits. Unit A freezes timeout/retry values with context evidence; Unit B re-reads them at invocation and on retry. This changes the number and duration of side effects under the same attempt id. Say whether timeout and retry policy are part of the reconciled capability bundle, whether they may only tighten, and which version audit records for them.

- **[High] Failure classification and retryability are incomplete outside the explicit lower/missing case.** Missing/lower is mandated as `ModelBudgetUnavailable`, but disabled, unconfigured, non-text-capable, invalid limits, and projection-unavailable have no required context classification. Generation already distinguishes `ProviderDisabled` from `ProviderUnavailable` while context collapses failures into a zero budget. Independent durable owners can therefore retry different failures or show different operator guidance. Define safe outcomes and retryability for each readiness/reconciliation failure, including whether “not configured” is disabled or unavailable.

- **[High] The trusted source of the snapshot floor is not an invariant at the aggregate boundary.** AD-10 says compare with `ProviderCapabilityVersion` “from the interaction snapshot,” but the server request carries a duplicate scalar and the context command carries only the assembled measurement. `AgentInteractionAggregate.Handle(BuildAgentInteractionContext)` trusts that measurement without comparing it with `state.Snapshot` (`src/Hexalith.Agents/AgentInteraction/AgentInteractionAggregate.cs:144-175`). One builder can rehydrate the interaction and source the floor from durable state; another can trust an orchestration DTO. Require the durable owner to read the recorded snapshot, and carry expected plus observed versions in a server-trusted reconciliation result that the aggregate validates against its own snapshot.

- **[Medium] The amended spine conflicts with the shipped snapshot documentation.** `AgentInteractionSnapshot` still says later `ProviderCatalog` edits affect only future interactions and “never this one” (`src/Hexalith.Agents.Contracts/AgentInteraction/AgentInteractionSnapshot.cs:5-9`), while amended AD-4 says current readiness/limits may tighten or block in-flight work. Two teams following different authoritative-looking texts will implement Units A and B. Reconcile the contract documentation when the architecture decision is implemented.

- **[High] The required tests are too narrow to close the architecture decision.** Lower/equal/higher tests prove only the integer comparison. The conformance matrix must cross those cases with enabled/disabled, configured/not-configured, text/non-text, valid/tightened/expanded limits, and then exercise a catalog change between context and generation and between retries. It must assert context evidence version, invocation version, failure reason/retryability, provider-call absence/presence, and stable retry inputs. Without that matrix, either constructed unit can pass the proposed focused tests.

Required spine closure: retain the `live >= snapshot floor` decision, but add a normative runtime-readiness predicate; distinguish snapshot floor, observed context version, and invocation version; define whether and how the accepted version advances the floor; specify the immutable or revalidated context-to-generation bundle; and bind retry identity to stable governed inputs. Until those points are explicit, the floor amendment prevents one stale-read bug but does not prevent independently compliant implementations from diverging.

## Recheck 2026-08-01

Verdict: **Fail, with substantial improvement.** Amended AD-10 now fixes the readiness predicate, distinguishes snapshot provenance from effective runtime evidence, and advances later accepted steps from prior effective versions. Amended AD-13 binds the first invocation's governed inputs. Two literal implementations can still diverge in the following critical/high cases:

- **[Critical] Readiness freshness is still not ordered.** AD-10 deliberately leaves enable/disable outside `CapabilityVersion`, then requires a “live” status read. An eventually consistent projection can return `Enabled, version 7` after the authoritative entry was disabled at the same version `7`; an implementation using that projection invokes, while one using a strongly consistent read blocks. Independent readiness checking cannot detect this regression. Version every readiness transition or require a separate monotonic readiness/entry revision and freshness watermark in the floor.

- **[High] A rejected higher observation does not clearly advance the cross-step floor.** The rule advances from the latest prior *effective* step version. If a retry observes version `9` but rejects it as disabled, a later new step can accept a lagging enabled version `8` because `9` never became “effective.” One implementation advances on every successful catalog observation; another advances only on accepted readiness. Define the floor as the latest trusted observed entry revision, including higher not-ready observations, or explicitly justify allowing that regression.

- **[Critical] The exact context approved by `ContextReady` is still not bound to the first provider input.** AD-13 binds an input fingerprint immediately before the first invocation, but it does not require that fingerprint/payload to be the context measured in the earlier context step. With an equal capability version, one implementation freezes the measured context; another re-reads a longer Conversation, binds that new input, and invokes without repeating the fit decision. Require an immutable context identity from context evidence or require generation to remeasure and reapply AD-11 to the exact provider payload before binding.

- **[High] “Runtime evidence field” does not cover every durable/runtime use of `ProviderCapabilityVersion`.** AD-10 clearly defines snapshot and runtime-evidence meanings, but generated-version records and provider-port requests are not unambiguously “evidence fields.” One implementation stamps the effective live version on `AgentGeneratedVersion` and `AgentGenerationProviderRequest`; another preserves snapshot provenance there and uses the effective version only on attempt evidence. Enumerate the effective-version consumers or rename the contracts to `SnapshotCapabilityFloor` and `EffectiveCapabilityVersion`.

- **[High] Failed reconciliation evidence still has no prescribed version semantics.** A lower/not-ready read consumes no effective capability, so the runtime evidence rule does not say whether to record zero, the rejected observed version, the prior floor, or both. Those choices produce different audit trails and different inputs to the next floor calculation. Require separate floor, observed version/revision, effective version, and safe reconciliation outcome fields for failures.

- **[Critical] AD-13 explicitly permits two different outcomes when bound inputs change.** “Fails closed or starts an explicit new attempt identity” allows Unit A to terminate and Unit B to invoke automatically under a replacement identity; both are literal. Select the allowed behavior per workflow and define whether a new attempt requires a user/domain command rather than being an infrastructure retry.

- **[High] A replacement attempt identity is not deterministically specified.** An implementation may derive it from an ordinal, another from the new input fingerprint, and another from effective version. Replay, concurrent recovery, and audit will disagree on whether two replacements are the same attempt. Define the canonical identity inputs, collision/domain scope, and atomic allocation rule.

- **[Critical] “Binds before invocation” is not explicitly a durable pre-side-effect write.** Unit A checkpoints the entire binding in the durable owner before calling the provider; Unit B constructs it in memory and relies on the deterministic id. A crash after the provider accepts the request but before outcome persistence lets B rebuild different bound inputs under the same id. Require the binding to be durably recoverable before the first network call, with recovery reading that binding rather than recomputing it.

- **[High] The input fingerprint has no canonical byte domain.** Builders can hash raw provider payload bytes, normalized Conversation text, message DTO serialization, or content plus instructions/tools while all calling the result an input fingerprint. They will disagree on whether reordering metadata, newline normalization, tool schemas, system instructions, or safety constraints changed the attempt. Define a versioned canonical preimage covering every provider-visible and capability-dependent input, excluding only explicitly named volatile/secret fields.

- **[High] “Retry” is not scoped to an actual provider network call.** One adapter may perform `MaxRetries` internally without returning to the readiness gate; another durable owner may gate every call. AD-13 can be read as governing orchestration retries only or every transport retry. State that readiness is rechecked before each actual provider invocation, and either prohibit opaque SDK retries or require a governed callback/seam around them.

- **[High] Per-step valid-limit invariants remain underspecified.** “Valid positive limits required by that step” does not settle whether zero retries are valid, whether timeout and retry count are both bound limits, whether max output must be strictly below the context window, or which combinations force revalidation. Two implementations can accept different catalog entries and still claim positive validation. Bind the exact context, generation, regeneration, and retry predicates.

- **[High] Non-context failure classification and retryability remain open.** Context gets `ModelBudgetUnavailable`, but generation/regeneration can classify the same disabled, unconfigured, lower-version, invalid-limit, or unavailable read differently. Durable owners can consequently retry different cases despite identical catalog state. Define safe failure classes and retryability for every AD-10 rejection at each provider-dependent step.

Recheck conclusion: the amendment eliminates the original basic lower/equal/higher and readiness-predicate divergence, but it does not yet make readiness freshness, rejected-version advancement, the context-to-first-invocation handoff, or replacement-attempt behavior single-valued.

## Final recheck 2026-08-01

Verdict: **Pass. No remaining Critical or High findings in the focused AD-4/AD-10/AD-13 reconciliation.**

Final attack results:

- Lower/equal/higher catalog versions are single-valued because every provider-dependent step compares a trust-bearing fresh read with the durable high-water mark.
- A higher observed version advances the durable mark even when readiness or limit validation subsequently fails, preventing a later stale regression.
- Enabled, configured, and text-generation readiness are independent mandatory predicates; version equality cannot stand in for readiness.
- Snapshot provenance and effective runtime provenance are distinct, and the effective version is required consistently across the internal request, provider request, outcome, and evidence.
- `ContextReady` cannot authorize stale provider input: generation and regeneration repeat the fresh content read, measurement, capability reconciliation, and full budget calculation immediately before preparation.
- The first provider side effect is preceded by a durable checkpoint of one prepared-attempt descriptor.
- The prepared descriptor binds provider/model, effective version, limits/timeout, and a canonical full provider-request fingerprint to one deterministic attempt id.
- A changed capability version, readiness result, or request fingerprint cannot be retried under that attempt id.
- The same interaction/regeneration action cannot replace the failed binding with a second attempt identity, eliminating the former fail-versus-replace fork.
- Retry eligibility is limited to transient transport/timeout failures before a terminal domain outcome, and every retry rechecks readiness while reusing the exact descriptor.
- Freshness, high-water advancement, descriptor durability, and terminal fail-closed behavior jointly prevent two compliant units from selecting different provider inputs after replay or recovery.
- The remaining brownfield differences documented in AD-10 are implementation gaps, not unresolved architecture choices.

Remaining Critical/High findings: **none.**
