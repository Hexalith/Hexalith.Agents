## Critical

### Finding 1 — The spine claims `launch-readiness-register.md`'s `LR-AUDIT-PROTECTION-DELETION` evidence contract now covers `DeletionRequest`/erasure symmetrically with `LegalHold`; the actual register file was never edited to say so

**AD:** AD-22, `ARCH-A-10`, and the register's `LR-AUDIT-PROTECTION-DELETION` row.

**Quoted spine text (current):**
- Architecture Assumptions preamble: *"this change retires no assumption and **extends `ARCH-A-10` to `DeletionRequest` symmetrically with `LegalHold` (C-8)**..."*
- `ARCH-A-10` row: *"A posted Conversation Message's Conversations-owned retention is independent of an Agents-side `LegalHold` or `DeletionRequest`; no seam propagates an Agents hold or erasure into Conversations preservation or purge... (tracked inside `LR-AUDIT-PROTECTION-DELETION`)"*
- AD-22 body: *"...a hold that outlives Conversations' own retention window for the posted copy, and an erasure whose posted copy survives in Conversations, are named residual risks, not silently absorbed ones: **both are tracked inside `LR-AUDIT-PROTECTION-DELETION`'s evidence contract in `launch-readiness-register.md`**..."*

**Actual current register text (`launch-readiness-register.md` line 93, unchanged since a prior round, `git log`-confirmed last touched at commit `74a9d66`, one commit before the spine's most recent commit `4ec626d`, and confirmed via `git status`/`git diff` to carry zero pending edits):**

> *"`LR-AUDIT-PROTECTION-DELETION` | Payload protection, authorized audit, retention/legal hold/export, cryptographic erasure/redaction, named projection purge, and safe tombstone evidence. **Includes evidence that a `LegalHold` either propagates to (or has a confirmed accepted-risk waiver for) the posted copy of held content in Conversations**, since AD-22 concedes posted Conversation Messages are otherwise governed only by Conversations' own independent retention (spine assumption `ARCH-A-10`). Invalidated by protection, retention, export, deletion, propagation-seam, or projection-inventory changes."*

**The gap:** the register's evidence description names only `LegalHold` propagation/waiver as the thing this gate requires proof of. It says nothing about `DeletionRequest`/erasure needing the symmetric evidence the spine now claims exists. This is not a wording nuance — `launch-readiness-register.md` is stated by the spine itself (AD-17) to be *"the normative readiness authority for the record schema, state vocabulary, minimum GateId inventory... gate sets, `OperationGateMatrix` versions... and measurement contracts; the spine binds only the invariants below."* The register, not the spine's prose, is the actual enforced contract a builder or auditor implements against when producing `LR-AUDIT-PROTECTION-DELETION` evidence for `RQ-1`.

**Concrete exploit/false-completeness scenario:** Security Engineering (the register's named evidence owner for this row) builds exactly what the register's own evidence description asks for: proof that `LegalHold` either propagates to the posted copy in Conversations, or a signed Legal waiver for that one direction. They record `Pass` for `LR-AUDIT-PROTECTION-DELETION`. `RQ-1` evaluation reads this as satisfied — nothing in the register's text, which is what an implementer actually follows, ever asked for equivalent evidence about a `DeletionRequest`/erasure whose posted copy survives in Conversations. The erasure-direction residual risk — the exact gap v4 rated Critical — is disclosed in the spine's prose but never becomes a gate requirement in the one document that actually gates release. This reproduces v4's original failure mode (a completeness claim that isn't actually enforced) one layer down: the spine *says* "both are tracked in the register," but that statement is itself false against the current register content, so a reader who trusts the spine's cross-reference rather than checking the register directly (exactly the trust v4's own methodology warns against) would believe erasure-direction evidence is required when it is not.

**Fix:** edit `launch-readiness-register.md` line 93's `LR-AUDIT-PROTECTION-DELETION` description to add the symmetric clause the spine already claims exists — e.g., *"...Includes evidence that a `LegalHold` **or a `DeletionRequest`** either propagates to (or has a confirmed accepted-risk waiver for) the posted copy of held **or erased** content in Conversations..."* — so the register's actual evidence requirement matches what AD-22/`ARCH-A-10` assert it requires. Until that edit lands, the spine's "tracked inside `LR-AUDIT-PROTECTION-DELETION`" sentence is itself inaccurate and should either be corrected to say the register update is still pending, or (preferably) the register should simply be fixed in the same change.

## High

### Finding 2 — AD-30's new `Platform` freshness re-check names "the Tenants-projection" as the source for a role the PRD defines as the one non-tenant-scoped role in the system

**AD:** AD-30 (Principals And Trusted Envelope).

**Quoted text (current):** *"`Platform` (the `system`-tenant Platform Operator, carried as the reserved `actor:agentsProviderAdmin` extension, populated only by the Agents API ingress after a **fresh Tenants-projection Platform Operator role check** on the same terms as `User` and `Administrator` above — never from a cached or token-embedded claim)."*

Compare `User`: *"resolved FR-33 roles re-read from the Tenants-projection role assignment at every command ingress... never trusted from a cached or token-embedded role claim alone"* — a `User`'s roles are inherently tenant-scoped, read from that `User`'s own tenant's Tenants-projection. `Administrator` mirrors this via *"a fresh Tenants-projection role check."*

**The gap:** `prd.md` line 488 states plainly: *"Every role except Platform Operator is tenant-scoped; a role assignment in one tenant grants nothing in another (FR-19)."* Platform Operator is explicitly the **one** role in the entire FR-33 matrix that is cross-tenant/platform-scoped — per AD-30 itself, `Platform` "carries `ActorTenantId = system`, targets the envelope `TenantId`" (a different tenant than its own), and per AD-2's pattern, platform-scoped state elsewhere in this same spine lives under the reserved EventStore tenant `system` specifically because it is *not* naturally tenant-scoped (`ProviderCatalog` is explicitly "reserved EventStore tenant `system`"). AD-30's fix, by contrast, reuses the literal phrase "Tenants-projection role assignment" — the same mechanism used for genuinely tenant-scoped `User`/`Administrator` roles — without ever stating which tenant's projection is read for a role that, per FR-19, isn't tenant-scoped at all. This is precisely the ambiguity v4's Finding 2 fix recommendation flagged and asked to be resolved by naming an explicit authoritative source (*"presumably a platform-level identity/role registry... since it is not tenant-scoped and therefore not literally 'the Tenants-projection'"*); the round-6 fix instead adopted the literal wording v4 said wasn't accurate.

**Why this matters:** `Platform` is, as v4 already established, the most powerful principal kind in the system (platform catalog mutation, any tenant's budget cap override, any tenant's kill switch, deletion requests in any tenant). Two plausible, materially different implementations both satisfy the current sentence: (a) the check reads a `system`-tenant-scoped Tenants-projection record (consistent with the `ProviderCatalog` pattern) — the more defensible reading but never stated; or (b) an implementer, following the "on the same terms as `User` and `Administrator`" instruction literally, keys the projection read off the **envelope's target `TenantId`** (the tenant the Platform Operator is acting on, since that's the `TenantId` in scope for the command) rather than a fixed platform-wide identity source — which would mean a Platform Operator's authority to act on tenant B could vary based on role data recorded in tenant B's own Tenants-projection, contradicting FR-19's platform-scoping guarantee and creating a path where a tenant-scoped role write (however that occurs) could affect cross-tenant authorization for the single most privileged principal in the system. The spine does not rule out reading (b).

**Fix:** name the authoritative source explicitly and unambiguously — e.g., "a fresh read of the Platform Operator role assignment from the `system`-tenant Tenants-projection record, never the envelope's target `TenantId`'s projection" — mirroring the disambiguation AD-2 already gives `ProviderCatalog`/`TenantProviderEnablement`, so the wording can no longer be read as scoping the check to the tenant being acted upon.

## Medium

### Finding 3 — The Consistency Conventions table's "Provider attempt fingerprint" row states plain (unkeyed) SHA-256, in apparent tension with AD-29's blanket HMAC rule for the same class of digest

**AD:** AD-13, AD-29, Consistency Conventions table.

**Quoted text:**
- Consistency Conventions, "Provider attempt fingerprint" row: *"One shared canonicalizer hashes the length-prefixed, stable-order prepared request with **SHA-256** over the AD-13 field inventory; descriptors store the digest and safe scalar inputs, never raw context."*
- AD-13: *"The fingerprint covers `TenantId`, `ProviderId`, `ModelId`, `EffectiveProviderCapabilityVersion`, `InstructionsVersion`, the structured role/provenance message sequence **with per-message content digests**, generation parameters, reserved output tokens, and the evaluated safety policy versions; nothing else invalidates a retry."*
- AD-29 (blanket rule): *"Every digest of sensitive content stored outside a `ProtectedContent` envelope (per-message digests, verdict-cache keys, **evidence fingerprints**, command-payload fingerprints) is an HMAC-SHA-256 under a per-tenant `DigestKey`... unkeyed SHA-256 is used only for identities derived from identifiers."*
- AD-29 (fingerprint-distinction sentence): *"This is the one command-payload fingerprint function every command-handler story uses; it is distinct from the **AD-13 Provider-attempt fingerprint** (which hashes the prepared external request, not the command DTO) and from this AD's own id-derivation components (which never include full payload state and stay unkeyed)."*

**The gap:** AD-29's blanket rule explicitly lists "per-message digests" and "evidence fingerprints" as categories requiring keyed HMAC-SHA-256 — both terms plausibly describing the AD-13 Provider-attempt fingerprint and its embedded per-message content digests (this fingerprint is stored durably on `ProviderAttempt` as evidence, per the class diagram's `RequestFingerprint` field, and is explicitly built "with per-message content digests" of conversation content). Yet the Consistency Conventions table — the one place that states the actual hash function for this specific fingerprint — says plain "SHA-256," not "HMAC-SHA-256," and AD-29's own distinguishing sentence stops at "distinct from," never clarifying whether that distinction includes an exemption from the keying rule or not. A reader has no unambiguous way to determine whether: (a) the outer Provider-attempt fingerprint is correctly unkeyed because its only sensitive component (the per-message content digests) is *already* separately HMAC-keyed per AD-29's explicit listing, making the outer hash safe regardless of keying (the likely intended reading); or (b) the Consistency Conventions table's flat "SHA-256" is itself the authoritative, narrower statement and the per-message digests embedded in it are not separately required to be keyed, which would make the digest brute-forceable given typical message-content entropy — reproducing the exact unkeyed-digest risk the v3→v4 fix was supposed to eliminate everywhere, just for a fingerprint the v3/v4 rounds never scoped in.

**Why this matters:** the review lens here is explicitly about whether "AD-29's fingerprint/digest scheme is stated correctly and *consistently*" — this is the one place in the current text where two clauses governing the same digest disagree on the algorithm name (plain SHA-256 vs. an implied-but-unstated HMAC requirement), and it sits exactly at the boundary the v3→v4 fix was meant to close (a request-fingerprint construction that "may itself carry sensitive content" via embedded per-message digests).

**Fix:** state explicitly, in either AD-13 or the Consistency Conventions row (preferably both, kept consistent), that the per-message content digests folded into the Provider-attempt fingerprint are each independently HMAC-SHA-256 under the per-tenant `DigestKey` per AD-29's blanket rule, and that the *outer* fingerprint over the full prepared-request field inventory may remain a plain SHA-256 specifically *because* its only sensitive-content-derived input is already keyed — closing the ambiguity instead of leaving "distinct from" to imply an unstated exemption.

### Finding 4 — Digests/fingerprints of erased content survive erasure indefinitely under a long-lived, non-rotated per-tenant `DigestKey`, with no residual-risk framing in AD-22's completeness narrative

**AD:** AD-22, AD-29.

**Quoted text:** AD-22: *"Identities, versions, decisions, timestamps, policy versions, and keyed content hashes are never inside the protected envelope, so the FR-24 trace survives erasure"* (via `prd.md` line 731, restated in spine terms by AD-27/AD-29's digest rules) and AD-29: *"Every digest of sensitive content stored outside a `ProtectedContent` envelope (per-message digests, verdict-cache keys, evidence fingerprints, command-payload fingerprints) is an HMAC-SHA-256 under a per-tenant `DigestKey` custodied through `EXT-SECRETS-1`."* AD-22's erasure rule: *"Cryptographic erasure destroys the DEK at interaction granularity... snapshots and replay caches inherit the DEK so a restore cannot revive erased content."*

**The gap:** erasure is scoped to destroying the per-interaction DEK that seals the `ProtectedContent` envelope. By design (and intentionally, per the PRD's own stated rationale — the FR-24 audit trail must survive erasure), every keyed content digest computed from that same now-erased content — per-message digests, verdict-cache keys, evidence fingerprints, command-payload fingerprints — lives *outside* the envelope and is explicitly untouched by DEK destruction. Its one-wayness against reconstruction depends entirely on the secrecy of the **per-tenant** `DigestKey`, which is never described as rotated, expired, or destroyed on any lifecycle event (tenant offboarding, retention expiry, or the tenant's own `DeletionRequest`/`LegalHoldRelease`). Because it is per-tenant rather than per-interaction, a single `DigestKey` compromise (`EXT-SECRETS-1` breach, insider access, backup exposure, migration mishap) would let an attacker dictionary/brute-force-match candidate plaintexts against every surviving digest for that tenant's entire interaction history — including interactions whose content was "erased" years earlier under this very AD-22 procedure — since natural-language message content is comparatively low-entropy and HMAC's security against a keyed adversary evaluating *known* candidate messages collapses once the key itself is known. AD-22's "Restrictive completion" narrative (*"every protected event unprotects as unreadable... only a support-safe non-content tombstone remains; deletion is not complete before that"*) never mentions this class of residual exposure, unlike the Conversations-posted-copy gap, which is now explicitly named.

**Why this is a distinct gap from Finding 1/the Conversations-copy risk:** the Conversations-copy risk is about content that was *deliberately* posted and is readable today, in plaintext, by design of a different module. This finding is about content that was *never* meant to remain reconstructable after erasure, but whose keyed representations persist by architectural necessity (for audit-trail survivability) under a key with no stated lifecycle bound — a materially different risk (single-key-compromise blast radius across a tenant's full erased history) that the current text does not name anywhere as a residual risk, tracked assumption, or `LR-AUDIT-PROTECTION-DELETION` evidence item.

**Fix:** at minimum, name this as a residual risk alongside the two `ARCH-A-10` items (a `DigestKey`-compromise blast-radius statement, scoped per tenant, with `EXT-SECRETS-1` custodianship named as the sole mitigating control), or specify a `DigestKey` rotation/versioning policy tied to a lifecycle event (e.g., rotate on `RQ-1`-qualifying tenant offboarding, or after full-tenant `DeletionRequest` completion) so that a future key compromise cannot retroactively threaten interactions that have already completed erasure.

Every other spine-referenced PRD-owned numeric parameter is inline-tagged, e.g. *"the regeneration ceiling (default 3, range 1 to 10 [ASSUMPTION A-6])"*, *"a margin defaulting to 10 percent (range 5 to 25) [ASSUMPTION A-5]"*. **Fix:** add `[ASSUMPTION A-19]` inline at the "FR-24 review window" reference, matching the citation style used for every other PRD-sourced numeric bound in the document.
