## Findings

### CRITICAL — AD-5's automatic-mode retry clause still contradicts FR-11/FR-18 (PRD self-flags this as unresolved)

**Location:** `ARCHITECTURE-SPINE.md`, AD-5, final sentence of the main rule paragraph (the "Automatic-mode posting shares the same bound..." clause, line 149). Cross-reference: `prd.md` FR-11 consequence bullet "Spine AD-5 states that automatic mode retries nothing; FR-11 governs, and the divergence is listed in §8.1." (line 347), and §8.1's AD-5 bullet (line 899): "...states that automatic mode retries nothing, whereas FR-11 gives the automatic posting record the FR-18 retry bound..."

**What's wrong:** The live AD-5 text reads: *"Automatic-mode posting shares the same bound: the workflow retries transient posting failures with the same `MessageId` and idempotency key, then records `PostingFailed` on `AgentInteractionStatus`... and automatic mode itself attempts no further automatic retry; the sole automatic-mode recovery is a new Agent Call."* This still says that once an automatic-mode posting record reaches `PostingFailed`, nothing but starting an entirely new Agent Call can recover it. FR-11 requires the opposite: an automatic post *"reuses the `ProposedAgentReplyState` posting values from `Approved` onward... `PostingFailed` with the same retry bound"* — i.e., the FR-18 transition-table row `PostingFailed → PostingPending | System (automatic retry within budget); Tenant Agent Administrator (audited administrative retry)` applies to automatic-mode posting records exactly as it does to Confirmation-mode proposals. AD-5's own general (non-automatic) `PostingFailed` rule already implements this bounded audited retry (3 attempts/15 minutes, then a Tenant Agent Administrator administrative retry) — the automatic-mode clause explicitly carves automatic-mode records *out* of that mechanism instead of routing them through it.

**Divergence risk:** This is the exact same divergence round-8 and earlier rounds could not close, and it is the one sub-clause of AD-5's PRD-cited divergence list (line 899) that round 5's otherwise-thorough AD-5 rewrite left standing (the sibling sub-clauses — `MessageId` lookup skipped from `Approved`, human abandon from `Approved`, `PostingWindowElapsed`, the `PostingPending` stored deadline — are all now fixed). A story built from AD-5 alone would implement automatic-mode `PostingFailed` proposals with no automatic or administrative retry path at all — forcing a brand-new Agent Call (a new generation, new cost, new safety scan) for every transient posting hiccup in Automatic Response Mode, contradicting FR-11's explicit "same retry bound" requirement and FR-33's Tenant-Agent-Administrator administrative-retry row, which FR-33 does not scope away from automatic-mode records.

**Suggested fix:** Replace the "automatic mode itself attempts no further automatic retry; the sole automatic-mode recovery is a new Agent Call" clause with the FR-18 `PostingFailed → PostingPending` automatic/administrative retry rule already stated earlier in AD-5, applied identically to automatic-mode posting records (the only difference from Confirmation mode being the substituted-Facilitator/no-Conversation-read-access abandon terms already correctly stated elsewhere in AD-5 and AD-7). Then delete or update the PRD's FR-11 footnote and its §8.1 bullet, since a spine text change is what retires that citation.

### CRITICAL — AD-8 invents a fourth Eligible-Approver exclusion absent from FR-7's own predicate definition

**Location:** `ARCHITECTURE-SPINE.md`, AD-8, main rule (line 169): *"The Eligible Approver predicate (resolved now, not the caller, not the last editor of the version, not the Approver who requested a regeneration of the version under decision, holding current Conversation read access)..."* Cross-reference: `prd.md` glossary, "Eligible Approver" (line 103): *"...a Party that the Approver Policy resolves from the Source Conversation's current Participants, that holds current read access, that is not the caller of the Agent Call, and that is not the Party that last edited the version under decision. Every proposal action in FR-7 tests this one predicate."*

**What's wrong:** The PRD's own canonical definition — explicitly called "this one predicate" that "every proposal action in FR-7 tests" — names exactly two exclusion conditions (not the caller, not the last editor) plus the positive current-read-access condition. AD-8 adds a third exclusion with no textual basis anywhere in the PRD: "not the Approver who requested a regeneration of the version under decision." A full-text search of `prd.md` for "requested a regeneration," "requesting Approver," or any equivalent phrasing near "Eligible Approver" finds nothing supporting this exclusion (the only "requesting Approver" hit in the PRD, line 382, is about proposal-discovery visibility, unrelated to the approval predicate). FR-7's own segregation-of-duties bullets (configuration time, call time, edit time, approval time) name only the caller-exclusion and the last-editor exclusion; regeneration requesters are never mentioned as a category to exclude.

**Divergence risk:** The Eligible Approver predicate gates edit, approve, reject, and abandon actions across the whole proposal lifecycle (AD-8's own binds list: FR-7, FR-13, FR-15..FR-18, FR-20). A story built from AD-8 as written would incorrectly reject an approval (or edit/reject) by a Party who requested a regeneration but was neither the caller nor the version's last editor — a Party FR-7/FR-18's own transition table (`Pending, Edited, Regenerated → Approved | Eligible Approver for that version`) would accept. This is a silent, unauthorized narrowing of who may act on a proposal — a governance-relevant behavioral difference a conformance test written from the PRD would catch as a spurious rejection.

**Suggested fix:** Either remove the third exclusion from AD-8's predicate text so it matches FR-7's glossary definition exactly, or — if Architecture believes the exclusion is a genuine, deliberate strengthening — route it through the PRD amendment path the PRD's own §8.1 reconciliation rule requires for any Spine rule that narrows an FR-7/FR-18 predicate, and add the corresponding row to the PRD's glossary/FR-7 text and Assumptions Index before treating it as binding.

### HIGH — AD-14 still omits FR-34's required attestation cadence (bounded periodic re-run, re-run on host composition change)

**Location:** `ARCHITECTURE-SPINE.md`, AD-14, "Second-update protection attestation, extended by the third update" paragraph (line 209). Cross-reference: `prd.md` FR-34 (line ~561ff): *"The attestation runs at startup, on every readiness evaluation, on a bounded cadence — hourly by default [ASSUMPTION A-24] — and on any host composition change..."*; §8.1's AD-14 bullet (line 904): *"AD-14 and the `EXT-SECRETS-1` register artifact: lack the attestation cadence (A-24), the pin, and the Security-qualified signed build identity the runtime compares against."*

**What's wrong:** Round 5 correctly added the signed-identity pin and the Security-qualified-build-identity comparison that the §8.1 bullet flagged as missing — AD-14 now reads: *"the runtime verifies the loaded engine's signed identity against that value on every check, pins it, and every seal and unseal call verifies the engine instance against the pin, failing closed... on a missing value, an unsigned engine, or a mismatch."* But the paragraph never states the third element the same §8.1 bullet named: the bounded re-attestation cadence (hourly by default, `[ASSUMPTION A-24]`) or the "on any host composition change" trigger. A repo-wide grep for `A-24`, `hourly`, `bounded cadence`, and `host composition change` across the entire 798-line spine returns zero matches. AD-14's own text only says the attestation runs "at startup and on every readiness evaluation," which is strictly narrower than what FR-34 requires.

**Divergence risk:** Without a bounded re-run cadence, a story built from AD-14 alone would only re-verify the payload-protection engine's identity at process startup and at readiness-evaluation time — potentially leaving a long-running host composition unattested for arbitrarily long stretches between readiness evaluations, and never re-attesting after a host composition change that doesn't happen to coincide with a readiness evaluation. This is a real gap in an NFR/FR-34 safety gate the PRD treats as launch-blocking (`PayloadProtectionUnavailable`).

**Suggested fix:** Add to AD-14's Second-update paragraph: "the attestation additionally re-runs on a bounded cadence (hourly by default, `[ASSUMPTION A-24]`) and on any host composition change," matching FR-34 and giving `ARCH-A-12`-style register treatment to the A-24 assumption if the spine wants to track its own confirmation date for it (it is not currently indexed anywhere in the Architecture Assumptions table).

### HIGH — AD-6 and the Deferred Beyond V1 table contradict each other on whether `EXT-CONV-AI-1` seam 7 is committed

**Location:** `ARCHITECTURE-SPINE.md`, AD-6 (line 155) vs. the Deferred Beyond V1 table's "Automatic-mode retraction metric" row (line 796). Cross-reference: `external-dependency-register.md`'s `EXT-CONV-AI-1` `RequiredArtifact` field.

**What's wrong:** AD-6 states: *"The seven Conversations-owned seams committed as `EXT-CONV-AI-1` [ASSUMPTION A-1, A-2, A-3, A-4, A-15, A-16, A-28] (idempotent AI membership..., idempotent posting..., Facilitator resolution, active-Conversation count, tenant-scoped content/roster/existence reads..., a Conversation deletion signal, and a message-retraction signal for the OQ-23 automatic-post retraction metric) are the only membership, posting, resolution, deletion-propagation, and retraction-signal paths..."* — listing the retraction seam as seam 7 of seven, on the same footing as the other six. The Deferred Beyond V1 table, two pages later in the same document, says of that same seam: *"`EXT-CONV-AI-1` now names the retraction signal as seam 7 (`[ASSUMPTION A-28]`), but the seam has not reached `Committed`; the metric waits on that and on the OQ-23 decision due 2026-09-30."* These two passages describe different states for the same seam within the same document: AD-6 folds it into the "committed as `EXT-CONV-AI-1`" set without qualification, while the Deferred table explicitly says it "has not reached `Committed`." Checking the actual authority — `external-dependency-register.md`'s `EXT-CONV-AI-1` `RequiredArtifact` cell — confirms the Deferred table's caution is the accurate one: the register's `RequiredArtifact` enumerates only **six** numbered items (membership, posting, Facilitator resolution, active-Conversation count, tenant-scoped reads, deletion signal); it does not mention a seventh (retraction) seam anywhere, even though the PRD's own §8 narrative (line 879) already numbers it "7." The register — the document AD-6 itself calls "the only membership, posting, resolution, deletion-propagation, and retraction-signal paths" and which "External V1 Prerequisites" calls authoritative for commitment status — has not yet been updated to require the seam AD-6 already counts as one of its "seven."

**Divergence risk:** A reader who only sees AD-6 would conclude all seven seams (including retraction) are equally scoped and simply awaiting delivery like the other six; a reader who reaches the Deferred table, or the register itself, would correctly understand the retraction seam is not yet even a required part of the `EXT-CONV-AI-1` commitment. This is exactly the kind of internal spine inconsistency that could let two consuming stories diverge — one blocking on `EXT-CONV-AI-1` reaching `Committed` for the whole seven-seam bundle, another correctly treating the retraction metric as separately gated behind both the seam's future addition to the register and the OQ-23 decision.

**Suggested fix:** Either soften AD-6's "committed as `EXT-CONV-AI-1`" framing to explicitly flag seam 7 as pending-not-yet-required (e.g., "six delivered seams plus a seventh, requested but not yet part of the register's `RequiredArtifact`, for retraction"), or drive an update to `external-dependency-register.md`'s `RequiredArtifact` cell to add the seventh seam so AD-6's count and the register agree.

### HIGH — AD-22 misclassifies the `ProviderAttempt` fingerprint as carrying "no rotation risk," contradicting AD-13 and AD-29's own persistence requirement for it

**Location:** `ARCHITECTURE-SPINE.md`, AD-22, `DigestKey` paragraph (line 261): *"A short-lived digest (a verdict-cache key, a `ProviderAttempt` fingerprint) is never compared across a rotation boundary and so carries no rotation risk..."* Cross-reference: AD-13 (line 201): *"...is persisted on the `ProviderAttempt` record together with its `DigestKeyVersion` so a retry's fingerprint recheck always recomputes against the version the retained fingerprint was computed under."*; AD-29 (line 303): *"Every digest of sensitive content stored outside a `ProtectedContent` envelope (per-message digests, verdict-cache keys, evidence fingerprints, command-payload fingerprints, and the AD-13 `ProviderAttempt` fingerprint) is an HMAC-SHA-256 under a per-tenant `DigestKey`... and is persisted together with the `DigestKeyVersion` it was computed under... — the idempotency record below, the `ProviderAttempt` fingerprint, and every per-message digest inside `audit-evidence`; re-verification or an idempotency-conflict comparison always recomputes against the recorded `DigestKeyVersion`, never the tenant's current one, so a comparison is never ambiguous after a rotation."*

**What's wrong:** AD-13 and AD-29 both explicitly require the `ProviderAttempt` fingerprint to persist its `DigestKeyVersion` precisely so that a retry, which may happen after a `DigestKey` rotation, can recompute the fingerprint under the *originally recorded* key version rather than the tenant's current one — this is only meaningful if the fingerprint genuinely can be re-checked across a rotation boundary (AD-13's own words: "a retry's fingerprint recheck"). AD-22, in the very next AD that discusses the same digest, classifies that same `ProviderAttempt` fingerprint as "short-lived" and states it "is never compared across a rotation boundary and so carries no rotation risk" — the opposite characterization of the same field, in the same document, written by the same round-5 pass (AD-22 was in this round's explicitly-touched list).

**Divergence risk:** This is a genuine contradiction about a cross-cutting security mechanism (digest-rotation safety) spanning three ADs (AD-13, AD-22, AD-29) that all bind the same field. An implementer who reads only AD-22 could conclude the `ProviderAttempt` fingerprint's `DigestKeyVersion` need not be persisted or checked on retry (since AD-22 says it "carries no rotation risk" and only requires versioning for "a long-lived digest embedded in an immutable audit or idempotency record"), directly contradicting AD-13's explicit persistence-and-recompute-under-recorded-version requirement for that exact field and creating exactly the rotation-ambiguity bug AD-29's closing sentence says must never occur.

**Suggested fix:** Remove the `ProviderAttempt` fingerprint from AD-22's "short-lived... no rotation risk" example list (leaving only the verdict-cache key there, which genuinely is short-lived per its own invalidate-on-policy-publication lifecycle), and instead fold it into the "long-lived digest... carries its `DigestKeyVersion`" category alongside the idempotency record and per-message digests — matching AD-13's and AD-29's own text for the same field.

### MEDIUM — AD-11's new Conversation-Context-Policy version counter is introduced as a fourth independent counter, but AD-4 (not touched this round) still asserts there are exactly three

**Location:** `ARCHITECTURE-SPINE.md`, AD-11 (line 187): *"...its version is mutated only by the Tenant Agent Administrator and increments only on an accepted edit to the policy's own fields..., on the same independent-counter terms AD-4 gives `ConfigurationVersion`, `InstructionsVersion`, and `ApproverPolicyVersion`."* Cross-reference: AD-4 (line 143): *"`ConfigurationVersion`, `InstructionsVersion`, and `ApproverPolicyVersion` are three independent monotonic counters on the `Agent` aggregate, not one counter under three names: `ConfigurationVersion` increments on every accepted `Agent` configuration or lifecycle event, including an edit that also bumps one of the other two..."*

**What's wrong:** AD-11 (explicitly in this round's touched-AD list) now asserts a fourth field on the `Agent` aggregate — the Conversation Context Policy's own version — that increments independently, "on the same terms" as AD-4's three named counters. But AD-4's own Rule text (not in this round's touched list) still literally says there are "three independent monotonic counters... not one counter under three names," with no acknowledgment of a fourth. This leaves two open ambiguities AD-4's text no longer resolves cleanly: (1) whether "the other two" ConfigurationVersion bumps alongside (the phrase used when describing a combined edit) still means exactly two, now that a context-policy edit is a fourth possible co-bumped field, and (2) whether an accepted edit to the Conversation Context Policy's own fields *also* bumps `ConfigurationVersion` under AD-4's general "every accepted Agent configuration... event" clause, or is deliberately carved out the way the regeneration-ceiling/proposal-expiry/response-mode edit is explicitly carved out ("bumps `ConfigurationVersion` alone") — AD-4 says nothing either way about context-policy edits specifically.

**Divergence risk:** Lower than the findings above since this doesn't describe outright contradictory runtime behavior, but it is a real specification gap: two implementers could reasonably read AD-4 + AD-11 together and build different answers to "does editing the Conversation Context Policy bump `ConfigurationVersion` too?" — which matters because `AD-4`'s interaction-snapshot rule snapshots `ConfigurationVersion` (not a context-policy version) at request time, so whether a context-policy edit is visible to that snapshot's staleness semantics depends on this exact question.

**Suggested fix:** Update AD-4's Rule to acknowledge the Conversation Context Policy version as a fourth independent counter (or explicitly fold it into the "one of the other two" language, making it "one of the other three"), and state explicitly whether an accepted context-policy edit also bumps `ConfigurationVersion`.
