# Adversarial Divergence Review v2 - ARCHITECTURE-SPINE.md (Hexalith Agents)

**Reviewer role:** independent adversarial reviewer, Reviewer Gate pass, 2026-09-09 (second pass; written without consulting the same-day `review-2026-09-09-adversarial-divergence.md` companion review to preserve independence).

**Method:** for each area of the spine, construct two hypothetical implementation units that each satisfy the literal wording of every binding AD, and show that they would still build incompatibly. Every finding below is a concrete pair, not a general worry.

## Finding 1 - General command idempotency has no defined payload-fingerprint canonicalization (CRITICAL)

**AD in question:** AD-29 (Deterministic Identity Derivation), specifically: "API command idempotency is keyed by (`TenantId`, principal..., operation family, client key) plus the payload fingerprint from the shared canonicalizer; ... an exact replay (same tuple and fingerprint) returns the original authoritative identity and projection version, the same tuple with a different fingerprint is a conflict."

AD-29 fully and precisely specifies the canonicalizer for **identity derivation** ("UTF-8, length-prefixed components, `U+001F` separators, SHA-256, lowercase hex, purpose tag as the first component") and separately, in the Consistency Conventions table, fully specifies the **Provider attempt fingerprint** ("hashes the length-prefixed, stable-order prepared request with SHA-256 over the AD-13 field inventory"). Neither of these defines how an arbitrary **command payload** (for any of the dozens of other commands: `ProposalEdit`, `TenantBudgetUpdate`, `LegalHold`, `AgentSetupMutation`, `PolicyPublication`, etc.) is mapped onto canonicalizer "components." A command payload is a structured object with optional fields, nested objects, and collections — the spine never states the field order, null/absent handling, or nesting-flattening rule that turns such a payload into "components" for the shared canonicalizer.

**Unit A - "TenantBudgetUpdate command handler" (Governance epic).** Builds the fingerprint by serializing the command DTO to canonical JSON (camelCase, contract-declared property order) and hashing the UTF-8 bytes through the shared SHA-256 primitive. An absent optional `CapOverrideExpiry` is omitted from the JSON entirely.

**Unit B - "ProposalEdit / generic command-handler base class" (Interaction epic).** Builds a shared `IdempotencyFingerprint` helper used by every proposal command: it treats the payload as an ordered list of canonicalizer "components" the same way identities are built — flattening each property in **alphabetical name order**, and representing an absent optional field as an explicit empty-string component (not omission), matching the AD-29 identity-derivation style literally ("length-prefixed components... separators").

**Collision:** Both teams can point to AD-29's single sentence ("the payload fingerprint from the shared canonicalizer") as authority for their approach, because the AD never says whether the "shared canonicalizer" invoked for command payloads uses the identity-style component list (Unit B's reading) or an out-of-band JSON/byte serialization (Unit A's reading, arguably more natural for a full command object). Worse, the two teams' helpers are not interchangeable: a client that retries a command using a slightly different but semantically-null variation (e.g., sending `CapOverrideExpiry: null` instead of omitting it, which many JSON serializers do) produces the **same** logical command but a **different** Unit-A-style fingerprint (if Unit A's JSON canonicalizer treats explicit null differently from absence) or the **same** fingerprint under Unit B's scheme. Depending on which handler a given command family lands under, an idempotent retry can be misclassified as a 409 conflict (breaking the AD-13 "retries reuse identities and never mint new ones" guarantee for governance commands) or, in the opposite direction, two different commands with coincidentally-omitted optional fields can collide onto the same fingerprint and one silently returns the other's stale authoritative result.

**Suggested fix:** AD-29 should name one canonical payload-to-bytes mapping used by *every* command handler (e.g., "every public command's fingerprint hashes its `Hexalith.Agents.Contracts` DTO via `[specific serializer + settings]`, contract-declared property order, with an explicit `Unset` sentinel distinguishing absent from default for every optional field") and state explicitly that this is the same or a different function from the AD-13 Provider-attempt fingerprint and the identity canonicalizer, so no two command-handler stories can each defensibly invent their own.

## Finding 2 - AD-2 and AD-10 give contradictory answers for a disabled/non-enabled catalog entry that is an Agent's own selection (CRITICAL / HIGH)

**ADs in tension:**

- AD-2: "`TenantId` is a mandatory component of every... query cursor scope...; a query for a key outside the caller's tenant, **or for a platform entry not enabled for it, returns exactly the absent-key response**." No exception is carved out anywhere in AD-2.
- AD-10: "Tenant-facing readiness is the platform entry joined with `TenantProviderEnablement`; a by-key query for a non-enabled or absent entry returns the not-found response **and `EntryMissing` is reported only for the Agent's own selected entry inside `AgentReadinessStatus`**." AD-10 then separately states that "not-enabled" (among other reasons) is one of the states that make `Callability` = `Blocked` inside a `ProviderReadinessResult` — i.e., a reason-coded, non-absent response, for the Agent's own entry.

**Unit A - "Provider catalog query API" (implements AD-2 literally).** Builds the generic by-key catalog query used by every caller, including the readiness path: if the (`ProviderId`,`ModelId`) key is not present in the caller tenant's `TenantProviderEnablement` list, the query returns the absent-key sentinel — full stop, with no special case, because AD-2 states the rule with no carve-out and Consistency Conventions reinforces "absent and cross-tenant keys return the identical not-found response."

**Unit B - "AgentReadinessStatus / `agent-setup` projection" (implements AD-10 literally).** Builds `AgentReadinessStatus.EntryMissing` on top of that same by-key query, assuming it can distinguish "the Agent's own previously-selected entry became not-enabled/disabled" (which must render a reasoned `Blocked` `ProviderReadinessResult` with `ReasonCode` = e.g. `EntryDisabled`/`NotEnabled`) from "no such entry ever existed" (a different, harmless case) — because AD-10 explicitly promises this distinction exists ("`EntryMissing` is reported only for the Agent's own selected entry").

**Collision:** Unit A's implementation is indistinguishable-by-construction: once a previously-enabled entry is disabled or de-enabled for the tenant, Unit A's query returns the *identical* absent-key response it would return for a `ModelId` that never existed. Unit B has no signal left to build `EntryMissing` or any reason code from — it can only render "unknown provider," not "your Agent's provider went away," which breaks the FR-9/FR-24 requirement (AD-10's whole `EntryMissing` carve-out exists specifically to support telling an administrator *their configured Agent* lost its provider). Either Unit B silently violates AD-2's absent-key contract by building a privileged side-channel query that leaks entry existence for the Agent's own key (violating tenant-isolation intent), or Unit A's literal reading makes Unit B's contractually-promised behavior structurally impossible to build.

**Suggested fix:** AD-2's absent-key rule needs an explicit, spine-level exception matching AD-10's: "...except that a query scoped to an Agent's own previously-snapshotted or currently-selected `ProviderId`/`ModelId` may report `EntryMissing`/reason-coded `Blocked` instead of the absent-key response." Alternatively, split the query surface explicitly into two named contracts (a hard-blind generic catalog browse query vs. a self-scoped readiness query) so no single "by-key query" implementer has to reconcile the two rules unaided.

## Finding 3 - Independent Agent-configuration version counters are named but never disambiguated (HIGH)

**ADs in tension:** AD-4 ("`ConfigurationVersion` increments on every accepted `Agent` configuration or lifecycle event"), AD-21 ("regeneration ceiling and proposal expiry duration are `Agent` configuration written by the Tenant Agent Administrator... through `AgentSetupMutation`... and increment `ConfigurationVersion`"), AD-8 ("adopting a Conversations owner field requires an AD-8 amendment and a new `ApproverPolicyVersion`; in-flight interactions keep their snapshot"). The interaction snapshot (AD-4) lists `ConfigurationVersion`, `InstructionsVersion`, and `ApproverPolicyVersion` as three separately-named fields, implying three independent counters, but no AD states which `Agent`-aggregate event types bump which counter(s), or whether they are independent at all.

**Unit A - "Agent setup mutation handler" (builds `AgentSetupMutation` broadly, covering response mode, regeneration ceiling, proposal expiry, and — since AD-8 calls `ApproverPolicy` "Agents-owned configuration" — approver-policy source edits too).** Reads AD-4's rule ("increments on every accepted Agent configuration... event") as globally true and implements one counter: every accepted `AgentSetupMutation`, including an `ApproverPolicy` source edit, increments the single `ConfigurationVersion`, and derives the snapshot's `ApproverPolicyVersion` as simply "the `ConfigurationVersion` at last approver-policy edit," i.e., a value that also moves whenever an unrelated field (e.g., proposal expiry duration) changes, since the aggregate doesn't track a separate approver-policy-only counter.

**Unit B - "Approver Policy Resolution" story (implements AD-8 literally).** Assumes `ApproverPolicyVersion` is its own monotonic counter that changes **only** on an approver-policy-affecting event (source list edits, the future Conversations-owner-field amendment), because AD-15 states "pending proposals are queryable by `ApproverPolicyVersion`" as a first-class filter distinct from configuration churn, and because AD-8's amendment sentence talks about "a new `ApproverPolicyVersion`" as a deliberate, rare event, not something that moves on every regeneration-ceiling tweak.

**Collision:** Under Unit A's build, a Tenant Agent Administrator lowering the proposal-expiry duration (an unrelated, frequent operation) silently bumps the same counter Unit B's queries and AD-8's "in-flight interactions keep their snapshot" logic treat as the approver-policy epoch. Any consumer built to Unit B's assumption (e.g., a UI "pending proposals by `ApproverPolicyVersion`" filter, or a background job re-validating that in-flight interactions still match the current approver-policy epoch before some future scope change) will see spurious epoch changes on every benign edit, either forcing unnecessary re-resolution churn or — worse — masking a real approver-policy change if Unit A's counter is already "noisy" and a downstream consumer starts ignoring single-increment deltas as expected noise.

**Suggested fix:** AD-4 (or AD-8) should enumerate, or at minimum characterize by rule, which `Agent` event types bump `ConfigurationVersion` versus `InstructionsVersion` versus `ApproverPolicyVersion`, and state explicitly whether these are independent monotonic counters on the same aggregate or derived/mirrored from one another.

## Finding 4 - Per-Party rate-limit/concurrency attribution at regeneration time is ambiguous between `CallerPartyId` and `OnBehalfOfPartyId` (MEDIUM-HIGH)

**ADs in tension:** AD-21: "one atomic `BudgetLedger` `AdmitCall` command at FR-8 step 4 enforces the per-Party and per-Conversation windows and the `MaxConcurrentNonterminalInteractionsPerParty` set... and records the consumption." AD-30: "`OnBehalfOfPartyId` is the Party whose command initiated the current step (the caller for the first generation, **the requesting Approver for a regeneration**) and **is the Party charged by per-Party limits**, with `CallerPartyId` carried separately." AD-13's numbered pipeline places `AdmitCall` inside the original **acceptance** sequence (step "rate limits" before reservation) for the *interaction's* first generation, but regeneration is a later, separate flow (AD-5, "Regenerated" state; AD-13 "regeneration (a new descriptor)... `AttemptOrdinal` increments").

**Unit A - "Cost Reservation & Rate Limits" story (builds `BudgetLedger.AdmitCall` and its per-Party counters as a single ledger keyed by `CallerPartyId`, since `AgentInteractionId` itself is derived from `CallerPartyId` per AD-29).** Treats the entire interaction — original generation and every subsequent regeneration — as one economic unit charged against the original caller's per-Party window and `MaxConcurrentNonterminalInteractionsPerParty`, incrementing once at acceptance and decrementing once at interaction termination. Regeneration attempts do not call `AdmitCall` again against a different Party because, in Unit A's model, "per-Party" means "the Party who owns the interaction."

**Unit B - "Confirmation/proposal workflow — regeneration" story (implements AD-30's `OnBehalfOfPartyId` literally for every AD-13/AD-21 gate a regeneration attempt re-runs, since AD-4/AD-11/AD-20 all require every provider-dependent step to "re-read"/"re-run" its gates for each new attempt).** When an Approver (a different Party from the original caller) requests a regeneration, Unit B's `AdmitCall`-equivalent recheck charges the **Approver's** per-Party window/concurrency bucket, per AD-30's explicit statement that `OnBehalfOfPartyId` (the Approver, here) "is the Party charged by per-Party limits."

**Collision:** If a tenant enables strict `MaxConcurrentNonterminalInteractionsPerParty`, Unit A never touches the Approver's counter (so an Approver who regenerates ten different callers' proposals never gets rate-limited, defeating the control's intent), while Unit B debits the Approver's counter on every regeneration but the increment/decrement pairing is asymmetric — nothing in the spine says who "releases" that per-Approver charge, since AD-21's release/settlement rules are all phrased in terms of the interaction's reservation (`BudgetLedger` owns "reservation balance and settlement," singular, per interaction), not per-attempt per-charged-Party accounting. A team building the release/expiry sweep (yet a third unit, following AD-21's interaction-level release rules) would release only the original caller's slot, permanently leaking Approver-side concurrency slots under Unit B's scheme, or double-counting under a naive reconciliation between the two models.

**Suggested fix:** AD-21 should state explicitly whether `AdmitCall`'s per-Party window and `MaxConcurrentNonterminalInteractionsPerParty` are keyed by `CallerPartyId` (interaction owner) for the whole interaction lifetime, by `OnBehalfOfPartyId` per attempt (requiring a defined release rule per attempt, not per interaction), or both — and if both, how each is incremented and released independently.

## Finding 5 - "Retry-window clock paused" under the kill switch has no defined pause/resume accounting rule (MEDIUM)

**ADs in tension:** AD-5: "`PostingFailed` allows a bounded audited retry of at most 3 attempts within 15 minutes of the first `PostingFailed` command's `EvaluatedAt`." AD-12: pulling the kill switch "...suspends `PostingFailed` and administrative retries **with the retry-window clock paused**..." AD-28 (Time Authorities) defines exactly three instant kinds — `DomainInstant`, `EvaluationInstant`, `SchedulingInstant` — none of which models an accumulating elapsed-active-duration across a suspend/resume cycle; it only supports point-in-time deadline comparison (`EvaluatedAt >= deadline`).

**Unit A - "Kill switch suspend/release" story (Authorization epic).** Implements "pause" by recording a `KillSwitchPulledAt` instant and, on release, computing a new effective deadline as `original deadline + (ReleasedAt - PulledAt)` — i.e., shifts the AD-5 15-minute boundary forward by exactly the paused duration, preserving previously-elapsed retry time. This requires storing and carrying forward an accumulated-pause-duration field that AD-28 never names as a stored quantity.

**Unit B - "PostingFailed retry" story (Interaction epic), built independently against AD-5's literal wording ("within 15 minutes of the first `PostingFailed` command's `EvaluatedAt`").** Since AD-5 anchors the window strictly to a fixed `EvaluatedAt` origin with no mention of pausing at all (the pause behavior is only described in AD-12, a different AD with a different binds-list — FR-19..FR-21, FR-28, FR-33 — not FR-13..FR-18 which AD-5 binds), Unit B implements the window as a simple fixed 15-minute wall-clock deadline from the original `EvaluatedAt`, with no pause logic, and treats "suspend...retries" during kill-switch as merely "reject new retry attempts while stopped," letting the fixed-origin window keep expiring in the background.

**Collision:** Under Unit A, a `PostingFailed` proposal that was paused for, say, 2 hours during an emergency stop gets its 15-minute budget preserved and shifted, so a retry attempt 10 minutes after release (12 minutes of *actual elapsed retry time*) succeeds. Under Unit B, the same proposal's fixed-origin window silently expired hours ago during the pause, so the identical retry attempt is rejected as out-of-window even though, from AD-12's promise, the clock was supposed to have been "paused" and therefore should not count that time against the bound. Two units each fully satisfying their own AD's literal text produce opposite accept/reject outcomes for the same audited-retry-bound decision — a governance-visible discrepancy (the retry bound is an audited number, AD-5/A-7).

**Suggested fix:** AD-28 or AD-5 should name the stored quantity precisely (e.g., an accumulated `PausedDuration` field on the proposal, updated at kill-switch pull/release, with the effective deadline defined as `origin + window + PausedDuration`), and AD-5's binds-list should cross-reference AD-12's pause behavior so a builder working from AD-5 alone cannot miss it.

## Finding 6 - `ConversationAgentState`'s "index of non-terminal proposals" has no defined synchronization owner, and its automatic-mode coverage is unstated (MEDIUM)

**ADs in tension:** AD-2 defines `ConversationAgentState` (`TenantId`, `ConversationId`) as owning "membership-established fact, the Agents-owned block, and **the index of non-terminal proposals for that Conversation**" as durable aggregate state (not a projection). AD-7 requires that on detecting an external removal, the membership step "record[s] the external removal on that aggregate at its expected revision, which sets the block, **abandon[s] that Conversation's non-terminal proposals**, and reject[s] with `RemovedInConversations`" — implying the fan-out from `ConversationAgentState`'s index to individual `AgentInteraction` abandon commands. AD-3 requires this fan-out to happen in orchestration, not inside either aggregate's `Handle`. AD-5 states only `Posted`, `Rejected`, `Abandoned`, `Expired` are terminal, so `PostingFailed` (including from **automatic-mode** posting, per AD-5's "Automatic-mode posting shares the same bound... records terminal `PostingFailed`... the sole recovery is a new Agent Call" — note: AD-5 calls this state "terminal" for automatic mode specifically, in apparent tension with the general state list where `PostingFailed` is not in the terminal set) is ambiguous as to whether it belongs in the index at all.

**Unit A - "Confirmation/proposal workflow" story.** Builds the index-maintenance orchestration step as part of every proposal-state-changing workflow activity in the *confirmation* path only (create/edit/regenerate/approve/reject/abandon/expire), dispatching an idempotent add/remove command to `ConversationAgentState` alongside each `AgentInteraction` event, including `PostingFailed` (since, per the general AD-5 state list, `PostingFailed` is explicitly not terminal and therefore must remain indexed so a later external removal can reach and abandon it).

**Unit B - "Automatic response posting" story.** Reads AD-5's sentence "records terminal `PostingFailed`... the sole recovery is a new Agent Call" for the automatic-mode path as meaning automatic-mode `PostingFailed` proposals are terminal and therefore never enter (or are immediately removed from) `ConversationAgentState`'s index — since, in Unit B's model, there is nothing left to abandon once a "terminal" outcome is recorded, and building index-add/remove plumbing for a state its own AD calls "terminal" seems like dead code.

**Collision:** An automatic-mode `PostingFailed` proposal built by Unit B is invisible to `ConversationAgentState`'s index. If the Facilitator later removes `hexa` from that Conversation, AD-7's guaranteed fan-out ("abandon that Conversation's non-terminal proposals") never reaches that proposal — because Unit A's abandon-sweep orchestration walks the index Unit B never populated — leaving an orphaned `PostingFailed` proposal that (per AD-5) "persists until... the Tenant Agent Administrator administratively retries it or... abandons it... or the system abandons it," but the system-abandonment trigger (`RemovedInConversations`, per AD-5's own typed-reason list) can now never fire for this proposal, since AD-7's only fan-out is index-driven and this proposal isn't indexed. This is a genuine collision because both units can defend their reading from the text: AD-5's own wording is internally inconsistent about whether automatic-mode `PostingFailed` is terminal.

**Suggested fix:** AD-5 should stop calling automatic-mode `PostingFailed` "terminal" (it should use the same non-terminal vocabulary as the general state list, since its own next clause describes a persisting, abandonable proposal), and AD-2/AD-3 should name the orchestration step and idempotency key responsible for keeping `ConversationAgentState`'s index synchronized with every `AgentInteraction`'s proposal-state transitions, explicitly including automatic-mode `PostingFailed`.
