# Implementation Conventions - Command Steps

This companion defines the target command-step convention under [AD-3](ARCHITECTURE-SPINE.md#ad-3---pure-aggregates-side-effects-outside). The [architecture spine](ARCHITECTURE-SPINE.md) remains authoritative; this note specifies how to implement its pure-aggregate boundary consistently. Only the examples explicitly labeled shipped describe current implementation. If the two documents diverge, the architecture spine prevails.

## Normative Pattern

A command step MUST use an impure, fail-closed Server orchestrator around a pure EventStore aggregate:

1. The orchestrator performs dependency reads, authorization, measurement, external calls, and other I/O only when the operation's durable authorization facts permit them. It reduces those observations to one server-trusted result for the step. When a target mutation, protected-content access, dependency read, or external effect requires a prior durable authorization fact, the workflow is split into separate command steps: the first command records that authorization at the expected revision, only the resulting event permits the I/O, and a later result command records the observed outcome.
2. Structural, response-mode, authorization, and cancellation exits MAY return or propagate without dispatch. Once the step has one audit-worthy durable result, the orchestrator MUST build and dispatch at most one trusted command and envelope. An evaluated dependency failure SHOULD travel in a content-safe failure-result command when the failure itself requires durable audit evidence; that result carries only the safe classifications and evidence allowed by [AD-14](ARCHITECTURE-SPINE.md#ad-14---sensitive-content-and-secret-safety), never raw dependency payloads or exceptions.
3. The aggregate `Handle` method MUST enforce authoritative state, idempotency, terminal-state, and command-precondition guards before policy evaluation. A rejection or no-op at this seam does not call the policy.
4. An accepted command delegates to an internal, pure, deterministic twin-policy. `Evaluate` maps the trusted result to durable event(s); `Decide` maps that same result to the safe status returned by orchestration. Both MUST call one private `Compute` implementation so their result-to-decision mapping cannot drift. This guarantee applies only after the aggregate's authoritative guards accept the command; it does not bypass a rejection/no-op or assert that dispatch was durably accepted.
5. On a dispatching path, the orchestrator dispatches that command once and returns `Decide` for the same trusted result. It MUST NOT reproduce the policy decision independently.

"Single command" is a write-round-trip ownership rule for one durable step, not a claim that a multi-step workflow dispatches only once or that every command emits one event. A retry is a later invocation and MUST reuse the same deterministic command identity and idempotency metadata under [AD-13](ARCHITECTURE-SPINE.md#ad-13---idempotent-external-effects); it does not authorize a second distinct command for the same step or attempt. One accepted command MAY return multiple events together only when they are one atomic domain decision and no external observation or effect belongs between them. Posting is deliberately three durable steps: `ApproveProposedAgentReply` records only `Approved`; after full pre-post validation, `BeginPosting` records only `PostingPending(PostingAttemptId, MessageId, Deadline)`; only that committed event authorizes `AppendMessage`; `RecordPostingSucceeded` or `RecordPostingFailed` later records its result, with lost acknowledgement resolved by the same deterministic `MessageId` lookup. No policy may emit `Approved -> PostingPending -> Posted|PostingFailed` in one result.

Interaction creation is directory-first, while Product-fixed FR-8 membership remains step 10 immediately before acceptance. `RegisterInteractionPermit` targets `ConversationAgentState` and atomically appends the content-free `InteractionCreationPermitted` fact plus one target-limited durable creation outbox protected through the target interaction's explicit key alias; this registers intake but is not `AgentCallAccepted` and performs no membership read/join. Only that outbox may create the named `AgentInteraction`; the first append emits the reciprocal directory acknowledgement plus the sole workflow-start outbox. The interaction then executes rate/open step 5, Confirmation-only Approver step 6, Context step 7, Budget step 8, safety step 9, and leased membership step 10 before acceptance. Rate/open, Budget reservation, and capacity acquisition are unleased external phases: each begins only after the interaction appends its exact `RateAdmissionAuthorized`/`OpenInteractionLeaseAuthorized`, `BudgetReservationAuthorized`, or `CapacityAdmissionAuthorized` capability, and each records its result/acknowledgement separately.

Every workflow start, Confirmation-mode call-time or scheduled Eligible Approver resolution, Context read, membership read/join, Provider invocation, generated/edit/regeneration/resolution mutation, and Conversation post uses four directory-owned phases. Before leasing, orchestration may perform only the closed content-free owner-local checks for target identity, operation shape, principal binding, expected revisions, and migration/barrier state. `ConversationEffectLease:Acquire` then appends `Reserved` and authorizes nothing. `CommitConversationEffect` conditionally changes that same lease to `CommittedToEffect` at the `ConversationAgentState` expected revision before the first target mutation, protected-content access, safety/roster/Conversation or other dependency read, or external effect; only the commit revision may authorize that deterministic phase and its typed positive or negative result. The target result and any external lookup/Budget/capacity/posting settlement then precede `Settled`. A request-scoped deletion Closing competes with acquire/commit on that same owner, atomically changes every losing reservation to `CancelledBeforeCommit`, manifests every winning committed lease as must-settle, and rejects later matching acquisitions/commits after the EventStore admission fence. A stale worker holding reserved evidence therefore cannot act. A workflow-start commit settles at the first durable workflow checkpoint; a cancelled reservation records `StartSuppressedByDeletion`. After capacity admission is durably recorded, the Provider lease commits generically without a non-owner decision read. The next interaction step observes the reserved-system output-status authority and records exactly one branch. An effective exact authority appends `ProviderInvocationAuthorized`, phase-pinning its decision revision, contract digest, selected status/reason/metric/open-lease mapping, catalog activation, and observation before Provider work. Open, missing, malformed, or unavailable authority instead appends content-free `ProviderInvocationNotAuthorized` plus exact pre-invocation Budget/capacity dispositions; those revisions release/acknowledge the existing identities, record the negative target result, and settle the committed lease without Provider work. A recorded branch never re-reads a successor. Provider error/timeout records content-free `GenerationFailed`; output-safety denial/unavailability records only the authorized branch's phase-pinned Product-selected mapping. Both branches have proposal/version/content fields absent. If deletion Closing wins after capacity queue/admission but before a Provider authorization branch, an exact allocator lookup plus proof that no authorization/begin/active state exists permits only `PreProviderCapacityDispositionDecided(CancelNoInvocation)`, release, and acknowledgement of that existing identity; absence alone cannot invent no-use. Only allowed output requires a separate committed `ProposalMutation(RecordGeneratedVersion)` lease before persistence; if Closing cancels it, content is discarded and only the Provider's safe outcome/settlement is recorded. Approval safety and each pre-post safety/Conversation read occur after their `ProposalMutation` or `ConversationPosting` commit and bind even a no-mutation/no-post result to that lease. A User-origin edit, regeneration, approval, rejection, or abandonment atomically reserves its `ProposalMutation` lease with an immutable target-limited action-intent outbox; edited bytes are sealed under the interaction DEK. Commit binds that intent, and either the original request or the exact Interaction Workflow recovery variant records the same intent-bound positive/negative target result before acknowledging the outbox and settling the lease. Recovery records the original human initiator and Workflow executor separately and never impersonates fresh human authority.

Every governance operation carries canonical `GovernanceScopeV1` and its SHA-256 predicate digest. Exact sorted interaction ids are executable; the exact-Conversation wire form is executable without another Product choice only for PRD-fixed `ConversationApprovedDeletion`. Human-origin exact-Conversation hold/export/operator deletion rejects before fence, cut, or inventory while `OD-HUMAN-EXACT-CONVERSATION-SCOPE-1` is Open. Membership comes from tenant target-stream identity, immutable first-event/directory-permit `SourceConversationId`, and permit/action/lease/phase-authorization owner facts. Unknown, malformed, cross-tenant, or unverifiable membership rejects a write. The `ClassUtcRange` form is forbidden while `OD-GOVERNANCE-CLASS-RANGE-SCOPE-1` is Open; implementation must not invent a class vocabulary, clock field, boundary semantics, human exact-Conversation time semantics, later-content treatment, or fence lifetime.

Both deletion origins use the same named matrix cut before candidate construction. First, an authorize/effect/result protocol installs an ordinal EventStore scope admission fence, blocking later matching permits, protected User-action intents, lease acquisitions/commits, and rate/open/Budget/capacity phase-authorizations. From its authenticated checkpoint the Workflow freezes the finite `ConversationAgentState` owner cohort and creates one immutable cut cycle keyed by (`DeletionRequestId`, scope digest, `AdmissionFenceOrdinal`) on each owner, then converges the exact permit/outbox/lease/phase-authorization/rate/open/Budget/capacity/posting manifest to Effective. A successor ordinal creates separate owner cycles whose manifests carry every still-restrictive prior obligation plus the violating/new winner; it never changes an old Effective fact back to Closing. Only the same-ordinal owner-receipt fixed point plus authenticated `ZeroAcceptedViolationsSinceInstall(InstallCheckpoint, VerifiedHighWater)` permits a reversible candidate; prior ordinal violations remain append-only and visible. Candidate, acceptance, content-fence authorization/binding, and prepare reverify that current-ordinal proof. Accepted-violation containment has two explicit idempotent branches: before the first global cut it proves that cut/candidate/token are absent; afterward it invalidates only exact present revisions. Either branch assigns one successor ordinal and preserves every restrictive fence/cycle. Acceptance binds the canonical predicate, global cut, current migration `Ready` epoch/guard receipt, and namespace high-water. The content guard is independently immutable at (`DeletionRequestId`, scope digest): the initial authorize/effect/result installs it and its first ordinal/token binding; after one or more recuts, a separate authorize/effect/result appends the new binding only after proving continuous installation, unchanged predicate, the latest actually installed binding, the complete gap-free ordered chain of intervening invalidated/tokenless ordinal containment receipts, new global cut, and current zero proof. A binding authorization overtaken by another violation returns terminal `ObsoleteBindingAuthorization` without changing the guard; the next authorization extends the chain from the latest installed binding. It is never silently reused, removed, or reinstalled. A content conflict performs no preparation and refreezes under the same request/predicate after exact lookup.

The EventStore guard assigns the authoritative ordinal at an accepted matching append's own linearization instant. Its `AdmissionGuardEvaluationReceipt(AcceptedAtAdmissionFenceOrdinal, AcceptedAtGuardHighWater, CallerPresentedOrdinal?)` is atomically stored in the then-current partition; caller evidence never selects the partition, and successor installation serializes with that assignment. Delayed detection follows the receipt. Missing/unverifiable acceptance-time evidence is `AdmissionIntegrityUnattributable`, contaminates current clean evidence, and blocks deletion. This is the only meaning of current `ZeroAcceptedViolationsSinceInstall`.

The final irreversible boundary is another authorize/effect/result protocol, not a clean read followed by a `ProtectionFence` append. The single tenant `GovernanceScopeGuard` is shared by hold registration and deletion sealing. Every already-authorized hold request conditionally registers its canonical scope there before `ProtectionFence` prepare; this guard commit is the hold-contention instant, exact lookup recovers loss, and the contender remains until exact release/unpin/fence receipts authorize its guard release. `AuthorizeDeletionDestructionStartBarrier` records the exact observed `GovernanceScopeGuard` revision/compare token, current ordinal zero proof, current content binding/checkpoint, migration/fence receipts, accepted token, immutable sorted key-target manifest/digest, and phase-pinned values. Only its exact revision may call `CommitDeletionDestructionStartBarrierEffect`, which conditionally appends at that observed guard revision and serializes with every admission write and overlapping hold registration/release. Any intervening guard mutation returns authenticated stale; reauthorization binds the new revision only after that result is mirrored. A contender that wins after authorization makes that authorization stale; while the hold-precedence decision is Open neither branch advances, and only an exact effective deletion-allowed disposition may be consumed atomically with `DestructionSealed`. Sealing is `DestructionStarted` and returns one deterministic non-expiring, revocable, single-use `DestroyDekManifest` capability for the whole accepted manifest, not a reusable bearer. It has no `ExpiresAt` or logical-capability renewal path. A post-seal hold attempt conditionally appends guard-owned `PostStartHoldContenderObserved(..., DestructionAlreadySealed)` and changes the guard revision; it is mirrored by exact lookup and, while its exact Product disposition is Open/missing/mismatched, blocks any unconsumed accepted batch, new containment issue/consume, purge, and completion. Already-consumed vectors cannot be recalled. Only an exact effective deletion-allowed outcome may be bound as `PostStartHoldDispositionApplied` to each later batch/completion step; a hold-allowed outcome grants no destruction.

Each batch uses `DeletionBatchCapabilityV1`, an ES256 detached JWS over RFC 8785 canonical fields including issuer, committed protection-target audience, tenant/request/stable destruction-seal id, batch kind/ordinal/id, manifest digest, guard stream/intended issue revision, attestation ordinal, signing-attempt ordinal, and key version. The actual successful `CommittedIssuedGuardRevision`—`CommittedDestructionSealGuardRevision` for the accepted batch—is result evidence recorded separately and is excluded from the seal id, batch id, signing request id, and signed bytes. A recorded authorize/sign/result step invokes only the `EXT-SECRETS-1` `DeletionBatchCapabilitySigningKey`; the guard issue commit records the exact active attestation. Before protection, a separate `AuthorizeDeletionBatchDispatch` → guard-revision-conditional `CommitDeletionBatchDispatchEffect` → issued-or-stale mirror binds that batch/manifest/attestation, the current post-start-hold disposition if required, and the observed guard revision. An earlier unresolved hold or intervening guard mutation returns stale and no dispatch. A winning `DeletionBatchDispatchAuthorized` is uninterruptible only against a later hold for that batch; that hold is durably ordered after it, cannot cancel possibly begun work, and still blocks other batches/purge/completion. `EXT-PROTECTION-1` verifies both the public anchor and a linearizable exact lookup of that active dispatch receipt before consuming; signature-only or batch-issue-only acceptance is forbidden. Routine rotation keeps prior public anchors through batch/outcome retention. Emergency compromise enters through the non-public registrar and races the protection-owner block against reservation; it preserves reserved/consumed outcomes and may re-attest an immutable batch under a healthy key only from an exact capability-compromise-blocked owner state by expected-revision authorize/sign/commit/result followed by successor dispatch and owner activation: same batch/manifest, incremented attestation ordinal, old attestation revoked, exactly one active credential. If compromise follows dispatch but precedes consume, a successor dispatch authorization is required after re-attestation. Unknown status remains blocked.

The current capability protocol additionally binds `SigningAttemptOrdinal` and `IntendedIssuedGuardRevision` into both signed bytes and `DeletionBatchCapabilitySigningRequestId`. The once-assigned destruction-seal id and batch id survive every such retry. A signature whose guard issue loses must be proven never issued by exact guard lookup and recorded as terminal `SignedAttestationObsoleteUnissued` before a successor pre-issue attempt keeps the same batch/manifest/attestation ordinal, increments only the signing-attempt ordinal, and binds the returned current guard revision; two or more consecutive stale issues retain the same seal/batch identities while producing distinct terminal signing attempts. Emergency re-attestation remains a distinct post-issue path.

After dispatch, admission-integrity/key-compromise cancellation and irreversible consumption share the protection owner. `BlockDeletionBatchConsumption` and `ReserveAndConsumeDeletionBatch` race one local state transition; `ConsumptionReserved` is the irreversible instant for those reasons. Guard facts block new issue/dispatch/purge/completion immediately but are `BatchBlockPending` for an already-dispatched batch until the exact protection result is known. Re-attestation requires the protection-owned `ConsumptionBlocked(CapabilityKeyCompromise)` receipt, keeps that state blocked while guard replacement and successor dispatch are recorded, and reopens only through `ActivateReattestedDeletionBatch` at the same owner. Activation binds the replacement key, next attestation, successor dispatch, expected blocked-batch revision, and expected tenant-key block-set revision, and atomically requires no replacement-key block at that revision. If that key is already blocked or its block wins the compare, activation returns `ActivationBlockedByReplacementKeyCompromise` and leaves/places the batch in the new key's exact `ConsumptionBlocked` state for another re-attestation; it never clears a global key block. A later legal hold remains intentionally ordered at guard dispatch and does not use this cancellation path.

Post-seal containment deduplicates on `(TenantId, AgentInteractionId, TargetProtectionKeyAlias)`. The `ProtectionFence` target-coverage index maps every violation resource to one accepted or containment batch target. Same-target observations append non-authorizing `ViolationCoveredByDeletionBatch`; they allocate no new ordinal or capability and use the original batch/vector, including `AlreadyDestroyedByBatch` after consumption. Only a previously uncovered target gets a new singleton containment ordinal. Different uncovered targets remain distinct, changed/cross-tenant aliases conflict, and every newly observed copy still requires its own purge accounting.

Completion is also authorize/effect/result. `AuthorizeDeletionCompletionBarrier` freezes every batch/coverage/vector/copy receipt, current admission ordinal/acceptance high-water/content binding, exact post-start disposition if required, and observed guard revision. `CommitDeletionCompletionBarrierEffect` conditionally appends at that revision and atomically verifies the complete current guard state; any intervening admission, content, hold, release, containment, capability, or other guard mutation returns `DeletionCompletionAuthorizationStale`, which must be mirrored before retry. A winning `DeletionCompletionSealed` rejects every later matching write; only its exact lookup may be mirrored as `DeletionCompleted`. A direct completion append is forbidden. A post-seal admission integrity failure invokes `BlockDeletionBatchConsumption` to race `ReserveAndConsumeDeletionBatch` at the protection owner, records `DeletionIntegrityCompromised`, and blocks new batches/further destruction/completion; a consumed vector cannot be recalled. Conversation-origin deletion never Abort. Operator-origin deletion also only Resume/retries while its cancellation decision is Open; if an approved outcome permits Abort, cleanup precedes removal of every admission ordinal plus the continuous content guard/all bindings and release of every owner/ordinal cycle, all before sealing. Operator nonterminal work likewise stays Closing while its decision is Open; no implementation invents a Product outcome.

Before this path is enabled, the Platform-Operator-started migration Workflow quiesces ingress/writers, inventories the finite legacy cohort, installs the EventStore namespace epoch guard and revokes legacy direct-write authority, backfills every member, and proves protected-or-exact-empty content plus two post-fence identical scans. An accepted late legacy write invalidates the directory. Repair records the old/successor plan first, then uses a committed authorize/effect/result boundary to atomically install the directory-repair fence, revoke new permit/outbox/lease-acquire/lease-commit and rate/open/Budget/capacity phase-authorization capability, and obtain the directory/effect-authorization checkpoint. Only after that receipt may it freeze all current permit, creation/workflow-start/User-action-intent outbox, lease, unleased phase-authorization/result/acknowledgement, acceptance-time guard receipts/current-ordinal contamination high-waters, active deletion ordinal/violation-chain/cut-cycle/content-binding, barrier/containment/batch-dispatch/completion observed-guard-revision authorization/stale outcome, post-start hold/disposition facts, protection-target coverage/`AlreadyDestroyedByBatch` links, seal/batch guard-issued/dispatch and capability-attestation/revocation state, completion seal, and referenced protection-owner consumed-or-revoked outcome. The bridge accepts only that finite pre-fence cohort; reserved intents/leases cancel before effect, committed intents/leases reach their exact result, acknowledgement, and settlement, and already-authorized unleased phases reach only their exact result/disposition and acknowledgement. Successor activation compares every checkpoint/high-water and preserves all those facts without creating or changing Product outcomes, batch authority, or completion. It then atomically revokes the old epoch, repair fence, and bridge. `OD-LEGACY-PLAINTEXT-DISPOSITION-1` remains Open and blocks nonempty plaintext; no outcome-specific procedure is inferred. These steps follow the normal pure-command convention and are not pre-command exceptions.

Export-key release follows the same authorize/effect/result rule. `ExportDownload:AuthorizeKeyDelivery` appends only the stable delivery identity and principal/purpose/expiry/commit/version evidence; the custodian receives that committed authorization, delivers directly and idempotently to the principal, and supports exact outcome lookup. The result/recovery command stores only safe Delivered/NotDelivered/Indeterminate evidence. A lost acknowledgement is looked up before the same delivery id can retry; expiry, authority revocation, or unknown outcome never causes a new identity or inferred success, and raw key bytes never enter Agents.

The only pre-command exceptions are the three capabilities closed by AD-3 and AD-30. `RegisterTrustedEnvelopeFirstSeen` may run only the pure `TrustedEnvelopeReplay` handler and conditionally append only `TrustedEnvelopeFirstSeen` to the exact reserved-system (`Issuer`, `DeliveryNonce`) stream. `RecordSecurityObservation` may durably append one content-free observation to the operational spool, after which its drain worker may run only the pure `SecurityEventLog` handler and conditionally append only `SecurityEventRecorded` to the computed (`RoutingTenantId`, `UtcDay`) stream. `RegisterDeletionCapabilityKeyCompromise` may be invoked only by the platform-composed `IDeletionCapabilityCompromiseRegistrar` from an authenticated `EXT-SECRETS-1` per-tenant key-revocation delivery; it installs only that tenant/key-version block at `EXT-PROTECTION-1` and mirrors only the exact protection receipt as `DeletionBatchCapabilityKeyCompromiseObserved` on the tenant guard. None carries an Agents principal or recursive envelope, invokes the ordinary orchestrator pattern, or authorizes another target/event/stream/operation. Generic conformance tests MUST allow exactly these three target-limited paths and reject every other direct append or capability bypass.

Authorization handling remains operation-specific. Edit and regeneration can deny before dispatch; approval can dispatch a denied result when durable failure evidence is required. Either form obeys the at-most-one-command rule.

## Visibility Boundary

Twin-policies are domain implementation details and MUST remain `internal`. The domain assembly grants `InternalsVisibleTo` to its own domain tests and to `Hexalith.Agents.Server`, which must call `Decide`; it MUST NOT grant domain-internal access to `Hexalith.Agents.Server.Tests`. The canonical boundary is [`Hexalith.Agents.csproj`](../../../../src/Hexalith.Agents/Hexalith.Agents.csproj).

## Test Obligations

- Domain tests MUST exercise policy truth tables directly, prove `Evaluate` and `Decide` agree for every result variant, verify ordered multi-event sequences where applicable, and prove aggregate rejections/no-ops occur before policy evaluation.
- Server tests MUST prove zero-dispatch exits and at-most-one dispatch through the orchestrator.
- Posting tests MUST prove the external append is impossible before committed `PostingPending`, a concurrent terminal decision cannot win after that uninterruptible fact, and result/lost-ack commands reuse the exact posting attempt and `MessageId`.
- Interaction/deletion tests MUST prove every lease reservation/commit—including Approver resolution and User-action intents—and every unleased rate/open/Budget/capacity authorization versus the admission fence and owner Closing, stale workers cannot act after `CancelledBeforeCommit`, every committed lease and phase authorization has one durable target/result/settlement/acknowledgement path, workflow start is suppressed when Closing wins, FR-8 failures through safety produce no membership effect, a queued/admitted pre-Provider capacity item cannot be stranded, and every owner reaches a manifest fixed point before the global cut receipt. They MUST prove generic Provider-lease commit precedes the decision read and one immutable authorized/not-authorized branch follows. Deletion tests MUST cover both origins; admission-fence races and ordinal-partitioned evidence; violation containment before the first global cut and after each later artifact; one idempotent successor ordinal; immutable carried-forward cycles; current zero proof; continuous content-guard successor binding after install/preparation, including repeated recuts, gap-free invalidation chains, and terminal obsolete binding authorizations; hold registration/release before/at/after guard-revision-bound barrier authorization and sealing, authenticated stale compare outcomes, and reauthorization; Open-decision stalling; admission and hold serialization at the tenant guard; exact seal lookup; non-expiring capability restore, all-or-none multi-key batch consumption and per-target vector lookup; guard-owned singleton containment-batch authorize/effect/result, duplicate/concurrent allocation, and lost-issuance lookup; batch-revocation races; post-seal integrity blocking; migration preservation; and denial of every unresolved Product branch. Migration tests MUST prove the repair fence/checkpoint precedes cohort freeze, every pre-fence directory/effect winner is included, every post-fence stale append loses, the bridge drains only that cohort, and every admission ordinal/violation-chain/owner cycle/content binding/hold contender/compare authorization/stale outcome/seal/batch guard-issued state and protection-owner outcome survive successor activation.
- Deletion boundary tests MUST additionally prove server-assigned acceptance-time ordinal attribution across successor-install races; post-start hold observation before/at/after accepted and containment consumption with Open/missing/deletion-allowed/hold-allowed dispositions; same-alias distinct-resource coverage before and after original consumption; signature issuer/audience/canonical bytes, routine rotation, emergency compromise enumeration, consume-versus-revoke, and same-batch re-attestation including a second replacement-key compromise before/at activation and after activation but before reserve; stable seal/batch identity across two or more signed-obsolete pre-issue attempts with actual committed issue revision stored separately; and completion authorization versus every late admission/content/hold/containment/capability mutation, including stale lookup/retry and restore.
- Export-key tests MUST prove durable principal/purpose/expiry/version-bound authorization precedes custodian release, deterministic delivery identity is idempotent, exact lookup resolves lost acknowledgement, expiry/revocation around the release instant has one outcome, and key material never traverses Agents state or surfaces.
- Server tests MUST prove no drift without calling the internal policy: capture the dispatched public envelope, deserialize its public command, seed real aggregate state, call the public aggregate `Handle` seam, and compare the emitted decision with the orchestrator's returned status. ## Adoption Checklist

- Identify the single durable step decision and its server-trusted result.
- Classify structural, mode, authorization, and cancellation exits that may dispatch zero commands; classify failures that require durable evidence.
- State the operation-specific authorization and cancellation recording choice instead of inheriting one implicitly.
- Keep all I/O in the orchestrator and all authoritative state/idempotency/precondition guards in the aggregate.
- Dispatch no more than one command for the step result; reuse its deterministic identity on retry, and allow the aggregate to emit the ordered event sequence the decision requires.
- Split every effect that requires durable authorization into authorize/effect/result steps; for posting, persist `Approved`, then persist `PostingPending`, then append externally, then record the result.
- Register interaction creation through the Conversation-owned permit/outbox before workflow start; preserve FR-8 Approver resolution as leased step 6 and membership as leased step 10; durably bind every User proposal action to its protected intent/outbox; reserve, same-owner commit, execute, and settle a Conversation-owned effect lease for every leased content/external-effect phase; and record interaction-owned authorization/result pairs for rate/open/Budget/capacity. Commit the generic Provider lease before observing the output-status authority, then record exactly one authorized/not-authorized branch; phase-pin the approved mapping only on authorization and settle Budget/capacity/lease without Provider on the negative branch. Install the migration and repair fences and prove every legacy/directory/effect member protected, drained, or empty. Implement both deletion origins with server-assigned acceptance-time ordinal receipts, immutable owner/ordinal cycles, explicit pre-cut/post-cut violation recovery, current zero proof, candidate/acceptance, one continuous predicate content guard with gap-chain successor bindings and obsolete outcomes, revision-bound shared hold/deletion scope-guard linearization, durable post-start hold facts, alias-target coverage, non-expiring signed batch capabilities with emergency same-batch re-attestation, guard-owned containment-batch issuance, atomic manifest-batch destruction, and guard-linearized completion sealing. Never implement class/range scope, human-origin exact-Conversation scope, pre- or post-start hold precedence, operator nonterminal terminalization, or operator Abort/removal from an Open Product decision.
- Split export-key delivery into durable authorization, idempotent custodian effect, safe result, and exact-outcome recovery while keeping raw key material outside Agents.
- Implement one internal policy with `Evaluate`, `Decide`, and a shared private `Compute`; do not duplicate decision logic.
- Preserve the domain friend boundary: own tests and Server, never Server.Tests.
- Add domain truth-table tests and public Server cross-seam agreement tests.
- Add a direct-mutation guard test that permits exactly the three AD-3 pre-command capability/event/stream triples and rejects every other bypass; Story 5.4 owns the replay and security-recorder triples, while Story 8.3 owns the compromise-registrar triple.
