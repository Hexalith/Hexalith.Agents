# Architecture Spine - Hexalith Agents

## Design Paradigm

Hexalith Agents is an event-sourced, Dapr-Workflow-orchestrated, hexagonal Hexalith domain module: EventStore aggregates in the `Hexalith.Agents` domain assembly are business truth, replay-safe Server orchestrators and workflow activities coordinate every side effect through ports, adapters implement Conversations, Parties, Tenants, Provider, safety, secret, and FrontComposer integration, and a platform-owned host composes it all.

```mermaid
flowchart LR
  Browser[Authorized browser] --> UI
  Browser --> BrowserTelemetry[Browser-monotonic telemetry]
  Browser --> ConvSurface[Conversations surface<br/>Call hexa via EXT-CONV-UI-1]
  ConvSurface --> Client
  subgraph PlatformBoundary[Platform-owned host boundary - EXT-HOST-1]
    API[Agents DomainService]
    UI[FrontComposer UI]
    Workflow[Dapr Workflow runtime]
    App[Replay-safe Agents activities]
    CapacityGate[Shared durable capacity allocator]
    ReadinessRegistry[Launch-readiness registry]
    Proj[Agents projections]
    EvidenceIngress[Authenticated browser evidence ingress]
    BrowserMetrics[browser-ui-metrics projection]
  end
  UI --> Client[Hexalith.Agents.Client]
  Client --> API
  API --> Workflow
  Workflow --> App
  App --> ReadinessRegistry
  App --> CapacityGate
  CapacityGate --> Generation[Generation activity<br/>optional Microsoft Agent Framework]
  App --> Ports[Ports]
  App --> ES[EventStore command/query boundary]
  ES --> Agg[Agents aggregates]
  Agg --> Events[(Protected Agents events)]
  Ports --> Conversations[Conversations client]
  Ports --> Parties[Parties client/projection]
  Ports --> Tenants[Tenants projection]
  Generation --> ProviderPort[Provider/model port]
  ProviderPort --> Provider[Provider adapters]
  App --> Safety[Content-safety port]

  Proj --> UI
  Proj --> ReadinessRegistry
  BrowserTelemetry --> EvidenceIngress
  EvidenceIngress --> BrowserMetrics
  BrowserMetrics --> ReadinessRegistry
  Evidence[Level 4/5 qualification evidence] --> ReadinessRegistry
  ReadinessRegistry --> API
```

## Invariants & Rules

### AD-1 - Agents Is A Full EventStore Domain Module [ADOPTED]

- **Binds:** all V1 capabilities.
- **Prevents:** proposal, provider, governance, and audit state being split between a transient orchestrator and unrelated modules.
- **Rule:** Hexalith Agents owns durable Agent configuration, provider governance, tenant enablement, Agent interactions, generated/edited/regenerated proposal versions, approval decisions, posting outcomes, budget, safety and governance policy, legal hold, export, deletion, readiness evidence, and operational status as EventStore-backed domain state.

### AD-2 - Aggregate Boundaries And Tenant Scope

- **Binds:** FR-1..FR-18, FR-24..FR-26, FR-28, FR-30, FR-32..FR-34, OQ-20, OQ-28.
- **Prevents:** two owners for one entity, an unbounded tenant-wide hot aggregate, a cross-tenant catalog, or governance state that lives only in a projection.
- **Rule:** V1 aggregates are exactly, with identity key and tenant scope: `Agent` (`TenantId`, `AgentId`; `hexa` is provisioned exactly once per tenant at tenant enablement by an idempotent create-only orchestration under the `Platform` principal, with a tenant-wide response mode, proposal expiry duration, regeneration ceiling, Conversation Context Policy, and immutable Party identity link; the orchestration obtains or creates the Party identity selected by the committed `EXT-PARTIES-1` branch through the Parties adapter under the Agents Service Principal before dispatching the Agent create command; exact replay is a no-op, a divergent second provision is a conflict, and no tenant role may create a second Agent, delete `hexa`, or replace its Party identity), `ProviderCatalog` (reserved EventStore tenant `system`, one stream per `ProviderId` + `ModelId`; provider/model records, capability metadata, versioned pricing, secret reference state, platform enablement), `TenantProviderEnablement` (`TenantId`; which platform entries the tenant may see and select, mutated by the Platform Operator [ASSUMPTION A-10]), `AgentInteraction` (`TenantId`, `AgentInteractionId`; each call, prepared attempts, safety decisions, proposal lifecycle, version history, approval/rejection/abandonment/expiry, posting outcome), `RateLimitLedger` (`TenantId`, `ScopeKind`, `ScopeId`; immutable per-Party or per-Conversation rolling-window consumption), `OpenInteractionLedger` (`TenantId`, `CallerPartyId`; one lease per nonterminal caller interaction), `BudgetLedger` (`TenantId`, `BudgetPeriod` as the UTC calendar month; monetary reservations and settlement in the original period), `TenantGovernancePolicy` (`TenantId`; cost caps, rate limits, tenant safety restrictions, calling restriction [ASSUMPTION A-11], durable SM-4 incident confirmations, trigger-review decisions, and the per-tenant kill switch, all serialized on one governance revision), `ConversationAgentState` (`TenantId`, `ConversationId`; exactly one of `NeverJoined`, `Joined`, `ExternallyRemoved`, `Blocked`, and `ReadmitPending`; monotonic `BlockVersion`; one `CurrentMirror(BlockVersion, Direction, Outcome, AttemptId)`; and an idempotent nonterminal-proposal materialization with interaction-source-revision high-water), `InteractionDirectoryMigration` (`TenantId`; one Platform-Operator-started content-free Workflow/cutover checkpoint, finite legacy-stream count/hash/high-water manifest, per-Conversation reconciliation positions, EventStore namespace write-fence epoch/revocation receipt, directory-repair boundary/checkpoint, and completion/integrity-invalidated state), `AuditInspection` (`TenantId`, `InspectionId`; compliance inspections, never under an interaction key), `SecurityEventLog` (`RoutingTenantId`, `UtcDay`; content-free authorization denials and security events routed exactly by AD-30, where `RoutingTenantId` is an authenticated actor/workflow tenant or reserved `system`, daily-partitioned by the aggregate key as the sole V1 volume mitigation [ASSUMPTION ARCH-A-9]), `TrustedEnvelopeReplay` (reserved tenant `system`, `Issuer`, `DeliveryNonce`; one content-free first-seen record binding target tenant, logical command, canonical-envelope tag digest, key version, and retention deadline), `ContentSafetyPolicy` (`system`; published policy versions with `ChangeKind` and `LastLoosensVersion`), `SafetyVerdictEpoch` (`TenantId`; current/pending epoch, frozen content-free safety-index checkpoint/manifest, bounded worker cursor, and expiring fenced coordinator lease) and `SafetyVerdictIndex` (`TenantId`, `ConversationId`; epoch-local verdict status and source high-water), `LaunchReadinessGate` (`GateId`, `TenantScope`, `EnvironmentProfile`), `ArchitectureDecisionCatalog` (reserved tenant `system`, one fixed stream; append-only pending/effective catalog versions enumerating every required stable `DecisionId`, minimum contract version, baseline affected evaluations, and root/predecessor authorization), `ArchitectureDecisionRecord` (reserved tenant `system`, one stream per catalog-listed `DecisionId`; append-only pending/effective contract versions, immutable predecessor/root-governance authorization, outcome approval evidence, and union-preserving affected evaluations feeding `launch-readiness`), `LegalHold` (`TenantId`, `HoldId`; canonical `GovernanceScopeV1` plus predicate digest), `ProtectionFence` (`TenantId`; low-volume tenant-serialized hold/deletion/export intent, request-scoped admission/effect-cut receipts, continuous content-guard binding receipts, reversible deletion candidates accepted as immutable resource sets only at the fence expected revision with one once-assigned stable `DestructionSealId`, prepare tokens, mutually exclusive prepare-recovery dispositions, and sole export-commit decisions with committed-export index high-water), `GovernanceScopeGuard` (`TenantId`; canonical-predicate hold contenders and releases, deletion admission-fence ordinals and violation partitions, continuous content-guard bindings and ordered invalidation-gap chains, barrier/containment observed-revision compare tokens, immutable destruction seals with actual committed guard revisions, and accepted/containment stable-seal manifest-batch identities plus non-expiring capability key versions and issued state; the protection owner separately owns consumed/revoked outcome), `AuditExport` (`TenantId`, `ExportId`; canonical scope, frozen interaction set, lifecycle-policy version, fence token, manifest and artifact outcome), and `ProtectedDeletion` (`TenantId`, `DeletionRequestId`; origin and canonical scope, admission/effect-cut receipts, reversible inventory candidates, exact `ProtectionFence` accepted-set acknowledgement, prepare acknowledgements, destruction and purge receipts). After provisioning, the Tenant Agent Administrator may configure, activate, disable, and inspect `hexa` but never invoke the provisioning operation. The `Agent` aggregate stores no safety policy; the interaction snapshot's safety version is the pair (`ContentSafetyPolicy` version, `TenantGovernancePolicy` version). Any decision whose wrong answer is unrecoverable (deletion under hold, key destruction, export scope) reads hold and policy state from the owning aggregate at an expected revision, never from a projection. `TenantId` is a mandatory component of every aggregate identity, deterministic id, idempotency tuple, projection key, query cursor scope, allocator call, and ledger call; a query for a key outside the caller's tenant, or for a platform entry not enabled for it, returns exactly the absent-key response, except that a query scoped to an Agent's own currently-selected `ProviderId`/`ModelId`, or to an in-flight interaction's previously-snapshotted entry, may instead report `EntryMissing` or a reason-coded `Blocked` `ProviderReadinessResult` inside `AgentReadinessStatus`, per AD-10 — the one named carve-out from the absent-key rule. A terminal historical interaction uses its immutable snapshot and authorized Audit Evidence and never receives this catalog-existence carve-out.

**Provider data-handling ownership:** `ProviderCatalog` owns the four-field data-handling record (retention term, training-use status, processing region, retained contractual reference), its monotonic `DataHandlingVersion`, and any Platform-Operator-declared tightening classification with the recorded field-level diff. `TenantProviderEnablement` owns the tenant's last accepted version and an explicit accept or decline decision for the current version; platform enablement permits selection but never constitutes tenant acceptance.

**Trusted replay namespace:** The `TenantId` component of every `TrustedEnvelopeReplay` identity is the reserved EventStore tenant `system`, not the target tenant authenticated by the envelope. Its entity key is (`Issuer`, `DeliveryNonce`), and the content-free first-seen record separately binds `TargetTenantId`. Nonce uniqueness is therefore platform-wide per issuer, so reusing one issuer/nonce against a different tenant addresses the same stream and is rejected as changed authenticated data.

**Canonical governance scope:** Every hold, export, deletion request, deletion effect cut, inventory candidate/acceptance, EventStore scope fence, violation, and completion carries one versioned `GovernanceScopeV1` discriminated value plus `ScopePredicateDigest = SHA-256(canonical length-prefixed scope bytes)`. Its wire variants are `ExactInteractions(TenantId, sorted-distinct AgentInteractionIds)` and `ExactConversation(TenantId, ConversationId)`; a `ConversationApprovedDeletion` is always the latter and cannot be coerced. Exact-interaction membership is the tenant-bound target stream plus immutable first-event/directory-permit binding. Exact-Conversation membership is the `ConversationAgentState` identity plus immutable permit/first-event `SourceConversationId`; later appends match that stored binding and exact permit/effect capability, never caller metadata. A permit/action intent exposes membership from its Conversation owner and interaction id; every interaction effect-phase authorization or lease acquire/commit exposes it from the referenced permit. Missing, malformed, unknown-version, cross-tenant, absent-permit, changed-source, or unverifiable membership rejects the write and makes verification incomplete. Only exact interactions and the PRD-fixed `ConversationApprovedDeletion` exact-Conversation variant are executable without another Product choice. Human-origin exact-Conversation hold, export, and operator deletion reject before fence/cut/inventory work while `OD-HUMAN-EXACT-CONVERSATION-SCOPE-1` is Open; Architecture does not choose point-in-time versus prospective semantics, later-content treatment, fence lifetime, or public effect.

The earlier `class:<ContentClass>` plus UTC-range notation is a reserved `ClassUtcRange` variant only; it is not executable while `OD-GOVERNANCE-CLASS-RANGE-SCOPE-1` is Open. That Product + Governance + Security decision must select the closed vocabulary/classification owner, authoritative UTC instant, boundary semantics, and public meaning. Architecture supplies no default. An approved successor adds its canonical fields and EventStore proof to the same schema/digest contract; exact interactions and source-approved exact-Conversation deletion remain independently evaluable.

**Conversation interaction directory, effect cutover, migration, and deletion-origin ownership:** `ConversationAgentState` retains exactly the five FR-2 membership states; orthogonally, it is the EventStore-authoritative content-free directory and effect owner for every derived interaction/failure record of (`TenantId`, `ConversationId`). Its immutable permits name interaction id, logical/request fingerprint, stored source Conversation/revision, creation outbox, protection-key alias, and monotonic high-water; payload exists only as AD-22 `ProtectedContent` sealed under the target interaction DEK and is absent from the directory projection. The aggregate also owns deterministic content-free leases for `WorkflowStart`, `ApproverResolution`, `ContextRead`, `ConversationMembership`, `ProviderInvocation`, `ProposalMutation`, and `ConversationPosting`, each bound to one permit, operation/attempt/target, revisions, and exactly one of `Reserved`, `CommittedToEffect`, `Settled`, or `CancelledBeforeCommit`. Reservation authorizes nothing. Only a same-owner `CommitConversationEffect` won before the first protected read, target mutation, dependency read, or external effect authorizes that exact phase and typed result. After an EventStore scope admission-fence receipt, an immutable owner-cycle `DeletionEffectCut(DeletionRequestId, ScopePredicateDigest, AdmissionFenceOrdinal)` may enter Closing on that owner: it cancels matching reservations/intents and manifests committed work as non-revocable. Effective is terminal for that ordinal and requires every matching outbox acknowledgement, cancellation, target/external result, ledger/capacity/posting settlement, and lease settlement. A successor ordinal never reopens or mutates that Effective fact; after a recorded admission violation invalidates the old global cut, it creates a separately keyed Closing cycle whose manifest is the union of every still-restrictive prior-cycle obligation and every newly visible/violating winner. The finite same-ordinal owner receipts then produce that ordinal's global effect-cut fixed point; no matching content-producing read, mutation, or external effect can escape it.

For a human edit, regeneration request, approval, rejection, or abandonment, `ProposalMutation:ReserveUserActionIntent` atomically appends the `Reserved` lease plus an immutable target-limited action intent/outbox on `ConversationAgentState`. The intent binds the original `User` principal's stable actor/Party/role/binding evidence, exact operation and target version, client/logical-command/idempotency identity, expected owner revisions, protection-key alias, and—only for an edit—the submitted bytes sealed under the target interaction DEK; the directory projection exposes no content. `CommitConversationEffect` binds that exact intent revision and digest. A reserved intent authorizes nothing and Closing cancellation consumes its outbox without a target read or mutation. After commit, either the still-authenticated original request or the existing `Interaction` Workflow may execute `RecoverCommittedUserProposalMutation` from that outbox. The recovery principal re-evaluates every current role, Party, Conversation, safety, lifecycle, and target precondition inside the committed lease and records the exact positive action or typed negative result; actor revocation or dependency failure therefore converges rather than impersonating the human or cancelling the lease. It cannot change operation, payload, actor, target, or expected intent, initiate an action, satisfy a second-party requirement, or expose the sealed bytes through workflow state. The target append records both original-human decision evidence and Workflow execution evidence, then the exact target revision acknowledges the outbox and settles the lease. API/workflow races use the same idempotency identity and expected target revision; crash or lost acknowledgement reads only the directory intent, interaction, and lease owners.

**Common deletion admission/effect cut:** Both deletion origins execute the same scope-aware cut before any deletion inventory candidate can be built. Every unleased external phase first has an interaction-owned authorization append whose exact revision is the sole capability for its external owner: existing `RateAdmissionAuthorized` plus `OpenInteractionLeaseAuthorized` for rate/open, `BudgetReservationAuthorized` for Budget reserve, and `CapacityAdmissionAuthorized` for allocator acquire/queue. Their external result/acknowledgement appends are distinct and cannot create a new phase. From the recorded origin, approved `GovernanceScopeV1`, current migration `Ready` epoch/guard, and authoritative directory/effect-authorization namespace high-water, the deletion Workflow records `DeletionScopeAdmissionFenceAuthorized`; only that revision lets `EXT-HOST-1` atomically install the predicate. The guard rejects every later matching permit, User-action-intent reservation, lease acquire/commit, or rate/open/Budget/capacity phase-authorization append, while permitting only exact result, settlement, cancellation, acknowledgement, deletion-cut, and guard-repair commands for work authorized before its receipt. It is independent of writer process/migration epoch and preserved across repair. Exact lookup resolves lost acknowledgement.

After the admission-fence receipt, the Workflow enumerates the finite authoritative `ConversationAgentState` owner cohort at that receipt: source deletion has its one owner, while exact interactions group permits by stored source Conversation and fail closed on unresolved binding. Each owner appends Closing for the exact `AdmissionFenceOrdinal` and manifests matching permits, creation/workflow-start/User-action-intent outboxes, leases, and every interaction-owned rate/open/Budget/capacity/posting authorization, decision, result, and acknowledgement through exact count/hash/high-waters. The fence makes every pre-boundary authorization a manifested obligation and every post-boundary authorization append lose. Approval selects exactly one version, pins `ApprovedVersionId`, removes edit, regenerate, and approve, and freezes expiry. `ExpiresAt` applies only while awaiting a decision and is enforced on every read and command regardless of timer delivery. `PostingPending` is uninterruptible: nothing leaves it except the posting attempt's own conclusion, so no removal, block, suspension, or abandonment can act on a post in flight; each is applied on exit if the attempt did not post. The attempt carries a stored deadline — no shorter than the AD-6 `EXT-CONV-AI-1` seam-2 posting timeout, with no more specific duration fixed by the PRD or this spine [ASSUMPTION ARCH-A-14] — evaluated on every read, command, and recovery after a process loss regardless of timer delivery, and never extended: an elapsed deadline concludes the attempt as timed out, the `MessageId` lookup below then runs, and the proposal moves to `Posted` with `LateConfirmed` if the message is found or to `PostingFailed` if the lookup finds no posted message; an unavailable lookup leaves it `PostingPending` and the lookup is repeated on the next read, command, or recovery. `PostingFailed` allows a bounded audited retry of at most 3 attempts within 15 minutes of the first `PostingFailed` command's `EvaluatedAt` [ASSUMPTION A-7] — a deadline computed as origin plus window plus AD-12's `PausedDuration`, since AD-12 pauses this clock while the tenant kill switch is pulled or the Agent is disabled — and an administrative retry is one audited attempt per command, after which the proposal persists until an Eligible Approver abandons it, the Tenant Agent Administrator administratively retries it or, audited and without Conversation read access, abandons it only when the Source Conversation is gone or inaccessible to the Agents service principal, or the system abandons it on a detected removal or an unresolvable Source Conversation (below). Failed or incomplete generated content, when retained, is a separate `GenerationFailureRecord` under AD-14 protection and is never a `ProposalVersion`. Abandon is legal from every awaiting-decision state, from `Approved`, and from `PostingFailed`; `PostingPending` accepts no abandon at all and completes or fails on its own terms. An Eligible Approver may abandon an `Approved` or `PostingFailed` proposal; the Tenant Agent Administrator may also abandon an `Approved` proposal, or a `PostingFailed` proposal whose Source Conversation is gone or inaccessible, audited and needing no Conversation read access (FR-33); both are permitted while the Agent is `Disabled` or the tenant is `Suspended`. A proposal that has stood in `Approved` or `PostingFailed` for longer than its original expiry duration in total, excluding `PausedDuration`, is system-abandoned with reason `PostingWindowElapsed` — for `PostingFailed`, once the `MessageId` lookup below finds no posted message — and counts as decided for SM-3; an administrative retry is refused with a typed reason once this bound has elapsed. The administrative retry and the Tenant Agent Administrator's human abandon are `ProposalResolution` commands needing no Conversation read access. System abandonment carries a typed reason (`NoEligibleApprover`, `SourceConversationUnavailable`, `RemovedInConversations`) and, per AD-7's membership re-check, now also fires from `Approved` and `PostingFailed` on a detected removal or block, not from `PostingFailed` alone: the `Approved`/`PostingFailed` -> `Abandoned` (`RemovedInConversations`) transition runs only after the `MessageId` lookup below finds no posted message. Posting is at-least-once, so before every retry attempt and before any exit from `PostingFailed` — covering a human or administrative abandon, an automatic or administrative retry, and the system's own `RemovedInConversations`, `SourceConversationUnavailable`, or `PostingWindowElapsed` abandonment — the system looks the approved version's `MessageId` up through the AD-6 `EXT-CONV-AI-1` seam-2 existence read (skipped only for a `PostingFailed` proposal whose failure was a pre-post re-validation that never attempted a post). The lookup is always skipped for an exit from `Approved` — a human abandon, or the system's `RemovedInConversations` or `PostingWindowElapsed` abandonment — because no post was ever attempted from `Approved`, so a detected removal or an elapsed posting window abandons it directly. A found message moves the proposal to `Posted` with `LateConfirmed` recorded in Audit Evidence and status, and the requested exit is rejected with a typed reason instead; a proposal whose approved version is in the Conversation is never recorded `Abandoned`. For an abandon exit, a typed absence and a typed `ConversationDeleted`/`PrincipalRemovedFromConversation` answer both count as no posted message; for a retry exit, only a typed absence permits the retry. An unavailable lookup refuses the `PostingFailed`-origin exit and the proposal stays `PostingFailed`; it is re-evaluated on the next post attempt or membership re-check instead. An automatic post is carried by a system-approved posting record — not a Proposed Agent Reply, and with no human Approver — that reuses these same `ProposedAgentReplyState` posting values from `Approved` onward and is referenced by the Agent Call, so proposal state is never duplicated (FR-8, FR-11, FR-18): the generated version is the approved version and the generation success instant is the approval instant; the pre-post re-validation, `PostingPending` with its stored deadline, `PostingFailed` with the same bounded retry — automatic and administrative, on the same terms and bound as a human-decided proposal above, not "no further retry" — the `MessageId` lookup, `LateConfirmed`, and the `PostingWindowElapsed` bound all apply on the same FR-18 terms. No Eligible Approver is resolved or referenced in Automatic Response Mode: wherever an FR-18 row names an Eligible Approver, the posting record substitutes any current Conversation Facilitator of the Source Conversation, and the Tenant Agent Administrator's abandon of a `PostingFailed` posting record carries no accessibility condition (FR-33). The posting record remains in the AD-7 `ConversationAgentState` non-terminal-proposal index until it reaches a terminal `AgentInteractionStatus` member — `Posted` when the record is `Posted`, `PostingFailed` when it is `Abandoned` — which releases the caller's per-Party concurrency slot and starts the §9 retention clock; an automatic call whose posting record is non-terminal is non-terminal. Terminal proposals preserve all versions and never post.

**Durable-before-post protocol:** Human approval at the expected proposal revision appends only `Approved` with the immutable selected version and approval evidence. Automatic mode creates the equivalent system-approved record without a human Approver. After every required pre-post validation passes, a separate deterministic `BeginPosting` command at the then-current expected revision appends only `PostingPending(PostingAttemptId, MessageId, ApprovedVersionId, PostingDeadline)`; that committed event is the sole authorization for the Conversations append. **Operation-family classification:** The administrative-retry request and the Tenant Agent Administrator's human abandon are lock-bearing `ProposalResolution` public commands needing no Conversation read access. Once an administrative-retry request is accepted, the workflow's `MessageId` lookup, full pre-post re-validation, durable `BeginPosting`, and posting attempt each declare `ConversationPosting`; the command/activity split prevents the administrator request from inheriting Conversation membership while ensuring that the actual post cannot bypass posting gates.

**Administrative-retry availability:** API, BFF, and UI consume one server-evaluated `CanAdministrativeRetry` verdict covering a remaining attempt in the shared three-attempt bound, the adjusted 15-minute retry deadline, a non-safety failure reason, active Agent and unsuspended tenant state, and the latest `MessageId` lookup result. An administrative retry may consume any remaining shared attempt; it does not wait for an automatic sub-budget to exhaust. Automatic and administrative retry authorizations append at the same expected proposal revision, so exactly one concurrent winner consumes an attempt and every loser refreshes without posting.

It quiesces ingress and all legacy writers over the exact topology cohort, freezes the finite inventory, installs the current migration-epoch/directory-capability append guard at the EventStore boundary, revokes the legacy direct-write capability, idempotently writes content-free `MigratedFrom` members/outcomes/protection evidence, and proves two identical post-fence high-water scans before `DirectoryReady`. Every disconnected, queued, restored, or stale writer is rejected at append; an accepted post-fence legacy write is impossible under ready evidence and invalidates the gate as an integrity failure. The protected-or-exact-empty predicate is mandatory. Legacy plaintext remains `PayloadProtectionUnavailable` and is governed by Open `OD-LEGACY-PLAINTEXT-DISPOSITION-1`; no migration/eradication outcome or immutable-history exception is inferred. Restart, duplicate, wrong principal, cross-tenant/wrong-stream, unavailable protection/spool, concurrent Begin, EventStore-fence installation/revocation, stale/disconnected/restored writer, projection lag, accepted-write invalidation, cross-tenant key-alias substitution, repair, and migration-outbox loss are required fixtures.

**Mirror outcome:** A typed permanent refusal from Conversations ends retry for that current mirror attempt and derives `MirrorRefused`. A refused `Remove` leaves `Blocked` authoritative; a refused `Readmit` leaves `ReadmitPending`. The authorized successor action is direction-aware: re-set starts a fresh `Remove`, clear starts or repeats `Readmit`, and re-set from a refused readmission returns to `Remove`. `ConversationAgentState`, public reads, status, and `product-metrics` carry the current record and its mutually exclusive derived status; SM-C4 counts only Conversations whose current outcome is `Refused`.

**Mirror record:** `ConversationAgentState` stores one versioned `CurrentMirror(BlockVersion, Direction, Outcome, AttemptId)` where `Direction` is `Remove` or `Readmit` and `Outcome` is exactly one of `Pending`, `Confirmed`, or `Refused`; `MirrorPending` and `MirrorRefused` are mutually exclusive public derivations of that record, never independent flags. A set or clear at the current expected `BlockVersion` increments the version, creates a new deterministic mirror attempt, and supersedes every lower-version record; late acknowledgements or refusals for a superseded attempt are audited but cannot change current state. A refused `Remove` leaves `Blocked` authoritative; re-setting starts a new `Remove`, while an authorized clear starts `Readmit`. A refused `Readmit` leaves `ReadmitPending`; an authorized clear repeated at the current version starts a fresh `Readmit`, while re-setting the block starts `Remove`. Starting either successor replaces the current `Refused` outcome with `Pending`; no standalone command clears the flag. SM-C4 counts a Conversation only when its current mirror outcome is `Refused`, never for superseded history.

**Mirror execution:** The Agents Dapr membership-mirror workflow is the sole initiator whenever the current record is `Pending`: `Remove` invokes the AD-6 AI-participant removal seam and `Readmit` invokes its idempotent membership seam under the same deterministic `AttemptId`. A lost acknowledgement is resolved through the fresh participant-state read: absent confirms `Remove`; present with the required identity/type/role confirms `Readmit`; the opposite state retries the same id unless the seam returns a typed permanent refusal, and unavailable or stale evidence leaves `Pending`. Startup and bounded recovery sweep every pending current record. Confirmation/refusal appends at the named `BlockVersion`; a superseded result is audit-only.

**Party-type check:** AD-7 always validates `hexa` by the immutable provisioned Party id. Its earlier unqualified AI-type check applies only when `EXT-PARTIES-1` selects Branch A; under Branch B the PRD A-27 Organization-typed identity is valid by id and is never replaced merely because an AI type later becomes available. While the record is `Uncommitted`, either branch may support contract development but neither can support launch evidence or `RQ-1`.

### AD-8 - Approver Policy Resolution

- **Binds:** FR-7, FR-13, FR-15..FR-18, FR-20.
- **Prevents:** each proposal workflow inventing a different meaning for facilitator, role, or predefined approver, or a caller approving their own call.
- **Rule:** ApproverPolicy is Agents-owned configuration with V1 sources Conversation Facilitator, predefined `PartyId`s, and tenant roles; the caller source is retired on the FR-23 deprecate-and-reject register. Conversation authority resolves to `ParticipantRole.Facilitator` [ASSUMPTION A-3], carried on the stable legacy wire identifier `ApproverPolicySourceKind.ConversationOwner` and labelled Conversation Facilitator on every surface; adopting a Conversations owner field requires an AD-8 amendment and a new `ApproverPolicyVersion`, and in-flight interactions keep their snapshot. Resolution is Conversation-scoped and Parties-authoritative: a source contributes only current Participants holding read access whose Party record is freshly resolved as active and human through `EXT-PARTIES-1`. The Eligible Approver predicate (resolved now, not the caller, not the last editor of the version, not the Approver who requested a regeneration of the version under decision, holding current Conversation read access) is applied at configuration time (every predefined Party is freshly validated as active and human; a non-human Party is rejected as `ApproverPartyInvalid(NonHuman)`, and a policy naming no Conversation-dependent source and fewer than two predefined Parties is rejected; Facilitator-only is valid), call time (typed `NoEligibleApprover` before Provider work), edit time (refuse an edit that leaves none), regeneration time (refuse before Provider work when excluding the requester leaves none), and approval time; current read access and Parties-owned human type and liveness are re-read at discovery, edit, regeneration, approval, rejection, abandonment, scheduled recheck, and audit-content inspection. A runtime source resolving to a non-human Party contributes no Approver; unavailable, stale, inactive, ambiguous, or missing Party evidence fails the action closed under the typed `ApproverPartyInvalid` reason family and never terminalizes a proposal. Every resolution appends an `AgentInteraction` event listing each resolved `PartyId` together with its stable `AuthenticatedHumanActorId`, `HumanActorBindingVersion`, and binding-validity evidence observed at that action; the action's human principal must match the authoritative actor bound to its `PartyId`, or it is rejected and audited. Later segregation-of-duties and anti-collusion checks compare these recorded actor ids rather than reinterpreting a current Party mapping. Discovery, queue, and count return full content only to a currently-readable resolved Approver, existence and state only to a previously-resolved Party that lost read access, and the absent-key response to anyone never resolved. Every source declares a PRD FR-7 disclosure category defaulting to operator-only, shared by API and UI; a restricted tenant-role source can never be user-visible.

**Regeneration segregation guard:** Before preparing a regeneration attempt, the server evaluates the same Eligible Approver predicate against the prospective regenerated version with the requesting Approver excluded; when no other Eligible Approver remains, regeneration is rejected before Provider work and the existing proposal remains decidable.

**Deletion-cutover lease:** Confirmation-mode call-time resolution is FR-8 step 6 and uses its own directory-owned `ApproverResolution` lease before step 7 begins. After closed content-free owner-local checks, the interaction Workflow reserves then same-owner commits the lease before the first Conversations roster/access or Parties classification/liveness/binding read; the exact resolved set or typed `ApproverResolutionUnavailable`/`NoEligibleApprover` result appends on `AgentInteraction` with the commit revision and settles the lease before Context. The scheduled per-proposal recheck uses the same lease kind with its own deterministic operation identity before its Conversations/Parties reads. A Closing winner cancels the reservation and no read begins; a commit winner is manifested and must record its exact authoritative/empty/unavailable result and settle. Edit, regeneration, approval, rejection, and abandonment already perform their corresponding action-time resolution inside the committed durable `ProposalMutation` intent protocol, so they do not acquire a second overlapping Approver lease.

**Atomic regeneration authorization:** `ProposalRegeneration` carries the current proposal revision and a client idempotency key. At one expected-revision append, the aggregate either rejects or records `RegenerationAuthorized(AttemptId, BaseVersionId, RequestingPartyId, RequestingAuthenticatedHumanActorId, HumanActorBindingVersion, ApproverPolicyVersion, ResolvedEligibleApprovers)` together with the prepared-attempt authorization, where every resolved approver tuple contains both Party and stable human actor identity; only that event permits Provider work. Concurrent commands race on the same revision, so every loser is rejected before Provider work. The resulting `ProposalVersion` is causally bound to that authorization and durably carries both requester identities and the binding version; approval evaluates the recorded requester actor for that exact version, never a mutable interaction-wide field or a current remapping.

**Scheduled resolution recheck:** Agents owns one durable per-tenant single-flight pass over every awaiting and `PostingFailed` proposal, with at most one in-flight resolution for any proposal, hourly by default and configurable per environment from 15 minutes through 24 hours [ASSUMPTION A-20]. A returned roster, typed `ConversationDeleted`, or typed `PrincipalRemovedFromConversation` is authoritative; timeout, denial, generic error, or any secondary tenant-role/access/Party evidence older than one configured cadence makes the whole pass unavailable. Typed deletion or removal moves either state to `Abandoned(SourceConversationUnavailable)` after the AD-5 `MessageId` rule. An awaiting proposal is abandoned as `NoEligibleApprover` only after two consecutive authoritative empty rosters at least one cadence apart; the first records `ResolutionEmptyPending`, and any intervening nonempty or unavailable pass breaks that two-pass sequence. A `PostingFailed` proposal records that marker but is never abandoned for an empty roster. An unavailable pass records `ResolutionUnavailable`, changes neither state nor `ExpiresAt`, and retries on the next pass. Later actions apply the same authoritative-versus-unavailable distinction, and call-time unavailability rejects as `ApproverResolutionUnavailable`, never `NoEligibleApprover`.

### AD-9 - Provider Adapter And Catalog Boundary

- **Binds:** FR-4, FR-5, FR-10, FR-24, FR-25.
- **Prevents:** provider SDK types, credentials, vault addresses, or provider-specific errors leaking into public contracts, UI, audit, or events.
- **Rule:** Provider integration is hidden behind Agents-owned generation adapters committed through `EXT-PROVIDER-1`; Provider and Agent Framework SDKs remain unselected until that record commits an immutable target and compatibility command — a deliberate deferral to that decision record, not a reflection of ecosystem immaturity, since Microsoft Agent Framework and Dapr Agents are both already GA — and catalog-truth publication is adapter-independent. `SecretReference` is the shipped opaque `ConfigurationReferenceId`: an operator-supplied, pattern-restricted handle with no infrastructure meaning (never a vault address or URI), bound to a secret only inside `EXT-SECRETS-1`; rotation keeps the handle; `SecretConfigured` is a durable catalog fact appended from a server-side resolvability probe (`Resolvable`, `Unresolvable`, `Denied`, `ObservedAt`), never computed in a query path; secrets are resolved only inside the generation activity immediately before transport, held in memory for the request, and never enter events, workflow state, exports, or logs. Public contracts and durable events expose only `ProviderId`, `ModelId`, safe capability/readiness metadata, versioned pricing, usage/status, and safe error classes; the `SecretConfigured` fact and the handle are visible to the Platform Operator only, and a tenant sees configuration problems solely as the AD-10 `PlatformNotReady` readiness code.

### AD-10 - Provider Capability Floor And Readiness

- **Binds:** FR-4, FR-5, FR-9, FR-10, FR-16, FR-21, FR-24, OQ-7.
- **Prevents:** incompatible capability shapes, stale or disabled catalog state trusted at runtime, snapshot and effective version conflated, or a retry reusing one attempt identity with changed provider inputs.
- **Rule:** The V1 capability floor per platform entry is `ProviderId`, `ModelId`, display label, enabled state, `SecretReference` and configured state, text-generation capability, context-window and max-output token limits, timeout policy, an optional per-model retry budget, the complete four-field data-handling record and its `DataHandlingVersion`, input/output pricing with currency and a `PricingVersion` that starts at 1 and strictly increases, and `CapabilityVersion`, a non-reusable unsigned monotonic sequence per (`ProviderId`, `ModelId`) in the `system` catalog; comparisons across keys are undefined and forbidden, and any observed decrease is a blocker. Every catalog write is serialized by the entry's expected EventStore revision (`EntryRevision`), and capability-bearing writes additionally carry an expected `CapabilityVersion`: below the stored value rejects as regressed, above as stale. An Agent whose selected entry is disabled remains inspectable read-only in a named migration state. Tenant-facing readiness is the platform entry joined with `TenantProviderEnablement`; a by-key query for a non-enabled or absent entry returns the not-found response and `EntryMissing` is reported only for the Agent's own currently-selected entry, or an in-flight interaction's previously-snapshotted entry, inside `AgentReadinessStatus`/`ProviderReadinessResult` — matching AD-2's carve-out exactly, no wider. `AgentReadinessStatus` (AD-15, AD-17) is a composite wrapper, never a bare enum: it carries the selected entry's `ProviderReadinessResult` as one field and the Agent-level growth states `ActiveNotProvenCallable`, `Stale`, and `AuthorityUnresolved` (AD-15) as sibling fields alongside it, not as alternate values of the same type. The public `ProviderReadinessResult` fixes `OperationalState`, `Callability`, safe `ReasonCode`, `CapabilityVersion`, `ObservedAt`, `ValidUntil`, and AD-17 `Freshness`, with the enum vocabulary and valid triples bound by `launch-readiness-register.md` section Provider Readiness Contract; that vocabulary includes the required additive `CurrencyMismatch` and `DataHandlingAcceptanceLapsed` members. `Degraded` is callable only when every hard gate passes; missing, stale, unconfigured, unpriced, invalid-limit, failed, disabled, not-enabled, regressed, currency-mismatched (`CurrencyMismatch`, AD-21), data-handling-incomplete or acceptance-lapsed (`DataHandlingAcceptanceLapsed`), unknown, or indeterminate state is `Blocked`, and unknown codes fail closed; a tenant sees platform-only blockers as the additive `PlatformNotReady` code. Enable/disable never bumps `CapabilityVersion`, so version comparison never substitutes for readiness. The interaction's durable capability high-water mark starts at the snapshot version and advances to every identified live version; every provider-dependent step requires a trust-bearing fresh entry with `CapabilityVersion` at least that mark, then advances the mark and re-evaluates every hard gate. The snapshot version is provenance; `EffectiveProviderCapabilityVersion` is the accepted live version a step consumed and is carried through its request, provider call, outcome, and evidence.

**Provider data-handling readiness:** A Provider/model is not eligible for tenant enablement without a complete data-handling record. Activation and every Provider-dependent step require the tenant to have accepted the current `DataHandlingVersion`; otherwise readiness is `Blocked` with `DataHandlingAcceptanceLapsed`, except that a Platform-Operator-declared tightening change carrying its field-level diff may continue under the last accepted version for 30 days. An undeclared or loosening change blocks immediately, and an explicit tenant decline ends any grace immediately.

**Data-handling version and grace contract:** Accept and decline name the current `DataHandlingVersion` and expected catalog and tenant-enablement revisions; a superseded version or stale revision is rejected. Tightening is computed cumulatively from the tenant's last accepted record to the current record, not merely from the immediately previous unaccepted version: retention must not lengthen, training use may only move toward opted out, and the normalized processing-region set may only narrow; any contractual-reference change, undeclared field change, or incomparable value requires fresh acceptance and cannot receive grace. Grace begins at the commit instant of the first unaccepted cumulatively-tightening version and stores one exclusive `GraceExpiresAt = StartedAt + 30 days`; later unaccepted versions never restart or extend it. A strict loosening at any intervening or current version, an explicit decline, or `EvaluatedAt >= GraceExpiresAt` blocks immediately with `DataHandlingAcceptanceLapsed`. Acceptance of the then-current version clears the grace and makes that version the new comparison baseline.

The public `ProviderReadinessResult` carries `CurrentDataHandlingVersion`, `InForceDataHandlingVersion`, and optional exclusive `GraceExpiresAt` in addition to its base readiness fields, so API and UI consumers never reconstruct grace or version state locally.

### AD-11 - Conversation Context Bounds

- **Binds:** FR-8, FR-9, FR-10, FR-31, OQ-10.
- **Prevents:** silent truncation, summary substitution, or provider calls on stale, partial, or over-budget context.
- **Rule:** The Conversation Context Policy is a self-versioned field on the `Agent` aggregate — not a separate AD-2 aggregate, and not independently published like `ContentSafetyPolicy` — snapshotted per interaction as `ContextPolicyReference`; its version is mutated only by the Tenant Agent Administrator and increments only on an accepted edit to the policy's own fields (its Approved Bounded Context Behavior declarations and the context-budget margin below), on the same independent-counter terms AD-4 gives `ConfigurationVersion`, `InstructionsVersion`, and `ApproverPolicyVersion`. V1 declares exactly one policy state, with no Approved Bounded Context Behavior; the public mode enum is `Unknown`, `Full`, `Bounded`, `Blocked`, and a request carrying `Bounded` while the policy declares no behavior is a typed rejection, never a fallback. V1 context is built only from authorized Conversations detail and visible timeline content, treated as untrusted data. Exact measurement uses the Provider/model tokenizer committed through `EXT-TOKEN-1`; a missing, unsupported, stale, or incompatible tokenizer blocks before Provider invocation. The Safe Context Budget is the model context limit minus the reserved output allowance, Agent Instructions, caller prompt plus system framing, and a margin defaulting to 10 percent (range 5 to 25) [ASSUMPTION A-5]; each term is recorded in audit evidence. If the complete source cannot be loaded fresh enough or exceeds the budget, the interaction records the additive `Blocked` context mode with a typed reason and creates no provider call, proposal, or Conversation Message. `ContextReady` authorizes progression but freezes nothing: immediately before generation or regeneration prepares an attempt, the step repeats the authorized fresh read, exact measurement, AD-10 check, and budget calculation, and fails closed on any change.

### AD-12 - Authorization, Dependency Uncertainty, And Emergency Stop

- **Binds:** FR-4, FR-5, FR-19..FR-21, FR-28, FR-33.
- **Prevents:** JWT-only or UI-only authorization, side effects on stale projections, or work continuing under a disabled Agent or stopped tenant.
- **Rule:** Authorization gates run before every side effect and fail closed on missing, stale, ambiguous, disabled, or unavailable dependency state. Tenant access comes from Agents' local Tenants projection; conversation access and context from Conversations authorized queries; Party state from Parties adapters/projections; provider readiness from the AD-10 view; approver rights from the AD-8 predicate on the snapshot policy; role rights from the FR-33 matrix carried by the AD-30 principal. Every side-effecting step (Provider invocation, proposal creation, edit, regeneration, approval, posting) re-reads Agent lifecycle, tenant enablement, the per-Conversation block, `hexa`'s own linked Party state per AD-7, and the per-tenant kill switch. A disabled Agent blocks new side effects for its proposals: awaiting proposals may be rejected or abandoned but never approved, edited, or regenerated; an `Approved` proposal cannot begin posting; only a `PostingPending` attempt already in flight completes or fails on its own terms; and, on the same terms as the kill switch below, a `PostingFailed` automatic or administrative retry is suspended with its retry-window clock paused while the Agent is disabled, resuming on re-enablement [ASSUMPTION ARCH-A-11]. The kill switch is a `TenantGovernancePolicy` fact read at its expected revision by every side-effecting step (family `TenantKillSwitch`). The Platform Operator pulls it immediately on a confirmed cross-tenant or unauthorized action (SM-4). A Release Operator trigger review is mandatory when an FR-28 operational rate exceeds its threshold over the rolling seven-day window — blocked-call share above 50 percent, unavailable-call share above 20 percent, Provider-or-generation failure share above 20 percent, or posting-failure rate above 10 percent — using the PRD numerator/denominator exclusions and minimum sample; below that sample the trigger is `InsufficientEvidence` and is reported rather than acted on, and an overdue review is `TriggerReviewOverdue`. The Release Operator pulls only as the recorded decision of that review. Two consecutive SM-3 or SM-7 misses at the 30-day, 60-day, or monthly launch-health review require a recorded Product disable-or-continue decision [ASSUMPTION A-17]. `product-metrics` is the only trigger source. Pulling the switch blocks call acceptance, Provider invocation, new descriptors, edit, regeneration, and approval tenant-wide; cancels queued admissions; and lets an `InvocationActive` attempt complete and dispatch its outcome command, including a version it records, without permitting a later post to begin while suspended. An `Approved` proposal stays `Approved` without starting a post or consuming a retry attempt. A `PostingPending` attempt already in flight is uninterruptible and completes or fails. `PostingFailed` automatic and administrative retries are suspended and their retry-window clock is paused — the affected proposal accumulates `PausedDuration` recorded at pull and updated at release — on the same terms as the disabled-Agent suspension above; the two causes accrue against the same `PausedDuration` field as the union of wall-clock time either cause was active, so an overlap between a pulled kill switch and a disabled Agent counts once, never twice, and the clock resumes counting down only once both causes have cleared, and AD-5's deadline is `origin + window + PausedDuration` under AD-28. Awaiting proposals remain rejectable or abandonable by humans and otherwise expire on their unchanged `ExpiresAt`; expiry during suspension records `ExpiredWhileSuspended` and leaves the SM-3 and SM-C5 denominators. The switch never system-abandons or deletes a proposal or Audit Evidence. Platform Operator or Release Operator releases it with audited justification; `agent-setup` and `launch-readiness` expose `Suspended` distinctly from Agent `Disabled`. A UI/BFF user session (the authenticated principal plus one browser circuit, identified by an opaque session id carried as the accepted-by reference on pending status) permits at most one pending command per resource within a lock-bearing family; the lock-bearing subset is `ProposalResolution`, `PolicyPublication`, `TenantBudgetUpdate`, `LegalHold` (also `LegalHoldRelease`), `ExportRequest` (also `ExportDownload`), `DeletionRequest`, `ProviderCatalogMutation` (also `TenantProviderEnablement`), `DataHandlingAcceptance`, `AgentSetupMutation` (also `TenantKillSwitch`, and the block/clear commands that set or clear `hexa`'s Conversation block), and `AgentActivation`; `AgentCallAcceptance`, `ProposalEdit`, and `ProposalRegeneration` are not lock-bearing and rely on the AD-29 client idempotency key; the family vocabulary is owned by the register matrix version. The advisory lock begins on submission and clears only on authoritative rejection or a terminal result; a client timeout forces refresh and never implies success.

**Deletion effect gate:** Directory readiness, the EventStore scope admission fence, and each immutable `(DeletionRequestId, ScopePredicateDigest, AdmissionFenceOrdinal)` AD-2 owner-cut cycle are authoritative state, not projection checks. `RegisterInteractionPermit` is the directory-first intake append and has no permit-bound lease; the migration capability and deletion admission fence serialize it. Only after that permit exists does each workflow-start, Approver-resolution, Context, membership, Provider, proposal-mutation, or posting phase reserve and conditionally commit its permit-bound lease. Reservation authorizes nothing, and only `CommittedToEffect` permits the exact target/read/effect and typed result. Unleased rate/open, Budget, and capacity phases instead require their exact interaction-owned phase-authorization revisions before external contact. The admission fence rejects later matching permit, intent, lease acquire/commit, and phase-authorization appends before owner Closing; Closing manifests every earlier winner, cancels reservations/intents, and retains committed/authorized work as must-converge. Effective waits for every outbox, lease, rate/open, Budget, pre-Provider/Provider capacity, posting, result, settlement, and acknowledgement. A successor ordinal creates a new cycle with carried-forward obligations and never reopens an old Effective fact. Its global cut requires every same-ordinal owner receipt plus the current ordinal's `ZeroAcceptedViolationsSinceInstall` proof; pre-cut and post-cut violation containment both assign exactly one successor. An existing predicate-scoped content guard stays continuously installed and gains an exact append-only successor ordinal/token binding from the latest installed binding plus the complete gap-free ordered invalidation chain before prepare; an overtaken binding authorization terminates obsolete without a guard append. Unknown or accepted guard violations invoke AD-2 recovery and cannot prove completion. Only `GovernanceScopeGuard(TenantId)`'s atomic `DestructionSealed` commit, conditionally made at the exact guard revision/compare token persisted by a `ProtectionFence` authorization while serializing against matching admission writes and overlapping hold registration/release, is `DestructionStarted`; an intervening guard mutation returns authenticated stale and no seal. It returns one deterministic non-expiring, revocable, single-use capability for an all-or-none `DestroyDekManifest` over the exact accepted targets; each later content target needs its own ProtectionFence ordinal and guard-owned conditional capability issuance; direct verification plus unrelated append, a stale no-hold authorization, or reuse of a batch capability is forbidden.

**Trigger calculation:** The blocked-call and unavailable-call shares count the distinct calling Parties with at least one blocked, respectively unavailable, call in the rolling seven-day window over the distinct calling Parties that attempted a call in the window, so neither share exceeds 100%; a share convenes a review only when its numerator holds at least 3 distinct Parties, or every calling Party in a tenant with fewer than 5, so one Participant cannot force a review. Excluded are only rejections at a rate limit set by the Platform Operator or Release Operator and `DataHandlingAcceptanceLapsed` rejections; a rejection at a limit the Tenant Agent Administrator lowered counts, is attributed as tenant-caused on the FR-25 surface, and a condition composed only of such rejections is closed by the Release Operator's recorded acknowledgement rather than a convened review; a condition composed only of `RescanPending` unavailability following a policy publication or secret rotation is closed by the Platform Operator's recorded acknowledgement; any other platform-caused condition keeps the one-business-day convening bound. Provider-or-generation failure share and posting-failure rate retain the PRD formulas. The minimum sample is 5 distinct calling Parties and 50 Agent Calls; a tenant with fewer than 5 calling Parties uses every Party that called and 10 Agent Calls per calling Party, never fewer than 20 nor more than 50. Below the minimum sample the trigger is `InsufficientEvidence`, reported and not acted on. A review decision is valid for 7 days or until the triggering rate rises a further 10 percentage points, whichever comes first; a condition persisting beyond that requires a new review [ASSUMPTION A-17]. Exceeding a threshold requires a Release Operator review within one business day; absence is `TriggerReviewOverdue` and blocks qualification. The switch moves only on the recorded review decision, except the Platform Operator's immediate confirmed SM-4 response. Gate and launch-health metrics remain separate calculations.

**Containment-safe switch protocol:** `TenantKillSwitch:ConfirmSm4Incident` and `TenantKillSwitch:PullContainment` never depend on `LR-TOPOLOGY`, `LR-TENANT-ACCESS`, `LR-AUDIT-PROTECTION-DELETION`, or another readiness record whose failure may be the reason for containment. They validate the target tenant, immutable command/idempotency shape, expected `TenantGovernancePolicy` revision, and fresh Platform-Operator authority. The emergency pull is legal only from a durable `Sm4IncidentConfirmed` fact for that target tenant naming immutable incident id, `CrossTenant` or `UnauthorizedAction` classification, confirming actor, source revision, and safe evidence digest; the pull event binds that exact fact and revision. A Release Operator instead uses the normally gated `RecordTriggerReviewDecision` followed by `PullReviewed`, with the tenant-role source freshly available and exact trigger-review decision recorded. Missing, stale, cross-tenant, differently classified, or conflicting evidence changes no switch state; a Platform action without confirmed SM-4 evidence never borrows emergency authority. The containment commands attempt their authoritative EventStore appends directly rather than requiring a prior `LR-EVENTSTORE` pass. If EventStore cannot append, the command returns unavailable and every call/side-effect path is already fail-closed by EventStore unavailability; the exact command is retried until the durable fact is visible. Release is a distinct `TenantKillSwitch:ReleaseReviewed` variant and retains all normal topology, tenant-access, audit, review/containment-evidence, and expected-revision gates. Incident confirmation, reviewed pull, containment pull, and release therefore cannot share one permissive or self-defeating matrix row.

**Kill-switch fact ownership and ordering:** `TenantGovernancePolicy(TenantId)` is the sole owner of `Sm4IncidentConfirmed`, `TriggerReviewDecisionRecorded`, `TenantKillSwitchPulled`, and `TenantKillSwitchReleased`; the immutable incident id is AD-29 `Sm4IncidentId`. `ConfirmSm4Incident` is a Platform-Operator command that verifies an existing content-free `SecurityEventLog` observation at its recorded source revision and appends only the confirmation at the expected governance revision. `RecordTriggerReviewDecision` is a Party-bearing Release-Operator command that binds the exact `product-metrics` contract/window/cohort and decision evidence. `PullContainment` then appends only from an exact unconsumed confirmation; `PullReviewed` appends only from an exact current review decision. Each accepted pull records the source fact and owner revision in the same aggregate history, so no projection, workflow, or UI state can manufacture the permission. Exact replay is idempotent; conflicting incident, review, target, or expected-revision evidence changes no state. This ownership and protocol are architecture mechanics implementing the already-bound FR-33 roles, not a new Product authority choice.

**Operation-family classification:** `DataHandlingAcceptance` is a lock-bearing public command family for a Tenant Agent Administrator's accept or decline decision on one tenant Provider/model version. Workflow-only `ProviderInvocation`, `ConversationPosting`, and `SystemTimer` activities are outside the browser-session advisory-lock classification and rely on aggregate expected revisions plus AD-13/AD-29 deterministic idempotency. The authoritative lock-bearing set therefore contains exactly ten families: `ProposalResolution`, `PolicyPublication`, `TenantBudgetUpdate`, `LegalHold`, `ExportRequest`, `DeletionRequest`, `ProviderCatalogMutation`, `DataHandlingAcceptance`, `AgentSetupMutation`, and `AgentActivation`. An administrative posting retry enters through lock-bearing `ProposalResolution`, then its workflow steps declare `ConversationPosting` as AD-5 specifies.



### AD-13 - Idempotent External Effects

- **Binds:** FR-4, FR-5, FR-8, FR-10..FR-18, FR-24.
- **Prevents:** duplicate provider attempts, duplicate messages, or duplicate proposal versions during retry, replay, or recovery.

- **Rule:** External side effects are causally tied to AD-29 identities. `AgentInteraction` is the sole owner of the prepared-attempt lifecycle and business facts; `RateLimitLedger` owns rolling consumption; `OpenInteractionLedger` owns caller concurrency leases; `BudgetLedger` owns monetary reservation balance and settlement; the shared capacity allocator owns admission leases and queue order only; Dapr Workflow owns execution only. Call processing has one directory-first registration followed by the Product-fixed FR-8 acceptance order. Before a permit: caller authorization, Party state, Source Conversation access, Agent lifecycle and tenant suspension, Party identity/dependency freshness, directory migration readiness plus barrier/block absence, Provider/model eligibility and production-like enablement, and payload-protection readiness pass at named revisions; no membership read or join occurs. `RegisterInteractionPermit` records durable intake registration and its protected creation outbox but does not assert `AgentCallAccepted`. The attestation passes only when both parts succeed, and refuses content-bearing activation or workflow progress on missing, stale, incompatible, no-op, or pass-through-wrapper evidence — this is exactly the pass-through-wrapper case the signed-identity pin exists to prevent, which a canary-only check cannot. **Deletion inventory and irreversible write fence:** For deletion only, “freezes” before fence ownership means a reversible candidate, not destructive authority. An accepted admission violation instead invalidates that ordinal's global cut and every derived candidate/token, preserving the old evidence while a separately keyed higher-ordinal owner-cut cycle carries forward obligations. Lost acknowledgement is recovered from the fence.

The accepted set becomes preparation-eligible only through the content-guard protocol. The guard is independently immutable at `(DeletionRequestId, ScopePredicateDigest)` and keeps append-only ordinal/token bindings. The first `DeletionScopeWriteFenceAuthorized` revision alone authorizes `InstallDeletionScopeWriteFenceEffect`; `RecordDeletionScopeWriteFence` records the authenticated continuous-install outcome and first binding. After a pre-seal admission recut, `AuthorizeDeletionScopeWriteFenceSuccessorBinding`, `BindDeletionScopeWriteFenceSuccessorEffect`, and `RecordDeletionScopeWriteFenceSuccessorBinding` add the new global-cut/current-ordinal/token binding to that same guard only after proving its original receipt, unchanged predicate, continuous installation, the latest actually installed predecessor binding, a complete gap-free ordered chain of intervening invalidated/tokenless ordinal containment receipts, and the new zero-since-install proof. They never remove or reinstall it. An authorization invalidated by a newer admission violation returns terminal `ObsoleteBindingAuthorization` without a guard append; the next authorization starts from the latest installed binding and carries the extended chain, so no invalid intermediate token must be retroactively bound and no containment evidence can be skipped. The guard rejects every later matching interaction/failure create or content append under any writer epoch, and every migration successor preserves all admission-fence ordinals/owner-cycle receipts plus every content-guard binding. Conflict before first installation permits only `SupersededBeforePrepare` plus same-id/same-predicate refreeze. Every defer, prepare, arm, and barrier step consumes the current admission receipt, continuous content-guard receipt/current binding, and current ordinal proof; none alone is irreversible authority.

The irreversible boundary uses the AD-2 start-barrier protocol, never “direct verification then append.” Before any `ProtectionFence` preparation, each legal-hold request registers its canonical scope on the same tenant `GovernanceScopeGuard` that owns deletion sealing; that guard commit is the hold-contention linearization, remains restrictive until exact release, and is recovered by exact lookup before its result is mirrored to the fence. `AuthorizeDeletionDestructionStartBarrier` records the stable `DestructionSealId` assigned with the accepted inventory plus the exact observed `GovernanceScopeGuard` revision/compare token, current admission ordinal/zero proof, current content binding/checkpoint, migration/fence receipts, accepted token, sorted key-target manifest/digest, and prepare-pinned lifecycle/store values. `CommitDeletionDestructionStartBarrierEffect` conditionally appends at exactly that observed guard revision and is serialized with every matching admission append and overlapping hold registration/release; any intervening guard mutation returns authenticated stale without a seal and reauthorization must bind the new revision. It rejects a contender that won after authorization unless the same fence recorded the exact effective deletion-allowed `OD-HOLD-DELETION-PRECEDENCE-1` disposition, which the guard consumes in its seal commit. It then atomically records immutable `DestructionSealed`; that instant is `DestructionStarted`. The result contains one deterministic non-expiring, revocable, single-use `DestroyDekManifest` capability bound to the entire accepted key-target manifest. It has no expiry/renewal branch; the capability key version remains verifiable for the full retention of the batch identity and protection-owner terminal outcome, including exact retry/lookup after consumption or revocation, and restore reuses the same seal and batch ids. The authenticated successful guard result records the actual `CommittedDestructionSealGuardRevision` separately; it is result evidence excluded from seal/batch identity and signed bytes. `RecordDeletionDestructionStarted` mirrors only the authenticated result on `ProtectionFence`; the protection engine consumes that batch atomically as all targets or none, returns an ordered per-target receipt vector, and exposes exact lookup after loss. Failure, change, accepted/unresolved violation/hold contention, or unknown commits no barrier and retains every fence/cut. A pre-barrier admission violation uses an explicit no-global-cut branch when necessary, assigns one successor ordinal, and requires the higher-ordinal full recut; if the content guard already exists, its continuous successor binding is also mandatory. After sealing, each authoritative same-predicate content violation receives exactly one ProtectionFence-serialized containment ordinal and immutable singleton target manifest. Its explicit `AuthorizeDeletionContainmentBatch` → guard-owned `CommitDeletionContainmentBatchEffect` → `RecordDeletionContainmentBatchIssued` protocol binds the immutable seal, current continuous content guard, violation receipt, manifest/digest, observed guard revision, and deterministic batch identity; changed/concurrent/lost outcomes use exact guard lookup, and only the recorded result may reach protection consumption. Unknown, malformed, outside-scope, or unresolvable proof blocks success. A later decision or migration successor cannot strand, revoke, or relabel the recorded branch.

### AD-23 - NFR-11 Recovery And Restore Qualification

- **Binds:** NFR-11, FR-24, FR-28, `LR-RECOVERY`.
- **Prevents:** recovery claims that lose accepted state, duplicate external effects, change terminal decisions, measure only process restart, or restore rebuildable stores past the truth.
- **Rule:** Recovery evidence uses the `EXT-TOPOLOGY-1` production-like failure-injection fixture over one frozen cohort of durable nonterminal interactions, measured by one injected monotonic clock from processing loss to full accounting, at most 15 minutes; UTC record freshness is never used for the duration. After restart every current gate is re-evaluated before a new or reversible effect and each such cohort member resumes, unwinds, or reaches a safe durable blocked/terminal state. A cleanup or irreversible governance branch already fixed by an immutable decision instead uses AD-17's dedicated gate-free recovery row and frozen/direct evidence; mutable readiness cannot strand it after the first effect, direct dependency unavailability retains its fence and retries, and recovery can never select a new outcome. Pre-fault terminal and branch decisions are immutable; evidence proves EventStore RPO 0 and inventories every deterministic identity. EventStore is the only backed-up business source of truth; the `EXT-HOST-1` content-free security-audit spool is separately durable operational write-ahead state and must drain idempotently after restore. Workflow state, allocator state, and read models are rebuildable and are never restored later than the EventStore restore point; after any restore all admission fences are invalidated, `InvocationActive` leases are reclaimed through outcome lookup, open reservations follow AD-21, and every nonterminal interaction re-enters recovery. `EXT-HOST-1` owns the procedure and `LR-RECOVERY` includes one restore-from-backup exercise. The same recovery run inventories every pending rate/open-lease/budget decision, safety-epoch activation, Conversation proposal-index checkpoint, `ProtectionFence` hold/export/deletion token, governance-protection workflow, unexpired trusted-envelope replay record, pending security-audit spool record, and architecture-decision projection position. External artifact/key/spool outcome lookup and the approved restore policy resolve acknowledgements that EventStore alone cannot prove.

- **Binds:** every stored instant, deadline, freshness evaluation, timer, latency metric, and product metric.
