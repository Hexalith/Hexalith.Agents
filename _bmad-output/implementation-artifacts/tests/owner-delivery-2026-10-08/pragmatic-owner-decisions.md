Recommendation, now selected by the owner: use the short-request profile above. Start with five explicit settings, one versioned profile and the existing signing/replay/idempotency code. Avoid introducing adaptive lifetimes, a new token service or a separate retry framework. The proposed figures are engineering choices for this delivery, not numbers mandated by a cryptographic standard.

The individual settings serve different purposes:

- **5-minute validity:** enough for ordinary service delivery, while an old request becomes unusable promptly. It is not the maximum age of the business operation. A 23-hour outage can still recover the same logical operation using fresh authorization and an exact prior-outcome lookup.
- **30-second future tolerance:** accepts small differences in issuance clocks. It must not turn exclusive expiry into a 30-second post-expiry grace period. Larger observed drift should fail the affected readiness gate and be corrected at the clock source.
- **10-minute routine overlap:** new requests use the current key; eligible older requests can verify with the previous healthy version. Compromise revocation overrides overlap immediately. Overlap is neither a key-rotation schedule nor permission to continue issuing with an old key.
- **24-hour recovery horizon:** the interval the owner promises to qualify for automatic outage recovery. Beyond it, retain unresolved intent/evidence and reconcile exact outcomes before any further effect; do not silently abandon the operation or repeat it blindly.
- **7-day replay retention:** a buffer above the 24-hour bound for retained first-seen evidence. The first accepted request establishes immutable retention times; retries do not extend them. Fingerprint-key retention must separately cover business idempotency, and deletion-capability verifiers must separately cover the full referenced batch/outcome lifetime. Neither inherits a 7-day deletion policy.

General key-management guidance supports explicit lifetimes, rotation and compromise handling; it does not select these five values for us. [OWASP key-management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html). HMAC authenticates message bytes using a shared key; current authorization, expiry and replay protection remain separate checks in this contract. [RFC 2104](https://www.rfc-editor.org/info/rfc2104/).

For sensitive approvals, reuse the existing independently governed approval issuer/public verification anchors when present. Keep its approval-signing keys outside the worker, recorder and export/custody runtime. The remaining human choice is who may approve each action; the software can implement that rule once the existing authority configuration is identified. No new identity platform is recommended.
